# U-Claw 决策记录

> 文档状态：持续更新  
> 初始整理日期：2026-08-07  
> 用途：记录已讨论方案、实验结果、已否决路线和待验证风险。

## 记录规则

- “已决定”表示可作为后续设计基线。
- “阶段性结论”表示当前证据支持，但仍需在新架构中重新验证。
- “已否决”表示不应在没有新证据时重复走同一路线。
- 会话中的历史实验发生在另一工作路径时，不默认认定其代码改动已出现在当前工作区。

## ADR-001：Node.js 运行时统一到 `v24.15.0`

- 状态：已决定
- 背景：原 portable runtime 使用 `v22.22.1`，OpenClaw 要求 `>=22.22.3 <23`、`>=24.15.0 <25` 或更高指定区间。
- 故障：OpenClaw 立即退出，`18789` 不可用，启动脚本随后停掉配置中心，浏览器显示 `ERR_CONNECTION_REFUSED`。
- 决定：发行 runtime 带 Node.js `v24.15.0`，不依赖客户系统 Node.js。
- 备注：会话中曾对多个安装脚本进行版本统一和回归测试；当前工作区是否包含全部改动需单独核对。

## ADR-002：产品形态使用独立桌面客户端

- 状态：已决定
- 背景：原 `portable/` 流程启动 Node.js/OpenClaw 后，需在浏览器访问本地网页。
- 问题：用户看到终端和浏览器地址栏，不符合普通 `.exe` 客户端预期。
- 决定：恢复或重建 Electron 桌面壳，由独立窗口加载 OpenClaw Web UI。
- 边界：底层仍可使用本地 HTTP gateway，但用户无需手动操作浏览器。

## ADR-003：不使用“大型单 EXE 每次自解压”

- 状态：已否决
- 背景：曾构建约 162 MB 的 Windows portable EXE，内部解包后约 916 MB、2.4 万个文件。
- 实际结果：双击后长时无窗口；任务管理器只有 `U-Claw` 外壳进程；`portable/` 数据目录尚未生成。
- 根因：NSIS portable 外壳静默解压大量文件，叠加 U 盘性能和 Windows Defender 逐文件扫描。
- 决定：`U-Claw.exe` 只作为轻量启动器。完整 runtime 单独放入 U 盘隐藏大包，首次按版本缓存到本机。

## ADR-004：不从 U 盘直接运行全量散文件

- 状态：已否决
- 背景：为避免单 EXE 每次自解压，曾改为预展开绿色目录版。
- 实际结果：向 ExFAT U 盘复制约 2.4 万个文件耗时超过 1 小时，写速曾降至约 `0.27 MB/s`。
- 附加问题：macOS 产生 `._*` AppleDouble 元数据，目标容量一度膨胀到约 1.7 GB；首次复制还漏了 Windows Node runtime。
- 决定：U 盘保留少量大文件和用户数据，runtime 在本机 SSD 展开并执行。

## ADR-005：启动界面与 gateway 初始化解耦

- 状态：已决定
- 背景：旧 Electron 逻辑等待 `ready-to-show`，主流程又同步等待 gateway，网关等待上限曾为 `180000 ms`。
- 实际结果：窗口出现约 2 分钟，界面出现后又等待约 3 分钟，整体超过 5 分钟。
- 决定：启动窗口立即显示，runtime 准备和 gateway 启动进入后台状态机。
- 限制：缩短 timeout 或修改 loading 文案不能解决根因。

## ADR-006：用户数据全部保存在 U 盘

- 状态：已决定
- 决定：配置、API Key、聊天、记忆、工作文件和授权数据必须位于 U 盘。
- 允许的本机内容：可删除、可重建的 runtime 缓存。
- 禁止：将 Electron `userData` 默认指向 AppData 后就声称是便携版。必须追踪 OpenClaw 所有持久化写入。

## ADR-007：首发仅支持 Windows 10/11 x64

- 状态：已决定
- 原因：`.exe`、macOS `.app`、ARM 与 x64 不能共用同一套运行时和原生模块。
- 决定：首发版专注 Windows 10/11 64 位 x64，普通用户权限启动。
- 后果：Mac 主要用于开发和制作时，仍需在真实 Windows 或 Windows 虚拟机上进行最终构建验证。

## ADR-008：正式 Windows 产品盘优先 NTFS

- 状态：已决定
- 选择：正式 Windows 客户盘优先 NTFS；开发阶段需要 Mac/Windows 双端读写时可使用 exFAT。
- 原因：NTFS 对 SQLite、配置和频繁写入更稳定，并具有日志恢复能力。
- 注意：文件系统不是性能唯一变量。U 盘控制器和 4K 随机读写速度同样关键。

## ADR-009：不使用旧版 Tuxera 制作 NTFS 产品盘

- 状态：已否决
- 实验环境：Tuxera NTFS `2021.1` + macOS `26.4.1`。
- 故障：只写入 `Windows_NTFS` 分区标记，未正确创建文件系统，检查报错 `Main boot region is invalid` 和 `Alternate boot region is invalid`。
- 处理：U 盘已恢复为 `exFAT + MBR`，卷标 `U-Claw`，并完成实际读写验证。
- 决定：正式 NTFS 盘在 Windows 上制作，或先验证当前 macOS 与 NTFS 工具版本完全兼容。

## ADR-010：隐藏目录不等于授权保护

- 状态：已决定
- 决定：`.uclaw/` 使用隐藏属性，用于减少误操作、保持根目录整洁。
- 安全结论：知道显示隐藏文件的用户仍可复制整套文件，因此隐藏不是防复制。
- 长期方向：使用 U 盘硬件标识和数字签名许可证，离线验证。

## ADR-011：先完成便携架构，再完成防复制

- 状态：已决定
- 第一阶段：任意受支持电脑可启动，数据只在 U 盘，本机只有 runtime 缓存，二次启动明显变快。
- 第二阶段：将原项目已有管理、模型和 OpenClaw 能力完整接入新客户端 UI。
- 第三阶段：接入启动授权、制盘自动开户、隐藏内置 New API 和服务端运营控制。
- 原因：授权方案不应遮蔽启动速度、数据路径和进程生命周期的基础问题。

## ADR-012：OpenClaw 与原生依赖必须可重现构建

- 状态：已决定
- 历史问题：`package.json` 使用 `openclaw: latest`，lockfile 仍指向 `2026.3.8`；安装时会导致 OpenClaw 和传递依赖漂移。
- 原生模块问题：交叉构建时曾混入 macOS 原生模块，漏掉 Windows `node.exe`，并出现 `@napi-rs/canvas` 主包与二进制版本不一致。
- 决定：锁定 OpenClaw 具体版本；在 Windows x64 目标环境准备依赖；对 `.node`/DLL 架构和版本进行构建后校验。
- 当前风险：2026-08-07 工作区中，`u-claw-app/package.json` 仍是 `"openclaw": "latest"`，而 lockfile 产物为 `2026.3.8`。

## ADR-013：发行目录不采用“烧录”模式

- 状态：已决定
- 决定：普通 U 盘产品制作是“格式化 + 复制发行文件”，不是像光盘或系统镜像那样烧录。
- 目标展示：根目录只显示 `U-Claw.exe`，其余发行与数据文件收纳在 `.uclaw/`。

## ADR-014：当前 portable 作为后端基线，归档 app 只作参考

- 状态：已决定
- 决定：使用当前 `portable/` 和锁定版本 OpenClaw 作为 runtime、配置、数据和 Agent 能力基线。
- 归档代码：`u-claw-app/` 只参考 Electron 进程、端口、gateway 健康检查、preload/IPC 和窗口生命周期。
- 原因：Electron 主进程在 2026-06-20 归档后未继续功能同步，而 `portable/` 后续增加了本地模型、微信、内网代理、诊断和更新等能力。

## ADR-015：客户端使用 Electron + React/Vite + Adapter

- 状态：已决定
- 桌面容器：第一版使用 Electron，优先保证 Windows 10/11 x64 离线兼容、Chromium 一致性和 Node.js/OpenClaw 子进程管理。
- 前端：使用 React + Vite 自建 U-Claw 客户端 UI；NextChat 只作产品与交互参考，不直接 fork 为业务基础。
- 协议边界：在前端和 OpenClaw gateway 之间增加 U-Claw Adapter，由 Adapter 吸收 API、WebSocket 和版本差异。
- 兜底：OpenClaw Dashboard 保留为高级控制台，供尚未原生化的功能使用。

## ADR-016：自研产品代码统一放入 `product/`

- 状态：已决定
- 目录：Launcher、Electron、React、Adapter、共享契约、打包脚本和产品测试统一放在仓库根目录 `product/`。
- 上游目录：`portable/` 尽量保持原样；`u-claw-app/` 保持归档参考状态。
- Git：本地只保留一个仓库，`origin` 指向我们的 fork，`upstream` 指向原作者仓库。
- 分支：`main` 尽量跟随上游，`product` 承载我们的客户端产品开发。

## ADR-017：第三阶段采用隐藏内置服务和三类模型源

- 状态：已决定
- 内部来源：模型请求支持 `builtin`、`domestic`、`custom` 三类来源。
- 用户界面：只展示原有国产模型和纯自定义模型两类配置；`builtin` 不展示配置项，作为未配置时的默认来源。
- 路由：用户明确启用国产或纯自定义来源后，模型推理不经过内置服务；清除或关闭外部配置后恢复内置服务；外部来源失败时不静默回退。
- 制盘：为每个产品盘生成随机唯一设备身份，调用 New API 管理接口自动创建随机唯一用户名和专属 Token，并在自有后端保存映射。
- 密钥边界：U 盘只持有设备专属 Token；企业商家上游 Key 只存在服务端；隐藏启动密钥与模型 Token 独立。
- 运营：额度、限速、模型权限和封禁由自有 New API 动态管理。
- 防复制边界：目标为“防君子”。缺少隐藏启动凭据时不能启动；完整复制同一授权仍归入同一设备账户，共享额度和风控，不承诺抵抗完整镜像或逆向。
- 格式化：格式化会清空程序、授权和用户数据，不提供格式化后继续运行保证。

## 待形成正式决策的问题

1. 轻量启动器使用哪种技术实现：Rust、Go、C#/.NET 或其他方案。
2. `runtime.pkg` 的压缩格式和解压库。
3. runtime 缓存清理、多版本共存和回滚策略。
4. U 盘硬件标识的可用字段和稳定性。
5. 数据加密与换机可用性如何同时满足。
6. 强制拔盘时的数据保护和用户交互。
7. 启动性能的最终可验收秒数。
8. 代码签名证书、SmartScreen 声誉和发行签名流程。
