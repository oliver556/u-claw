# 便携启动器冷启动校验加速实施计划

- 日期：2026-08-19
- 范围：`product/launcher/`（Go 便携启动器）冷启动路径
- 目标：把 `U-Claw.exe`（U 盘直启）的二次启动从 ~30s 降到个位数秒、首次从 ~5min 降到 ~1min 级
- 前提：**不换语言、不重写**。Go 方向正确，仅调整 launcher 的运行时校验策略
- 状态：待评审

---

## 1. 背景与问题

用户实测：打包后的 `U-Claw.exe` 从 U 盘直启，**首次约 5 分钟、二次约 30 秒**。

经代码走读定位，慢的根因**不是语言、不是引擎（OpenClaw 仍是 Node，合理且无法替换）**，而是 Go launcher 在**每次冷启动**都对整个 runtime（Node + OpenClaw，几百 MB、数千文件）做**三次全量 SHA256 校验**：

| # | 位置 | 行为 | 读取介质 | 频率 |
|---|------|------|----------|------|
| 1 | `cache.go:131` → `validatePackageFile`（`manifest.go:214`） | `io.Copy(hasher, file)` 把**整个 runtime 归档**读完并 SHA256 | **U 盘**（慢盘） | 每次启动，**无条件**，且在缓存复用判断之前 |
| 2 | `cache.go:152` → `runtimeCacheUsable` → `runtimeTreeDigestAt`（`cache.go:219`） | 逐文件读取 + SHA256 **整棵已解压树** | 本机盘 | 每次启动 |
| 3 | `state.go:157` → `AcquireRuntimeLease`（`runtime_lease_windows.go` / `runtime_lease_other.go:14`） | 再一次逐文件 `CreateFile` + SHA256 **整棵树**，并对每个文件持有句柄 | 本机盘 | 每次启动 |

关键点：

- **#1 无条件运行在缓存命中短路（`cache.go:152`）之前** → 即使本机缓存完全有效，每次启动仍要把整个归档从 U 盘完整读一遍。这是二次 30s 的最大头。
- **#2 与 #3 在本机盘上把整棵树各哈希一遍**（共两遍）；Windows 上 #3 还逐文件 `CreateFile` 持句柄，叠加 Defender 实时扫描进一步放大。
- 首次 5 分钟 = 上述开销 + 真正的归档解压（U 盘→本机缓存）+ Electron / OpenClaw 首轮冷启动。

> 设计初衷是「U 盘可能被篡改，启动前验证运行时完整性」，方向合理；**问题在于把完整密码学校验放在了每次启动、且重复三遍**，属于启动性能反模式。

---

## 2. 安全边界（先定，再改）

本计划的核心是把校验从「**每次启动全量**」调整为「**解压时全量 + 热启动轻量**」。必须守住以下边界：

1. **解压路径（cache miss / 版本变化）保持全量校验不变**：归档 SHA256（`validatePackageFile`）、解压后整树 digest（`runtimeTreeDigestAt` 对 `RuntimeTreeSHA256`）、entrypoint 可用性，全部保留。信任的建立点集中在**这一次**。
2. **本机缓存目录是可信区**：`EnsureHostCacheOwnership`（`cache.go:40`）已保证缓存根为 launcher 独占、`0o700`、marker 守护、拒绝 symlink。热启动的信任建立在「这是我上次亲手校验并写入、且第三方无权限篡改的目录」之上。
3. **`AcquireRuntimeLease` 的句柄持有（TOCTOU 加固）与内容哈希是两件事**：句柄持有用于防止运行期被替换（见 `docs/superpowers/plans/2026-08-10-P2-T14-TOCTOU加固实施计划.md`），**保留**；每次启动重算内容哈希是可降级的部分。降级 lease 前需对照该 TOCTOU 计划做威胁模型复核。
4. **降级项默认可配置、可回滚**：提供开关（编译期常量或 manifest/env 标志）在需要时恢复「每启动全量校验」，用于高安全场景或问题排查。

## 3. 改动方案

### Fix 1（P0，最大收益 / 最低风险）：`validatePackageFile` 移到缓存命中判断之后

**现状**（`EnsureRuntimeCache`，`cache.go:108`）执行顺序：

1. `ValidateManifest`
2. 打开 packageRoot、打开归档（U 盘）
3. `validatePackageFile(archive)` ← **全量读 U 盘归档**
4. `Seek(0)`
5. mkdir cacheRoot、`removeStalePartialCaches`
6. `Lstat` cachePath + `runtimeCacheUsable` → 命中则 `return Reused`
7. 未命中 → 解压

**改为**：把「打开归档 + `validatePackageFile`」下沉到 cache-miss 分支，命中路径**完全不碰 U 盘归档**：

1. `ValidateManifest`
2. mkdir cacheRoot、open root、`removeStalePartialCaches`
3. `Lstat` cachePath + `runtimeCacheUsable` → 命中则 `return Reused`（**不触碰 packageRoot / 归档**）
4. 未命中：打开 packageRoot → 打开归档 → `validatePackageFile` → 解压 → 解压后全量 digest → `writeCacheMarker` → rename 提交

**收益**：消除每次热启动对整个归档的 U 盘全量读取（#1）。这一步预计吃掉 30s 中的大部分。

**安全**：无损失——归档 SHA 仍在真正解压时验证；命中路径信任的是本机可信缓存（边界 2）。

---

### Fix 2（P1）：热启动把整树内容哈希降级为轻量校验

#### 2a. `runtimeCacheUsable`（`cache.go:211`）

**现状**：marker 匹配 manifest → entrypoint 存在 → `runtimeTreeDigestAt`（**整树内容哈希**）。

**改为**：marker 匹配 manifest → entrypoint 存在 → **stat 级快速校验**，去掉整树内容读取：

- 方案（推荐）：解压时把每个文件的身份快照（相对路径 + size + mtime，Windows 另存 `fileIndex`/`VolumeSerialNumber`）随 marker 落盘；热启动只做**只读 stat 遍历**比对快照（无内容 IO、无 Defender 内容扫描）。
- 备选（更激进）：完全信任 marker + entrypoint，取消遍历。整启动最快，但整树完整性仅靠目录权限保证——**默认不采用**，作为可配置的「极速档」。
- 折中：在 marker 里记 `lastFullVerify` 时间戳，**首次热启动或每 N 天**做一次整树内容哈希，其余时候 stat 级——兼顾速度与周期性完整性。

#### 2b. `AcquireRuntimeLease`（`runtime_lease_windows.go` / `runtime_lease_other.go`）

**现状**：遍历整树逐文件 `CreateFile` + `io.Copy` 内容哈希，比对 `RuntimeTreeSHA256`；Windows 版对每个文件持句柄。

**改为**（需对照 P2-T14 TOCTOU 计划复核）：

- **保留** entrypoint 及关键文件的句柄持有（TOCTOU 防替换）。
- **去掉**每启动整树内容哈希；改用 `runtimeFileIdentity`（size + mtime + fileIndex，Windows 版 `hashRuntimeLeaseFile` 已在计算 identity）做身份校验。
- 评估是否仍需对**整树**逐一 `CreateFile` 持句柄——若 TOCTOU 边界只要求锁住 entrypoint / Node 二进制等关键文件，可大幅减少句柄数与 Defender 扫描量；若要求锁全树，则保留句柄持有但仍去掉内容哈希。

**收益**：本机盘两遍整树内容哈希（#2、#3）降为一次只读 stat 遍历（或更少），Windows 句柄/Defender 开销骤降。

---

### Fix 3（可选，若威胁模型要求保留全量校验）：让校验更便宜

在必须保留内容级校验的前提下择一/组合：

- **只校验归档单文件 SHA**（一次），信任解压结果，取消整树遍历；
- **并行化**整树哈希：`runtimeTreeDigestAt` 当前单线程逐文件 `io.Copy`，改 goroutine 池并行读+哈希（受盘 IO 上限约束，本机 SSD 有明显收益）；
- 以 **identity（size+mtime+fileIndex）** 全面替代内容哈希（介于 2a/2b 与全量之间）。

### Fix 4（可选，工程外围）：Windows Defender 排除

安装流程中（**须用户明确同意**）将本机缓存根加入 Defender 排除目录，进一步削减 #2/#3 的每文件实时扫描开销。属独立小项，不阻塞 Fix 1/2。

## 6. 分期与优先级

| 阶段 | 内容 | 风险 | 预期收益 |
|------|------|------|----------|
| P0 | Fix 1（重排 `validatePackageFile`） | 低（无安全损失） | 二次 30s 砍掉大半 |
| P1 | Fix 2a（`runtimeCacheUsable` → stat 级 + marker 身份快照） | 中（放宽热启动整树内容校验） | 消除本机盘一遍整树内容哈希 |
| P1 | Fix 2b（lease 去内容哈希、保留句柄） | 中（触及 TOCTOU，需复核） | 消除第二遍整树哈希 + Windows 句柄/Defender 开销 |
| P2（可选） | Fix 3（并行/单文件/identity） | 视选型 | 保留强校验时的兜底提速 |
| P2（可选） | Fix 4（Defender 排除） | 低（需用户同意） | 进一步削 Windows 扫描开销 |

**建议先合入 P0 单独出一版实测**，确认收益后再推进 P1；P1 合入前完成与 TOCTOU 计划的威胁模型复核。
