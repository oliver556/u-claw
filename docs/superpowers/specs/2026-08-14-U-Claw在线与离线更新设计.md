# U-Claw 在线与离线更新设计

- 日期：2026-08-14
- 状态：待用户审核
- 适用范围：Windows x64 首个对外发布版本

## 1. 目标

U-Claw 采用“双通道、同一更新核心”：

- 联网客户在 `系统 -> 发布更新` 中检查、下载和安装更新。
- 无法联网时，交付单文件离线更新器 `U-Claw-Update-x.y.z.exe`。
- 两条链路共用发布清单、`runtime.pkg`、Ed25519 验签、SHA-256 校验、更新事务和回滚机制。

本设计不采用脚本更新，不让客户手动覆盖 `U-Claw.exe`，不在更新时重新激活。

## 2. 已有基础

现有代码已具备：

- Ed25519 发布清单和 runtime manifest 验签。
- `runtime.pkg` 大小上限和 SHA-256 校验。
- `platform`、`arch`、`runtimeId` 兼容性校验。
- `sequence` 防降级和同序号替换防护。
- 受控暂存、原子切换、上一版保留和中断恢复。
- Launcher 在新版本成功启动后完成更新事务收口。

因此，本次不新建第二套更新引擎。新增工作聚焦于正式发布服务、离线更新器和产品流程收口。

## 3. 系统边界

### 3.1 域名与职责

```text
license.yiyong.me
└─ 激活、许可证状态、撤销、换盘和设备凭据

updates.yiyong.me
└─ 签名发布清单和静态更新包
```

两个域名可先指向同一台阿里云服务器，由 Nginx 按 Host 分流。更新文件由 Nginx 静态提供，不经过 Go 激活 API 进程。

### 3.2 信任边界

- 许可证签名 key 与 runtime 发布签名 key 必须独立。
- runtime 发布私钥仅存在受控发布环境，不放入阿里云静态服务器、U 盘、Launcher 或离线更新器。
- Launcher 和受信客户端内置 runtime 发布公钥。
- HTTPS 保护传输；Ed25519 签名和 SHA-256 校验保护发布物。HTTPS 不取代发布物验签。
- Windows EXE 代码签名暂不作为首版更新功能的阻断项，后续补充。它不取代 runtime Ed25519 签名。

## 4. 发布物与服务端路径

继续使用现有客户端协议：

```text
https://updates.yiyong.me/releases/stable.json
https://updates.yiyong.me/releases/packages/<release-id>/runtime.pkg
```

服务器目录：

```text
/srv/uclaw-updates/releases/
├─ stable.json
├─ beta.json                    # 首版不对客户开放，保留协议能力
└─ packages/
   └─ <release-id>/
      └─ runtime.pkg
```

`stable.json` 是已签名发布清单，至少包含：

- `id`、`version`、`channel`、`publishedAt`、`expiresAt`、`sequence`。
- 更新说明 `notes`。
- `platform`、`arch`、`runtimeId` 兼容性约束。
- 包大小和 SHA-256。
- 已签名 runtime manifest。
- `mandatory` 标记。首版仅展示严重性，不实施静默强制更新。

离线交付物：

```text
U-Claw-Update-x.y.z.exe
├─ 离线更新器程序
├─ 已签名发布清单
└─ runtime.pkg
```

离线 EXE 内嵌的清单和 `runtime.pkg` 必须与线上同版本发布物字节一致。不生成“离线专用 runtime”。

## 5. 在线更新流程

```text
用户打开系统 -> 发布更新
-> 点击检查更新
-> GET https://updates.yiyong.me/releases/stable.json
-> 验证清单签名、有效期、sequence 和兼容性
-> 展示版本、发布说明、包大小和是否重要
-> 用户明确点击下载并更新
-> 流式下载 runtime.pkg 到受控暂存区
-> 限制实际下载字节数，校验 SHA-256 和 runtime manifest
-> 请求关闭主应用并阻止新任务
-> Launcher 执行受控更新事务
-> 保留旧 runtime 作为 rollback pair
-> 切换新 runtime.pkg 和 version.json
-> Launcher 从 START 重新运行完整授权 gate
-> 启动新版本
-> 确认新版本进入稳定启动阶段后提交更新事务
```

首版只支持用户手动检查和明确确认，不后台静默下载，不自动安装。

## 6. 离线更新流程

### 6.1 客户操作

1. 客服或运营向客户发送 `U-Claw-Update-x.y.z.exe`。
2. 客户插入已激活的 U-Claw U 盘。
3. 客户关闭 U-Claw，然后双击离线更新器。
4. 更新器显示当前版本、目标版本、更新说明和目标 U 盘，用户确认后开始。
5. 更新成功后，更新器提供“启动 U-Claw”。

### 6.2 更新器行为

```text
枚举候选 U-Claw U 盘
-> 只接受包含 U-Claw.exe、.uclaw/version.json 和完整授权材料的受支持 U 盘
-> 多个候选时要求用户选择，不自动猜测
-> 读取当前版本和 runtimeId
-> 验证内嵌发布清单和 runtime manifest
-> 验证 platform、arch、runtimeId、sequence 和剩余空间
-> 确认 U-Claw 进程已退出；未退出则提示客户关闭，不强制终止
-> 调用与在线更新相同的 Launcher 受控安装能力
-> 原子切换、保留回滚版、落盘并读回验证
-> 退出更新器
-> 由 U-Claw.exe 重新执行授权 gate 和新版本启动
```

离线更新器不携带激活码、许可证私钥、AI 网关 Token 或任何客户专属秘密。同一离线更新器可服务所有兼容的正版 U 盘。

## 7. 激活与数据保护

更新不是换盘，不产生新的 USB 绑定，不重新消耗激活码。

更新流程不得写入、覆盖或删除：

- `license.json` 及其生命周期缓存。
- startup credential。
- AI 网关设备身份和短期凭据缓存。
- `.uclaw/data/` 中的用户数据、会话、配置和工作区数据。

更新后 Launcher 必须从完整 `START` 状态重新执行 USB 身份、本地许可证、在线状态或离线宽限检查。更新成功不能绕过授权 gate。

## 8. 版本、降级与兼容性

- 对外版本号使用严格 `MAJOR.MINOR.PATCH`。
- 每次发布的 `sequence` 必须单调递增，不得复用。
- 默认拒绝低于已接受 `sequence` 的在线或离线包。
- 同一 `sequence` 只接受同一 runtime SHA-256 和同一签名身份。
- 正常回滚只能回到当前更新事务保留的、已验签上一版。
- 如果未来需要跨版数据迁移，迁移必须可重入、可识别已完成状态，并在发布清单扩展版本化迁移约束。首版不新增通用迁移引擎。

## 9. 失败与恢复

| 失败点 | 处理 |
|---|---|
| 无网络、DNS 或 TLS 失败 | 展示“无法连接更新服务”，保留当前版本，可重试或改用离线更新器。 |
| 清单过期、验签失败或 key 已撤销 | 拒绝显示为可安装更新，记录脱敏错误。 |
| 下载中断 | 删除不完整暂存包，不修改当前 runtime。 |
| 包大小或 SHA-256 不符 | 拒绝安装并删除暂存包。 |
| U 盘剩余空间不足 | 切换前终止，显示所需空间。 |
| U-Claw 仍在运行 | 要求用户关闭；不强制杀进程。 |
| 原子切换中断 | Launcher 根据 `.update-transaction.json` 恢复到可验证的新版或旧版配对。 |
| 新版本无法完成稳定启动 | 保留 rollback pair，通过受控回滚恢复上一版。 |
| 授权校验失败 | 按授权状态机处理，不回退到首次激活。 |

## 10. 发布流程

```text
锁定源码和依赖
-> 构建 Windows x64 runtime.pkg
-> 生成 runtime manifest 和文件树哈希
-> 在受控发布环境使用 runtime 发布私钥签名
-> 生成并签名 stable.json
-> 使用内部公钥独立验签和校验包哈希
-> 使用同一 stable.json + runtime.pkg 生成离线更新器
-> 在真实 Win10/11 普通用户环境做在线和离线更新演练
-> 先上传 packages/<release-id>/runtime.pkg
-> 最后原子替换 stable.json
-> 保存已发布包、清单、构建日志和 SHA-256 审计记录
```

发布顺序必须“先包、后清单”，避免客户看到已发布但无法下载的版本。

## 11. 首版界面

`发布更新` 页面保留：

- 当前版本。
- `检查更新`。
- 检查中、已是最新、可更新、无网络、服务不可用和验证失败状态。
- 新版本号、发布时间、包大小和更新说明。
- `下载并更新`、进度、取消和失败重试。
- 存在可恢复上一版时的受控回滚入口。

首版不提供：

- 自动更新开关。
- 静默下载或静默安装。
- 面向客户的 beta 渠道选择。
- 任意版本降级。
- 远程脚本执行。

## 12. 验收标准

### 12.1 在线

1. `updates.yiyong.me` 通过 HTTPS 返回有效 `stable.json` 和对应包。
2. 客户可手动检查、确认、下载、安装和重启。
3. 断网、超时、过期清单、错误签名、错误哈希、不兼容 runtimeId 和降级包均不能修改当前 runtime。
4. 更新后会话、配置、授权材料和 AI 设备身份完整。
5. 新版本通过完整授权 gate 后才进入正常工作台。

### 12.2 离线

1. 断网 Windows 环境中，离线更新器可更新一个兼容的已激活 U 盘。
2. 多个 U-Claw U 盘同时插入时，不得未经选择直接更新。
3. 非 U-Claw 盘、未激活盘、授权材料不完整盘和不兼容 runtimeId 均被拒绝。
4. 篡改离线 EXE 中提取的清单或 `runtime.pkg` 后，安装必须失败。
5. 中途拔盘、进程崩溃和重启后，Launcher 能恢复到可验证的新版或旧版。

### 12.3 真实环境

- Win10 x64 和 Win11 x64。
- 普通用户，不依赖管理员权限。
- 至少两种 U 盘型号、两台电脑、多个 USB 接口。
- Windows Defender 开启状态。如出现误报，记录样本和处置结果，不将“关闭杀毒软件”写入标准交付流程。

## 14. 决策摘要

1. 主通道：`updates.yiyong.me` 在线更新。
2. 离线兜底：发送 `U-Claw-Update-x.y.z.exe`。
3. 不发送 BAT、PowerShell 或其他远程拉包脚本。
4. 不让客户手动覆盖 `U-Claw.exe` 或 `.uclaw/` 内文件。
5. 在线与离线共用同一 runtime 发布物和更新安全内核。
6. 更新保留原 USB 绑定、许可证和用户数据，重启后再执行完整授权 gate。
