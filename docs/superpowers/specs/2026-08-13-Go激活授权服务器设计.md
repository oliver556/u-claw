# Bavi-box Go 激活授权服务器详细设计

> 文档状态：第一版实施设计  
> 决策日期：2026-08-13  
> 权威上位方案：[《Bavi-box 第一版启动、激活与授权总方案》](../../第一版启动激活授权方案.md)
> 实施状态：待编码、部署和真实环境验收

## 1. 目标与边界

本项目是独立部署的公网授权控制面。负责激活码库存、USB 首次绑定、Ed25519 许可证签发、许可证生命周期、管理员操作、New API 设备映射和审计。

它不是激活页面，不进入 U 盘发行包，也不负责 Electron UI、OpenClaw 启动或模型请求转发。

```text
Windows U 盘客户端
  Go Launcher + 单一 Electron 客户端
              |
              | HTTPS / OpenAPI
              v
Linux x64 授权服务器
  Go service + PostgreSQL
```

第一版不做微服务、不做消费者密码账号、不做支付、不做自动充值、不保存企业上游 Provider Key。

## 2. 技术决策

- 语言：Go，版本跟随仓库正式 Go toolchain 决策。
- 构建目标：`GOOS=linux GOARCH=amd64 CGO_ENABLED=0`。
- 数据库：PostgreSQL，事务和唯一约束是并发正确性的权威边界。
- HTTP：严格 JSON + OpenAPI 3.1，只接受 HTTPS 网关转发或服务自身 TLS。
- 签名：Go 标准库 `crypto/ed25519`。
- 激活码摘要：`HMAC-SHA-256(activationPepper, normalizedCode)`。
- 激活码：26 位 Crockford Base32，约 130 bit，不计连字符。
- 缓存：第一版不引入 Redis。限流优先放公网网关；业务幂等由 PostgreSQL 保证。
- 更新：可共用部署平台、管理员身份和审计框架；不得共用授权签名 key、发行签名 key、业务表或发布包存储。

## 4. 客户端契约

`api/openapi.yaml` 是公开和管理 HTTP 契约唯一来源：

- 生成 Go request/response 类型和 handler interface。
- 生成 TypeScript 客户端类型，供 Electron main process 使用。
- Zod 只承担客户端运行时校验，不另行定义字段语义。
- CI 校验生成产物无差异。
- 许可证签名载荷另用固定字段顺序的版本化编码，并保留 Go/TypeScript golden fixture。

## 5. 数据模型与约束

### 5.1 `activation_inventory`

```text
id UUID PRIMARY KEY
username_normalized TEXT UNIQUE NOT NULL
username_display TEXT NOT NULL
activation_code_digest BYTEA UNIQUE NOT NULL
status TEXT CHECK (prepared, binding, active, revoked)
order_reference TEXT NULL
new_api_setup_status TEXT CHECK (pending, configured, suspended)
created_at TIMESTAMPTZ NOT NULL
activated_at TIMESTAMPTZ NULL
```

数据库只保存激活码 HMAC 摘要。明文只在生成时输出一次；批量输出必须进入受控交付流程。

`binding` 是外部 signer/KMS 调用期间的持久化租约状态。记录绑定请求摘要和租约时间；同一请求可接管过期租约继续处理，不同 USB 不能接管。只有加密授权材料落库后才转为 `active`。

### 5.2 `devices`

```text
device_id UUID PRIMARY KEY
inventory_id UUID UNIQUE NOT NULL
fingerprint_version TEXT NOT NULL
fingerprint_sha256 BYTEA NOT NULL
status TEXT NOT NULL
created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
UNIQUE (fingerprint_version, fingerprint_sha256)
```

第一版一套库存只绑定一个 U 盘；同一物理 U 盘不能占用多套库存。

### 5.3 `licenses`

```text
license_id UUID PRIMARY KEY
device_id UUID NOT NULL
status TEXT CHECK (active, disabled, revoked, expired, reissued)
revision BIGINT NOT NULL CHECK (revision > 0)
key_id TEXT NOT NULL
startup_secret_salt BYTEA NOT NULL
startup_secret_hash BYTEA NOT NULL
not_before TIMESTAMPTZ NOT NULL
expires_at TIMESTAMPTZ NOT NULL
replacement_license_id UUID NULL
created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
UNIQUE (device_id, revision)
```

### 5.4 `activation_attempts`

```text
activation_id UUID PRIMARY KEY
idempotency_key TEXT UNIQUE NOT NULL
inventory_id UUID NULL
device_id UUID NULL
license_id UUID NULL
request_fingerprint BYTEA NOT NULL
stage TEXT CHECK (requested, server_bound, committed, failed_before_bind)
artifact_envelope BYTEA NULL
artifact_key_version TEXT NULL
last_error_code TEXT NULL
created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
committed_at TIMESTAMPTZ NULL
```

相同幂等键、相同规范化请求返回同一结果；相同幂等键、不同请求返回 `IDEMPOTENCY_CONFLICT`。

`artifact_envelope` 保存许可证、startup credential 和设备模型凭据的 KMS 信封加密结果，用于响应丢失和同盘恢复。DB、日志和备份不得出现明文授权材料。解密权限只授予激活恢复 use case；每次解密写审计。保留周期覆盖许可证有效期或直到 reissue/revoke 后按策略清理。

### 5.5 其他表

- `new_api_bindings`：每设备唯一 New API 用户、公开 ID、配置状态和策略摘要。
- `token_grants`：只保存 `jti`、设备、许可证、策略、到期和撤销状态，不保存明文 Token。
- `audit_events`：操作者、动作、对象、结果、request ID 和时间；不保存秘密。
- `license_status_events`：许可证状态和 revision 的追加式历史，用于回溯与签名回执。

所有外键、状态 CHECK、唯一约束和索引在 migration 中声明。应用层检查只改善错误提示，不能替代 DB 约束。

## 6. 激活事务

`POST /v1/activations` 执行：

```text
规范化并验证输入
-> 计算激活码 HMAC 摘要
-> 开启 SERIALIZABLE 或显式行锁事务
-> 锁定 activation_inventory
-> 校验 username + code、prepared/configured 状态
-> 查询 idempotency_key
-> 校验 USB 指纹唯一性
-> 创建 activation_attempt
-> 创建 device
-> 创建 active license revision 1
-> 建立 New API binding
-> inventory 改为 binding
-> 写 audit/status event
-> 提交事务
-> 在受控 signer 中生成许可证和授权材料
-> KMS 信封加密授权材料
-> 第二个事务写入 artifact_envelope
-> inventory 改为 active
-> attempt 改为 server_bound
-> 返回结果
```

签名或 KMS 加密失败不能留下无法恢复的模糊状态。实现采用持久化状态机：第一个事务生成稳定 ID、待签名载荷和 `binding` 租约；签名并加密成功后，第二个短事务把 inventory/attempt 推进 `active/server_bound`。只有 `server_bound` 才算激活码已绑定并可向客户端成功响应。进程崩溃后 worker 或同请求接管过期租约并继续未完成阶段，不新建第二套绑定。

同码双盘并发由 inventory 行锁和唯一约束保证只有一个成功。同盘响应丢失由幂等键或用户名、激活码摘要、USB 指纹三元组定位记录，解密并返回同一份授权材料。不得自动删除已绑定记录。

## 7. 客户端写盘与 commit

服务端成功即代表激活码已经绑定。客户端随后：

```text
server_bound
-> 写临时 generation
-> flush/fsync
-> 原子替换三份授权材料
-> 读回
-> 本地 Ed25519 验签和 startup secret proof
-> POST commit
-> Electron 退出
-> Launcher 从头执行 gate
```

`commit` 只记录客户端完成度，不决定绑定是否生效。commit 丢失、客户端崩溃或 U 盘拔出时，服务器不得自动解绑；下次同盘激活进入恢复流程。

## 8. 状态与错误模型

不可回退边界是 `server_bound`：

```text
requested -> server_bound -> committed
     └----> failed_before_bind
```

- `server_bound` 前失败：允许修正输入后重试。
- `server_bound` 后失败：只允许同盘恢复，不允许自动释放激活码。
- `revoked/reissued/expired`：许可证终态，不进入首次激活。
- `disabled`：可由管理员恢复，但客户端不能自行处理。

统一错误响应：

```json
{
  "requestId": "req_...",
  "activationId": "act_...",
  "code": "ACTIVATION_SERVICE_UNAVAILABLE",
  "stage": "server_bound",
  "retryable": true,
  "supportCode": "ACT-NET-004"
}
```

公开错误只暴露稳定 code。用户名不存在与激活码错误统一为 `ACTIVATION_INVALID`。响应不包含 SQL、堆栈、内部 URL、完整指纹、原始远端响应或秘密。

## 9. 安全设计

- Ed25519 许可证私钥只在服务端 signer 中可用；客户端只内置公钥。
- 许可证 key、AI 网关 Token key、runtime release key 三者独立。
- 私钥来自 KMS 或只读 secret mount；禁止普通环境 dump、源码和镜像层保存。
- 可恢复授权材料使用 KMS 信封加密；数据加密 key 不落库，解密调用最小授权并审计。
- activation pepper 与签名私钥独立轮换和授权。
- 管理接口使用独立监听入口或网关策略、强身份认证、最小角色和来源限制。
- 激活接口按 IP 摘要、用户名摘要和 USB 摘要限流。
- 日志默认结构化脱敏；禁止记录 request body、Authorization 和完整激活码。
- PostgreSQL 强制 TLS、最小 DB 角色、加密备份和恢复演练。
- 所有管理状态变更写不可变审计事件。

## 10. New API 边界

```text
生成库存
-> 创建独立 New API 用户/设备策略
-> 人工设置余额、模型权限和限速
-> 标记 configured
-> 允许交付和首次激活
```

授权服务器只保存 New API 公开标识、设备映射、配置状态和策略摘要。不得保存企业上游 Provider Key。设备获得短期、可撤销 Token；撤销或 reissue 许可证时同步停止旧设备刷新资格。

New API 调用失败不能回滚已完成 USB 绑定。若发货前已要求 `configured`，激活事务只需验证映射存在；若发生下游临时故障，返回已绑定可恢复状态。

## 11. 更新服务复用

允许共用仓库或 control-plane 部署流水线、管理员身份、审计框架、监控和告警平台，以及 `client-policy` 中最低支持版本和强制升级策略。

必须隔离：

```text
授权 API                  更新发布
api.u-claw.org            updates.u-claw.org
PostgreSQL 授权数据        对象存储/CDN
license signing key       runtime release signing key
事务型高一致性             静态高可用分发
```

更新包不从授权 API 进程流式下载。授权服务故障不得导致已缓存更新包不可下载；CDN 故障不得影响本地许可证验签。

## 12. 部署与运维

```text
TLS/WAF/Rate limit
        |
Go activation-server (linux/amd64, >=2 instances)
        |
PostgreSQL primary + managed backup/PITR
        |
KMS/secret mount + structured logs + metrics
```

- `/health/live`：进程可用，不检查依赖。
- `/health/ready`：DB、migration 版本和 signer 可用；不泄露依赖细节。
- 监控：请求量、P50/P95/P99、激活成功率、错误码、DB transaction retry、签名失败、状态查询可用率、commit 滞留、reissue/revoke、New API 映射异常。
- 备份必须定期恢复演练，证明库存、绑定、许可证 revision 和审计可恢复；签名密钥恢复走独立受控流程。

## 13. 管理员 CLI

第一版不要求 Web 后台。提供受保护 CLI：

```text
uclaw-activation-admin inventory generate --count N
uclaw-activation-admin inventory import --file ...
uclaw-activation-admin inventory show --username ...
uclaw-activation-admin license disable --license-id ... --reason ...
uclaw-activation-admin license enable --license-id ... --reason ...
uclaw-activation-admin license revoke --license-id ... --reason ...
uclaw-activation-admin license reissue --license-id ... --reason ...
uclaw-activation-admin new-api mark-configured --device-id ...
```

危险操作要求显式 reason、确认目标摘要和操作者身份。CLI 输出默认脱敏，不显示激活码明文、startup secret 或 Token。

## 14. 测试与验收

- Go：激活码生成/HMAC、签名 golden、key rotation、KMS 信封加密与解密失败、状态机、错误脱敏、migration、事务 rollback、同码双盘并发、同盘幂等、commit 丢失和管理员审计。
- 跨语言：OpenAPI 生成物无漂移；Go 签发与 Launcher/TypeScript 验签共享 golden fixture；strict JSON、大小限制、超时和错误码一致。
- 生产：正式 HTTPS、DB、备份恢复、KMS/secret mount、管理员认证；双实例并发；响应丢失恢复；revoke/reissue 传播；日志、DB dump、备份和镜像秘密扫描。
