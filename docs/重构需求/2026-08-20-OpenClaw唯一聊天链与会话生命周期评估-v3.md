# OpenClaw 唯一聊天链与会话生命周期评估 V3

> 日期：2026-08-20
> 状态：已完成源码级验证；当前方案不具备实施放行条件
> 性质：V2 验证补正，不含业务代码实施
> 前置文档：
> - [V2 评估](./2026-08-20-OpenClaw唯一聊天链与会话生命周期评估-v2.md)
> - [Claude V2 评审](./2026-08-20-OpenClaw唯一聊天链评审报告-Claude-v2.md)

## 1. V3 结论

产品负责人本轮意见正确，与目标架构无出入：

1. U-Claw 应是“新界面、OpenClaw 原能力内核”。
2. 除界面、Electron 安全边界和必要协议映射外，不重写聊天业务逻辑。
3. Provider 凭据和历史图片连续编辑不是实施阶段探索项，而是评估成立前必须验证的事实。
4. 两项验证不能以“以后再补”“客户端临时兜底”或“降低 P0”结束。

V2 和 Claude V2 评审把两项事实留到“实施计划前验证”，阶段划分不正确。它们属于评估阶段。V3 完成源码级核验后发现：当前代码还不能满足目标架构，不能直接进入实施或发布。

## 2. 原 OpenClaw 前端函数能否直接调用

### 2.1 能直接复用的部分

必须直接复用 OpenClaw 的公开运行能力：

- `chat.send`
- `chat.history`
- `chat.message.get`
- `chat.abort`
- Session、Run、Agent、Skill、Tool、Artifact
- Gateway WebSocket 事件
- OpenClaw 的图片生成、图片编辑和媒体管理能力

这些能力包含真正的聊天业务逻辑。U-Claw 不应再实现第二套上下文、run、工具调用、图片任务或 transcript。

### 2.2 不能把打包后的原前端私有函数当 API 调用

当前锁定 OpenClaw `2026.7.1-2` 的 Control UI 是 Lit 构建产物；U-Claw 前端是 React 19。

OpenClaw 原聊天页中的确已有大量成熟处理：

- 按 session 管理 run 和队列。
- Gateway 重连恢复。
- `chat.history` 版本防串线。
- 流式段、tool stream、final 合并。
- 多会话和 split view。
- 附件草稿持久化。
- managed image 展示。

但这些函数位于压缩后的 `dist/control-ui/assets/chat-page-*.js`，为模块私有函数：

- 没有稳定导出。
- 函数名会随每次构建变化。
- 强绑定 Lit host state、生命周期和 DOM。
- 直接导入会把 U-Claw 绑定到 OpenClaw 私有构建细节。

因此，正确边界不是“重新实现 OpenClaw 聊天”，也不是“调用压缩包里的私有函数”，而是：

```text
U-Claw React 界面
  → 极薄 UI Controller / IPC
  → OpenClaw Gateway 公共协议
  → OpenClaw 原 Session / Run / Agent / Tool / Artifact 实现
```

若 OpenClaw 上游提供正式、稳定导出的 UI controller/store 包，可以直接依赖。当前安装包未发现该公开包。未公开前，U-Claw 只实现 UI 状态投影，不复制聊天权威和业务运行逻辑。

把原 Control UI 整页嵌入 `webview/iframe` 可以复用其全部前端逻辑，但无法实现真正独立的新界面，只适合作为临时对照基准，不作为产品架构。

## 3. 商业凭据验证结果

### 3.1 OpenClaw 本身具备 Provider 凭据能力：通过

当前锁定版本源码类型确认：

- `models.providers.<id>.apiKey` 支持字符串或 SecretRef。
- SecretRef 支持 `env`、`file`、`exec`。
- Provider 支持 `headers: Record<string, SecretInput>`。
- Provider 支持 `authHeader: boolean`。
- `config.apply` 会校验 SecretRef，并安排 Gateway restart。

所以“OpenClaw 能否读取商业凭据”答案是：能。

### 3.2 U-Claw 激活凭据是否已经交给 OpenClaw：未通过

当前激活产物把商业凭据保存到：

```text
.uclaw/builtin-model-credential.v1.json
```

凭据由 `builtin-credential-store.ts` 读取，再交给 `builtin-service-client.ts`。后者直接请求中转站：

```text
Electron builtin-service-client
  → Authorization: Bearer <deviceToken>
  → /v1/chat/completions
```

当前未发现以下桥接：

```text
激活 builtinCredential
  → OpenClaw models.providers.uclaw-commercial
  → apiKey SecretRef / headers
  → agents.defaults.model.primary
```

现有 `ProviderStore → openClawConfig.synchronize()` 只覆盖普通 Provider 管理页面保存的 Provider；没有把激活产生的 `BuiltinModelCredential` 注册为 OpenClaw Provider。

结论：OpenClaw 有读取能力，但商业激活凭据当前没有接入 OpenClaw。商业聊天仍依赖直连链。

### 3.3 Token 更新语义：已确认

当前版本 `config.apply` 是 restart write，不是纯内存热更新。激活、续期或设备 Token 更换后，正确流程必须包含：

```text
安全存储写入新 Token
→ 更新 OpenClaw Provider SecretRef/凭据来源
→ config.apply
→ Gateway 有序重启/重连
→ config.get + models/auth 状态读回
```

不能只更新 U-Claw 私有凭据文件而不通知 OpenClaw。

### 3.4 安全阻塞

当前暂存的 `portable/default-config.json` 含字面量 API Key。该文件属于默认配置和打包输入。无论 Key 是否临时，均为发布阻塞：必须撤销、轮换已暴露 Key，并改为运行期 SecretRef/安全注入。V3 不修改该用户变更。

## 4. 商业中转站聊天协议验证结果

当前暂存代码已开始增加：

- `stream:true`
- SSE 转发和 flush
- `stream_options.include_usage`
- `tools`
- `tool_choice:auto`
- tool call delta

方向正确，但尚不能判定“已兼容 OpenClaw Provider”：

- 对应正向流式/tool 合同测试尚未齐全。
- 当前 `go test ./internal/transport ./internal/modelproxy` 失败。
- 失败集中在新增 `Grant.BaseURL` 后测试 fixture 未同步，多个代理合同测试返回 `503 SERVICE_UNAVAILABLE`。
- 这批代码仍是用户暂存中的未完成修改，V3 未改动。

结论：中转站文本聊天协议处于开发中，尚未验证通过，不能作为删除旧链后的可用底座。

## 5. 历史图片连续编辑验证结果

### 5.1 OpenClaw 原能力：源码链成立

当前 OpenClaw 已提供：

- `image_generate` 同时支持生成和编辑。
- 生成结果保存为 managed media。
- 工具结果记录 `paths`、`attachments` 和媒体信息。
- Webchat assistant media 正式写入 transcript。
- `chat.history` 能恢复 managed image block。
- 下一轮 Agent 可从前一轮工具结果获得生成图路径。
- `image_generate` 的 `image/images` 参数可加载本地路径、`file://`、data URL 或 HTTP URL作为参考图。

因此 OpenClaw 后端具备这条原生链：

```text
第一轮 image_generate
→ 保存图片和路径
→ tool result / assistant media 写入 transcript
→ 第二轮 Agent 读取同一 session 上下文
→ image_generate(image=<上一张路径>)
→ Provider edit
```

这进一步证明 U-Claw 不应自己拼“上一张图片”。只要所有轮次走同一 OpenClaw session，Agent 和 Tool 可以使用原生记录。

### 5.2 商业中转站图片编辑协议：未通过

OpenClaw 的 OpenAI 图片 Provider 在有参考图时调用：

```text
POST /images/edits
Content-Type: multipart/form-data
image[]=<binary>
prompt=...
```

当前商业中转站只实现：

```text
POST /model-api/v1/images/generations
Content-Type: application/json
```

未实现 `/model-api/v1/images/edits`，也未实现 multipart 参考图转发。

结论：历史图片在 OpenClaw 内部可以连续引用，但经过当前商业中转站无法完成编辑。“修改上一张”目前是确定失败，不是未知风险。

### 5.3 U-Claw 展示映射仍需统一

即使后端编辑链补齐，U-Claw 仍必须让实时事件和 history 走同一 mapper。否则会继续出现：

- 第一轮生成后不立即展示。
- 切换会话后才展示。
- live/history 图片 identity 不一致。
- 断线恢复重复或丢图。

这部分是界面协议投影，不是图片生成业务逻辑。

## 6. 评估验收矩阵

| 事实 | 结果 | 结论 |
|---|---|---|
| OpenClaw 支持安全 Provider 凭据 | 通过 | 支持 SecretRef、自定义 headers、`authHeader` |
| 商业激活凭据已注入 OpenClaw | 未通过 | 仍停留在 builtin credential store 和直连 client |
| Token 更新可无感生效 | 有条件通过 | 需 `config.apply`、Gateway 重启和客户端重连 |
| 中转站支持 OpenClaw 文本流/tool 合同 | 未通过 | 代码开发中，现有测试失败，缺正向合同 |
| OpenClaw 保存生成图并供下一轮引用 | 源码通过 | transcript、managed media、tool path 链存在 |
| 商业中转支持图片编辑 | 未通过 | 缺 `/images/edits` 和 multipart 参考图 |
| U-Claw live/history 图片映射一致 | 未通过 | 当前仍有两套映射路径 |
| 真机端到端商业链 | 未执行 | 本机无激活 builtin credential；且上述确定缺口已阻塞链路 |

## 7. 对 Claude V2 评审的修正

Claude V2 结论“可以进入实施计划编制阶段，但需先完成两项阻塞性协议验证”不够准确。

正确表述：

> 两项验证属于评估本体。验证未通过前，架构方向可以冻结，但实施方案不能冻结，不能进入删除旧链或发布阶段。

Claude 提出的“图片连续编辑失败时可降低门禁或客户端临时补救”仍不接受。当前已证明 OpenClaw 原链具备编辑能力，缺口位于商业中转协议和 U-Claw 接入；应补齐这两层，不能另建客户端图片链。

## 8. 实施放行前必须补齐

1. 把 `BuiltinModelCredential` 注册为 OpenClaw 商业 Provider，使用 SecretRef，禁止默认配置字面量 Key。
2. 明确激活、续期、Token 轮换时的 `config.apply → Gateway restart → reconnect → readback` 流程。
3. 补齐中转站 OpenClaw 文本 SSE/tool 正向合同，并修复现有失败测试。
4. 实现 `/model-api/v1/images/edits` 和受限 multipart 参考图转发。
5. 用真实激活设备完成一次：

```text
OpenClaw chat.send
→ 商业中转
→ 多帧 delta/tool call
→ 第一轮生成图立即展示
→ chat.history 恢复同一图片
→ 第二轮修改上一张
→ 返回编辑图
```

6. 真机链通过后，才允许删除全部客户端直连并进入前端生命周期改造。

## 9. 冻结结论

```text
新界面可以新写。
聊天、上下文、run、Agent、Skill、Tool、图片任务不新写。
优先调用 OpenClaw 公共能力。
不依赖 OpenClaw Control UI 压缩私有函数。
商业中转必须补足 OpenClaw 所需协议。
验证失败是 P0 阻塞，不是降级理由。
```
