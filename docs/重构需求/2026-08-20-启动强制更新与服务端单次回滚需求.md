# U-Claw 启动强制更新与服务端单次回滚需求

- 日期：2026-08-20
- 文档类型：重构需求与已确认商业决策
- 状态：需求与 License/版本门禁顺序均已确认
- 影响范围：Bootstrap、启动链路、发布服务、更新服务、runtime 安装事务、正式产品 UI

## 1. 背景

当前产品仍存在页面内更新、启动后检查更新、用户主动触发更新等设计空间。

新的商业策略不再允许用户决定是否更新。正式程序只有在确认本机运行的是服务端指定最新版后才能使用。

本需求不是在现有页面更新功能上增加“强制”选项，而是重新划分更新职责：

```text
更新完全退出正式产品 UI
→ 版本检查和安装前移到程序启动阶段
→ 未达到服务端指定最新版时，正式程序不启动
```

## 2. 已确认的商业决策

### 2.1 每次启动必须联网检查版本

每次打开 U-Claw 都必须向服务端查询当前唯一正式版本。

客户端不能仅凭本地缓存、上次检查结果或本地版本号直接进入正式程序。

### 2.2 所有设备执行同一强制版本策略

不设计：

- 灰度 cohort。
- 用户更新渠道。
- 用户延迟升级。
- 忽略版本。
- 跳过版本。
- 继续使用旧版。

服务端存在新正式版本时，所有设备下次打开都必须升级。

### 2.3 更新服务不可用时，客户端不可用

已接受以下结果：

```text
CDN、版本服务或必要发布服务故障
→ 客户端无法完成最新版确认
→ 正式程序不可用
```

本需求不提供离线版本检查降级。

因此，现有 License 离线宽限不能绕过强制版本门禁。即使 License 本地或离线缓存仍有效，只要无法确认最新版，正式程序仍不得启动。

### 2.4 客户端没有本地业务回滚

最新版安装或启动失败后，客户端不得：

- 自动启动上一版本。
- 临时启动上一版本。
- 允许用户选择降级。
- 绕过版本检查进入正式 UI。
- 使用上一版本继续正常业务。

客户端只能保持阻断，等待服务端发布更高 release sequence 的修复版本。

### 2.5 服务端只保留上一稳定内容

服务端只需保留：

```text
当前正式版本
+ 上一稳定版本内容
```

上一稳定内容用于一次紧急服务端回滚。不需要多级版本历史回滚能力。

### 2.6 正式产品页面删除全部更新能力

正式产品 UI 中删除：

- 设置页更新入口。
- 检查更新按钮。
- 自动更新开关。
- 稍后更新。
- 跳过版本。
- 更新渠道选择。
- 手动下载安装包。
- 进入页面后的更新提醒。

正式 UI 的前置事实固定为：

```text
能够进入正式 UI
= 已完成本次启动版本检查
= 当前运行服务端指定最新版
```

## 3. 目标结构

```text
用户双击 U-Claw
→ 启动最小 Bootstrap / 强制更新器
→ 本地路径与基础安全检查
→ 联网读取服务端 requiredReleaseSequence
→ 验证版本策略真实性和新鲜度
→ 本地不是指定版本：强制下载、验签、安装、切换、重启
→ 本地是指定版本：继续商业 License 门禁
→ License 门禁通过
→ 启动正式 shell
→ 后台启动 OpenClaw Gateway
```

正式产品 UI 不拥有更新职责。

## 4. Bootstrap / 强制更新器

### 4.1 必须独立于业务 runtime

最新版业务 runtime 可能无法启动。版本查询和修复安装能力不能依赖该 runtime。

因此必须存在一个独立、极小、稳定的 Bootstrap：

```text
Bootstrap
├─ 查询强制版本策略
├─ 验证策略签名
├─ 下载发布包
├─ 验证大小、SHA-256、manifest 和签名
├─ 安装到 staging
├─ 原子切换 current
├─ 启动当前正式版本
└─ 当前正式版本失败时继续查询服务端修复版本
```

Bootstrap 不应包含：

- React 正式 UI。
- OpenClaw Gateway。
- 聊天和会话逻辑。
- Provider 业务配置。
- 模型请求。
- Skill 和 Tool 业务逻辑。

### 4.2 Bootstrap 不提供旧版本启动能力

Bootstrap 独立存在的目的，是在最新版业务程序损坏时仍能获取后续修复版；不是为了允许运行上一版本。

### 4.3 启动阶段状态反馈

更新执行发生在正式 UI 之前。

建议 Bootstrap 提供最小状态反馈：

```text
正在检查版本
正在下载
正在验证
正在安装
正在重启
等待服务端发布修复版本
```

该状态反馈不是产品设置页，也不提供跳过、稍后更新或降级选项。

是否使用独立图形状态窗口、系统原生对话框或其他最小反馈方式，留给后续启动壳方案统一确定。

## 5. 唯一全局版本策略

服务端维护一个全局正式版本指针：

```text
production.requiredReleaseSequence
```

所有客户端按同一指针执行。

“最新版”必须由单调递增的 `releaseSequence` 判断，不能只比较 SemVer 字符串。

建议版本策略至少包含：

```json
{
  "schemaVersion": 1,
  "policyEpoch": 107,
  "requiredReleaseSequence": 107,
  "releaseId": "release-107",
  "contentVersion": "1.5.0",
  "reason": "release",
  "manifestUrl": "https://cdn.example/releases/107/manifest.json",
  "manifestSha256": "<sha256>",
  "issuedAt": "<rfc3339>",
  "expiresAt": "<rfc3339>",
  "signature": {
    "keyId": "<key-id>",
    "value": "<signature>"
  }
}
```

客户端门禁：

```text
localReleaseSequence == requiredReleaseSequence
→ 可以继续后续启动门禁

localReleaseSequence != requiredReleaseSequence
→ 必须安装服务端指定 release
```

## 6. 服务端一次回滚

### 6.1 禁止直接降低 sequence

示例：

```text
上一稳定内容：sequence 105
故障最新版：sequence 106
```

服务端不能重新要求客户端直接运行 sequence 105。否则会与客户端 anti-rollback 防降级记录冲突。

### 6.2 使用“向前发布的回滚”

正确回滚：

```text
读取 sequence 105 的稳定 runtime 内容
→ 生成新的 manifest
→ 使用新 sequence 107 签名
→ 发布为全局最新正式版本
→ 所有客户端从 106 强制更新到 107
```

sequence 107 的业务内容可与 105 相同，但发布身份和签名必须是新的。

建议记录：

```text
contentVersion: 1.5.0
releaseSequence: 107
releaseReason: rollback
rollbackFromSequence: 106
```

### 6.3 服务端双槽位

```text
production.current
production.previousStable
```

正常发布：

```text
previousStable = current
current = 新正式版本
```

紧急回滚：

```text
使用 previousStable 内容生成更高 sequence 的新 release
→ 验证 CDN 和 manifest 可用
→ current 原子切换到新 release
→ 故障 release 标记 withdrawn
```

故障版本不能成为下一次可回滚的稳定版本。

## 7. 最新版启动失败

客户端行为固定为：

```text
最新版启动失败
→ 记录 releaseId、sequence、attemptId 和失败阶段
→ 正式 UI 不启动
→ Gateway 不启动或立即停止
→ 不启动本地旧版本
→ Bootstrap 继续查询服务端版本策略
```

服务端未发布更高 sequence 时，客户端继续不可用。

服务端发布修复版或向前回滚版后：

```text
Bootstrap 获取更高 sequence
→ 强制下载和安装
→ 重新启动
```

## 8. 更新发布顺序

必须先保证制品可用，再公开全局强制版本：

```text
构建 runtime
→ 生成 manifest、SBOM 和签名
→ 上传完整制品
→ CDN 分发完成
→ 服务端从 CDN 回读并验证
→ 最后原子切换 requiredReleaseSequence
```

禁止：

```text
先切换 requiredReleaseSequence
→ 后上传或等待 CDN 制品
```

否则所有客户端会立即进入强制门禁，但无法获得更新包。

## 9. 客户端更新事务

```text
读取签名版本策略
→ 验证 HTTPS、策略签名、有效期和 policyEpoch
→ 下载到 staging
→ 校验大小、SHA-256、manifest、发布签名
→ 完整解压和文件树校验
→ 安装为 releases/<release-id>
→ 原子切换 current
→ 重启 Bootstrap
→ 再次在线确认 requiredReleaseSequence
→ 启动指定 release
```

任何更新失败都不得：

- 覆盖 `data/`。
- 覆盖 License 和设备绑定材料。
- 覆盖长期 `deviceToken`。
- 清空会话、记忆、工作区或附件索引。
- 把秘密写入日志。
- 启动旧版正式业务。

客户端不需要业务 `rollback` 指针。更新事务可以在切换完成前保留旧文件保证写入安全，但旧文件不能用于正式启动。

## 10. License 校验与版本检查顺序

最终顺序已确认：

```text
1. Bootstrap 启动并显示状态
2. 恢复安装事务，检查 U 盘、目录和本地文件安全边界
3. 检测激活材料
4. 已激活：本地验证 License 签名、设备绑定和 U 盘绑定
5. 在线获取并验证 requiredReleaseSequence
6. 本地不是指定版本：强制安装、重启 Bootstrap，并从第 1 步重新执行
7. 本地是指定版本：在线验证 License 有效期、撤销和状态
8. License 通过：启动正式 Shell
9. Shell 显示后，由 Electron Main 后台启动 Gateway
```

理由：

- 本地安全校验先阻断恶意或损坏材料。
- 旧客户端先更新，避免因旧协议无法完成新的在线 License 校验。
- 在线 License 校验仍在正式业务启动前 fail-closed。

未激活设备建议：

```text
仍先强制更新到最新版
→ 再启动最新版 activation-only UI
→ 激活成功后返回 Bootstrap
→ 从第 1 步重新执行完整门禁
```

Gateway 不参与版本或 License 门禁。余额检查属于商业模型请求授权，不替代启动阶段 License 校验。

## 11. 与其他重构的交叉影响

### 11.1 启动、打包、Gateway 重构

高影响：

- 原 `current/rollback` 方案需删除客户端业务 rollback。
- `runtime.pkg` 继续只作为运输格式。
- Bootstrap 必须在业务 runtime 外。
- 正式 shell 和 Gateway 只能在强制版本门禁后启动。
- 最新版启动失败后不能回到上一版业务。

### 11.2 OpenClaw 唯一聊天链重构

直接影响较低，但必须保证：

- 未通过版本门禁时不启动 Gateway。
- Provider 配置和长期设备凭据位于 release 外。
- 更新不能覆盖商业凭据。
- Provider 配置 migration 失败时正式 UI 不得带病启动。
- 模型服务失败不能被误判为安装包损坏。

两边方案完成后，需要重新统一评审本需求与最终启动、激活、校验、聊天和 Gateway 合同。

## 12. 验收门禁

### 12.1 强制版本行为

- 每次启动均产生真实在线版本查询。
- 本地不是 `requiredReleaseSequence` 时，正式 UI 不启动。
- 用户不存在跳过、延后、忽略或降级入口。
- 更新完成并重新确认最新版后，才继续 License 和业务启动。
- 服务端/CDN不可用时，正式程序不可用。

### 12.2 失败和事务

- 下载中断不破坏已安装 release。
- 签名、哈希或 manifest 错误时不切换 current。
- 磁盘空间不足时不切换 current。
- 安装进程崩溃后可以从 staging 清理或恢复更新事务。
- 最新版启动失败后不启动旧版正式业务。
- Bootstrap 能继续获取服务端后续更高 sequence。

### 12.3 服务端回滚

- 服务端保留上一稳定内容。
- 回滚通过更高 sequence 重新发布，不降低 sequence。
- 回滚制品在切换全局指针前已经完成 CDN 可用性验证。
- 所有设备下次启动均强制安装回滚 release。
- 故障 release 不成为新的 `previousStable`。

### 12.4 数据和秘密

- 更新不覆盖 `data/`。
- 更新不覆盖 License、设备绑定材料和长期设备 Token。
- 日志不包含激活码、startup secret、deviceToken、Provider Key 或 Authorization。
- release 切换不改变 U 盘业务数据身份。

## 13. 明确不做

- 页面内更新系统。
- 客户端业务本地回滚。
- 离线跳过版本检查。
- 多版本并行选择。
- 灰度 cohort。
- 用户可选更新渠道。
- 服务端多级历史回滚。
- 旧版临时使用。

## 14. 后续待确认

1. Bootstrap 自更新和 Windows 运行中 EXE 替换方式。
2. 启动更新状态反馈采用原生窗口、轻量 WebView 还是其他方式。
3. 最新版启动失败的服务端告警、人工回滚权限和审计流程。
4. `policyEpoch`、`releaseSequence`、withdrawn 状态和签名 key rotation 的正式协议。
5. release 配置 migration 失败时的阻断和恢复合同。

## 15. 最终需求摘要

```text
唯一全局正式版本
+ 每次启动在线硬门禁
+ 不允许用户跳过
+ 正式 UI 删除全部更新能力
+ 客户端没有旧版业务回滚
+ 服务端只保留上一稳定内容
+ 回滚时将上一稳定内容作为更高 sequence 重新发布
+ 独立 Bootstrap 负责在业务 runtime 损坏时继续获取修复版
+ 本地 License 校验 → 强制版本门禁 → 在线 License 校验 → Shell → Gateway
```
