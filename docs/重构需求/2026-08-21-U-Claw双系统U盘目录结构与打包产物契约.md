## 1. 背景

现有正式产品链路主要按 Windows x64 物理 U 盘设计：

```text
U-Claw.exe
.uclaw/
  runtime.pkg
  version.json
  data/
```

该结构能支持 Windows 首版验证，但没有定义 macOS 入口、跨系统 runtime 包、共享业务数据和跨系统授权材料的边界。

ZUXO U 盘产物显示了另一种更接近目标用户认知的结构：同一 U 盘根目录同时放 Windows 入口和 macOS 入口，业务数据在共享 `data/` 下，平台 runtime 分开携带。U-Claw 后续双系统发行应采用这个方向，但保留自己的商业授权、强制版本门禁和 runtime 安装策略。

## 2. 目标

双系统 U 盘必须做到：

1. 同一支 U 盘插入 Windows 可双击 `U-Claw.exe`。
2. 同一支 U 盘插入 macOS 可打开 `U-Claw.app`。
3. Windows 和 macOS 共用同一份业务数据、会话、附件、产出和授权身份。
4. Windows 和 macOS 使用各自平台的 launcher、runtime 包、签名和校验材料。
5. 宿主机只保存可重建 runtime/cache，不保存业务数据、明文秘密、完整会话和用户产出。
6. 激活、强制版本、License gate 和 Gateway 边界继续遵守既有商业安全契约。

## 3. 根目录目标结构

首版双系统正式制盘目录：

```text
U-Claw/
├─ U-Claw.exe
├─ U-Claw.app/
├─ app/
│  ├─ usb-manifest.json
│  ├─ current/
│  │  ├─ win-x64.json
│  │  └─ macos-arm64.json
│  ├─ install-state/
│  │  ├─ win-x64.json
│  │  └─ macos-arm64.json
│  ├─ manifests/
│  │  ├─ win-x64.version.json
│  │  └─ macos-arm64.version.json
│  └─ packages/
│     ├─ win-x64/
│     │  └─ runtime.pkg
│     └─ macos-arm64/
│        └─ runtime.pkg
├─ support/
│  ├─ U-Claw Updater.exe
│  └─ U-Claw Updater.app/
├─ data/
│  ├─ .openclaw/
│  │  ├─ workspaces/
│  │  ├─ agents/
│  │  └─ media/
│  ├─ outputs/
│  └─ logs/
└─ .uclaw/
   ├─ license/
   │  ├─ .startup-credential.json
   │  ├─ license.json
   │  └─ .lifecycle-cache.json
   ├─ device/
   └─ state/
```

说明：

- `U-Claw.exe` 和 `U-Claw.app` 是两个不同平台入口，不是一个文件被系统识别成两种应用。
- `app/packages/<target>/runtime.pkg` 是平台专属运输包。首版不把 Windows 和 macOS runtime 混在同一个 `runtime.pkg`。
- `app/manifests/<target>.version.json` 是平台专属签名 manifest。`target` 首版取 `win-x64` 和 `macos-arm64`。
- `app/current/<target>.json` 是当前平台已完成安装的版本指针；`app/install-state/<target>.json` 只记录下载、验签、安装和切换中的事务状态。它不是可启动旧业务的 rollback 指针。
- `app/usb-manifest.json` 是整支 U 盘的总 manifest，列出支持平台、入口文件、包路径、manifest 路径、数据根和最低 Bootstrap 版本。
- `data/` 是用户业务数据权威位置。用户会话、工作区、附件、媒体和产出必须跟 U 盘走。
- `.uclaw/license/` 保存授权材料。它可以被隐藏，但不能假设隐藏等于安全。
- `support/` 放离线修复、更新器和诊断工具。没有实现前可以为空，但路径契约先固定。

## 4. 平台 target

首版双系统 target：

| target | 入口 | runtimeId 示例 | 宿主 runtime 位置 |
| --- | --- | --- | --- |
| `win-x64` | `U-Claw.exe` | `openclaw-2026.7.1-2-win-x64` | `%LOCALAPPDATA%/U-Claw/runtimes/win-x64/<sequence>-<tree-digest>/` |
| `macos-arm64` | `U-Claw.app` | `openclaw-2026.7.1-2-macos-arm64` | `~/Library/Application Support/U-Claw/runtimes/macos-arm64/<sequence>-<tree-digest>/` |

后续如要支持 Intel Mac 或 Windows arm64，新增 target：

```text
macos-x64
win-arm64
```

新增 target 只能新增目录和 manifest，不能改变已有 target 的路径语义。

## 5. 数据目录契约

所有业务数据统一从环境变量或启动参数注入：

```text
UCLAW_USB_ROOT=<usb-root>
UCLAW_DATA_DIR=<usb-root>/data
UCLAW_OPENCLAW_HOME=<usb-root>/data/.openclaw
```

规则：

- Electron、Gateway、Adapter 和 OpenClaw 不得自行推导系统默认 home 作为业务数据根。
- 会话、agent session、workspace、media、artifact、用户导出文件必须优先写入 `data/.openclaw/` 或 `data/outputs/`。
- JSON、索引和会话记录不得写入 `F:\...`、`/Volumes/...`、`C:\Users\...` 这类绝对业务路径作为权威路径。需要记录来源时只允许保存脱敏 display path 或相对路径。
- macOS 和 Windows 文件名必须通过同一套非法字符、保留名、大小写碰撞和 Unicode 规范化检查。
- 宿主机 cache 可保存编译缓存、浏览器缓存和已安装 runtime；不得保存明文 prompt、完整回复、附件原件、用户产出和长期令牌。

## 6. 授权与 USB 身份

现有 Windows 方案使用 `DeviceIoControl` 获取 USB 指纹。双系统后必须补齐 macOS USB 身份采集，并重新评审跨系统稳定性。

关键约束：

- 同一支物理 U 盘在 Windows 激活后，macOS 应能识别为同一授权设备；反向也一样。
- 若 Windows 和 macOS 采集到的原始 descriptor 不一致，必须在服务端引入版本化映射或升级 `fingerprint_version`，不能让用户在另一系统上被误判为不同 U 盘。
- License 仍绑定物理 U 盘身份，不绑定某一个 OS 入口。
- `.uclaw/license/license.json`、`.startup-credential.json` 和 `.lifecycle-cache.json` 必须被两个平台共用。
- 激活成功后仍必须重新跑完整 gate，但用户可见窗口不能消失，详见《第一版启动激活授权方案》的 2026-08-21 激活体验复盘。

## 7. runtime 包与安装策略

双系统不改变 V3 已确认的 R2 方向：

```text
U 盘保存平台 runtime.pkg、业务数据和授权身份
→ 首次在当前电脑完整验签并安装到宿主机内容寻址 runtime 目录
→ 后续 warm startup 从宿主机 SSD 直接运行
```

平台差异：

- Windows 只读取 `app/packages/win-x64/runtime.pkg` 和 `app/manifests/win-x64.version.json`。
- macOS arm64 只读取 `app/packages/macos-arm64/runtime.pkg` 和 `app/manifests/macos-arm64.version.json`。
- 一个平台更新失败不得覆盖另一平台 runtime 包、manifest、current 指针、install-state 和已安装 runtime。
- 业务数据和授权材料不参与 runtime 更新覆盖。
- 客户端不得保留可启动旧业务的本地 rollback 指针。服务端向前回滚必须以更高 `releaseSequence` 重新发布。

## 8. 签名与发布

构建流水线必须拆成平台产物，再合成 U 盘总目录：

```text
固定 commit
→ build/typecheck/test/secret scan
→ 构建 win-x64 Electron runtime
→ 构建 macos-arm64 Electron runtime
→ 分别生成 inventory、SBOM、tree digest
→ 分别生成 runtime.pkg
→ 分别签名 version.json
→ 构建并签名 U-Claw.exe
→ 构建、签名并 notarize U-Claw.app
→ 生成 usb-manifest.json
→ 生成最终 U 盘目录
→ Windows 物理 U 盘 smoke
→ macOS 物理 U 盘 smoke
→ 同盘跨系统数据连续性 smoke
```

签名规则：

- Windows Launcher 使用 Authenticode。
- macOS `.app` 必须 Developer ID 签名并完成 notarization；外置 U 盘启动需单独验收 Gatekeeper、quarantine 和首次打开体验。
- `runtime.pkg` 使用 manifest 中的 SHA-256、大小、tree digest 和 Ed25519 签名校验。
- `usb-manifest.json` 必须签名或被平台 manifest 覆盖校验，不能成为未受信任的路径入口。

## 9. 当前实现差距

当前代码和文档距离本契约的差距：

- `product/runtime-versions.json` 只定义 `win32/x64` 和 `openclaw-2026.7.1-2-win-x64`。
- `product/shared/src/release.ts` 的 release schema 只接受 `platform: "win32"`、`arch: "x64"`。
- `product/packaging/build-release.mjs` 只生成 `U-Claw.exe`、`.uclaw/runtime.pkg`、`.uclaw/version.json`、`.uclaw/data`。
- `product/packaging/runtime-manifest.schema.json` 只允许 `targetPlatform: "win32"`、`targetArch: "x64"`。
- Launcher USB 指纹生产实现集中在 Windows；macOS 需要真实实现和物理 U 盘验收。
- 现有 `.uclaw/data` 与本契约的可见 `data/` 不一致，迁移时必须提供兼容读取或一次性迁移策略。

## 10. 验收门

双系统目录契约完成前，不得宣称双系统发行完成。

最低验收：

- Windows 双击 `U-Claw.exe` 可完成未激活、激活、重启 gate、进入工作台。
- macOS 打开 `U-Claw.app` 可完成同等流程。
- 同一支 U 盘先 Windows 激活，再 macOS 启动，授权识别为同一设备。
- 同一支 U 盘先 macOS 激活，再 Windows 启动，授权识别为同一设备。
- Windows 创建的会话、附件和产出，macOS 能在 `data/` 下读回；反向也成立。
- 拔盘、换盘符、换 USB 口、换电脑后，业务数据仍以 U 盘为权威。
- 宿主机 runtime 删除后，插回 U 盘可重新安装恢复；删除宿主机 runtime 不丢业务数据。
- 更新任一平台 runtime 不覆盖 `data/` 和 `.uclaw/license/`。
- 全包 secret scan 通过：客户端、U 盘、日志、诊断、manifest、runtime 包均不含 Provider Key、New API Key、完整激活码和长期明文令牌。
