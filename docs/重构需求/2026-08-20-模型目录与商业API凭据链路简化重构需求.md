# U-Claw 模型目录与商业 API 凭据链路简化重构需求

- 日期：2026-08-20
- 文档类型：重构需求与架构决策；不是实施计划
- 状态：产品决策已确认；待转实施计划
- 关联方向：OpenClaw 唯一聊天链、启动打包 Gateway 链路方案 D

## 1. 背景

当前 U-Claw 同时存在多套模型概念和凭据路径：

- 客户端编译期内置 Provider 模板。
- U 盘上的 Provider 配置和用户自带 API Key。
- 激活后下发的商业模型 endpoint、单个 model 和 deviceToken。
- OpenClaw `models.providers` 与默认模型配置。
- 前端聊天页硬编码的产品模型过滤。
- 服务端按设备保存的 New API 映射、加密 API Key、模型权限和限流信息。

这些机制分别解决过真实问题，但组合后产生重复状态：

```text
编译期模板
→ Provider Store
→ OpenClaw 配置投影
→ models.list
→ 前端产品模型过滤
```

商业模型又存在另一条链：

```text
激活响应
→ builtin-model-credential.v1.json
→ modelSourceRouter
→ 商业模型中转
```

结果：

- 增加一个模型可能需要改共享 schema、桌面端、前端白名单、激活响应和打包版本。
- 商业模型与用户自带 Provider 的语义混在一起。
- 一个 Provider 只能配置一个 `model`，不适合多模型目录。
- 商业模型凭据设计按“一盘一个上游账号/API Key”展开，复杂度高。
- 模型选择、会话上下文、流式和工具能力可能因模型来源走不同链路。

## 2. 已确认事实

### 2.1 当前客户端已有 Provider 模板

`product/shared/src/providers.ts` 已内置 DeepSeek、通义千问、豆包、MiniMax、Kimi、OpenAI 等模板。

这些模板解决 Provider 设置页初始化，不代表模型已经在产品聊天页开放。

### 2.2 当前聊天页存在产品模型硬过滤

`product/frontend/src/features/chat/product-model-catalog.ts` 当前只允许 `gpt-5.6-sol`。

这属于客户端硬编码白名单。新增模型必须改代码和重新打包，不符合后续扩展目标。

### 2.3 当前商业激活凭据只支持单个模型

`BuiltinCredentialArtifactSchema` 当前包含：

```text
endpoint
model
deviceToken
deviceId
licenseId
```

其中 `model` 为单个字符串。该结构不能表达动态模型目录。

### 2.4 当前服务端已有多模型授权基础

服务端已经保存和执行：

```text
allowed_models
default_model
device token digest
requests_per_minute
concurrent_requests
```

`GET /model-api/v1/models` 已按 `allowed_models` 过滤上游模型列表。

因此，服务端授权名单可保留；需要删除的是客户端硬编码产品白名单。

### 2.5 当前商业上游 API Key 位于服务器

当前模型代理从数据库读取加密后的 `api_key_envelope`，请求时临时解密，由服务器设置上游 `Authorization` Header。客户端只持有 `deviceToken`，不会得到上游 API Key。

该安全边界正确。需要评估的是：是否仍有必要为每个 U 盘保存一份独立上游 API Key。

### 2.6 ZUXO 可借鉴边界

ZUXO 本地保存模型目录、中转地址、设备凭据和中转访问凭据；未发现上游厂商真实 API Key。上游 API Key 由中转服务持有。

可借鉴：

- 客户端只调用统一中转 Provider。
- 模型目录与上游密钥分离。
- 一个中转 Provider 可以承载多个模型。

不可照搬：

- 本地静态模型目录不能成为唯一权威源。
- 本地设备凭据、relay 凭据和 Gateway token 仍属于敏感数据，不能当作“客户端没有秘密”。

## 3. 核心架构决策

### 3.1 删除客户端产品模型白名单

U-Claw 前端不得维护允许展示的固定模型 ID。

前端模型列表唯一来源：

```text
服务器授权后的 /models
→ OpenClaw models.list
→ U-Claw UI
```

前端可以按能力、可用状态和产品展示规则排序或分组，但不能用硬编码模型 ID 决定模型是否出现。

### 3.2 全体付费客户开放同一模型集合

产品不设置基础、专业等模型套餐，也不按设备区分可用模型。客户采用“充值多少、使用多少”的余额消费方式。

正式规则：

```text
New API 当前公开且由 U-Claw 全局启用的模型
→ 对所有 License 有效、设备有效、余额充足的商业客户开放
```

这里的设备、License 和 `deviceToken` 只承担身份、撤销、余额归属、限速、并发和审计，不承担模型分级。

服务端仍需保留全局模型开关，用于模型下架、上游故障、风险控制和协议不兼容。该开关对全体客户统一生效，不形成套餐白名单或每设备模型名单。

现有 `allowed_models` 迁移期可以统一填充同一全局模型集合；最终应改为全局模型目录/启用状态，避免长期为每个设备复制相同名单。

### 3.3 商业模型统一经过 OpenClaw

目标链路：

```text
U-Claw UI
→ OpenClaw session / chat / tool / history
→ U-Claw 商业中转 Provider
→ U-Claw 模型中转站
→ New API 或其他上游
```

商业中转只承担 Provider 数据面，不再绕过 OpenClaw 自建聊天链。

### 3.4 上游 API Key 只存在服务器

商业模型上游 API Key：

- 不进入客户端安装包。
- 不进入 U 盘普通配置。
- 不进入 Renderer。
- 不进入日志、诊断包和 API 响应。
- 不通过激活接口下发。

客户端只保存可撤销的 `deviceToken`。

已确认商业上游为自建 New API。当前可按以下配置理解：

```text
NEW_API_BASE_URL=https://api.gmnlee.com
NEW_API_KEY=<服务器固定 Key>
```

域名和服务器以后可以替换，但只能修改服务端配置；不得要求客户端换 Key、改 Provider 或重新打包。固定 New API Key 只允许存在服务端 Secret 中，不按客户、设备或 U 盘复制。

### 3.5 商业模型与 BYOK 分离

两种凭据不能混为同一安全模型：

#### 商业模型

```text
上游 API Key：服务器持有
客户端：deviceToken
模型目录：服务器动态返回
```

#### 用户自带 Key（BYOK）

`BYOK` 是 `Bring Your Own Key`，即“用户自带 API Key”。用户使用自己在 DeepSeek、通义千问、豆包、OpenAI 等模型供应商申请并付费的 Key，不使用 U-Claw 商业中转站持有的上游 Key 和额度。

```text
API Key：用户本地安全存储
Provider：用户自行配置
模型目录：对应 Provider /models 或用户配置
费用和额度：由用户自己的模型供应商账号承担
聊天运行链：仍必须经过 OpenClaw
```

BYOK 可以绕过 U-Claw 商业模型中转，但不能绕过 OpenClaw 聊天链。正确链路：

```text
U-Claw UI
→ OpenClaw session / chat / tool / history
→ 用户配置的 BYOK Provider
→ 模型供应商
```

BYOK 不得读取或复用商业中转的上游 API Key；商业模型也不得读取用户 BYOK Key。两类凭据、模型目录、用量和错误提示必须隔离。

## 4. 推荐的最小目标架构

### 4.1 客户端商业凭据

建议将商业凭据收口为：

```json
{
  "schemaVersion": 2,
  "endpoint": "https://api.example.com/model-api/v1",
  "deviceToken": "uclaw_dt_xxx"
}
```

不再保存：

- 单个 `model`。
- 上游 Provider API Key。
- 固定模型名单。
- 模型价格。
- 上游 Base URL。

`deviceId`、`licenseId` 若其他激活制品已有权威记录，不应在商业模型凭据中重复保存。若保留，只用于一致性校验，不能成为模型授权权威源。

### 4.2 服务器上游凭据

商业模型已确认共用一套自建 New API 基础地址和固定 API Key：

```text
NEW_API_BASE_URL=https://api.gmnlee.com
NEW_API_KEY=<服务器固定 Key>
```

真实值存储在部署环境 Secret：

- Kubernetes/Docker Secret。
- 云 Secret Manager。
- 权限受控的独立 secret 文件。

代码仓库只允许变量名和空模板。

未来更换域名或服务器，只替换部署配置和 Secret。客户端继续调用稳定的 U-Claw 商业中转接口，不感知 New API 地址或固定 Key。

### 4.3 服务端模型目录

建议模型记录至少包含：

```json
{
  "id": "deepseek-chat",
  "displayName": "DeepSeek",
  "provider": "newapi",
  "upstreamModel": "deepseek-chat",
  "enabled": true,
  "capabilities": ["text", "tools"]
}
```

模型目录是数据，不是代码分支。

普通 OpenAI-compatible 模型上线流程：

```text
服务器增加模型记录
→ 服务端验证模型
→ 客户端自动出现
```

无需修改客户端或重新打包。

### 4.4 服务端接口

#### 模型列表

```http
GET /model-api/v1/models
Authorization: Bearer <deviceToken>
```

设备和 License 有效时，返回 New API 当前公开且由 U-Claw 全局启用的模型。余额不足应返回明确的余额错误，不应伪装成模型不存在。

#### 对话

```http
POST /model-api/v1/chat/completions
Authorization: Bearer <deviceToken>
```

支持流式、工具调用和 OpenAI-compatible 消息格式，供 OpenClaw Provider 使用。

模型列表和对话必须执行相同授权规则，禁止“列表可见但请求被另一套规则拒绝”。

## 5. API Key 验证规则

### 5.1 上游 API Key 配置时验证

上游 Key 只由服务器验证：

```text
校验 Base URL 和允许域名
→ 建立 TLS 连接
→ 使用 Key 调用 /models
→ 发送最小真实对话请求
→ 记录验证结果
→ 成功后启用
```

不能让客户端参与上游 API Key 验证。

仅调用 `/models` 不足以证明聊天可用，因此至少需要一次最小真实推理测试。

### 5.2 运行时错误分类

- `401/403`：上游凭据无效或权限不足；服务端报警。
- `429`：上游限流或余额不足；返回可重试错误。
- `5xx`：上游故障；按策略重试、熔断或切换备用上游。
- 超时：中止上游请求，返回统一超时错误。
- 模型不存在：服务端禁用对应模型或阻止发布。

所有返回客户端的错误必须脱敏。

## 6. deviceToken 生成与验证

### 6.1 生成

激活成功后：

```text
服务器生成高熵随机 deviceToken
→ 服务器只保存摘要
→ 明文仅返回客户端一次
→ 客户端写入安全文件
```

推荐继续使用 opaque token，不必改成 JWT。Opaque token 更容易撤销，服务端本来就需要检查 License 和设备状态。

### 6.2 请求验证

每次模型请求：

```text
解析 Bearer token
→ 计算摘要
→ 查询设备授权
→ token 必须 active
→ 设备必须 active
→ License 必须有效且未撤销
→ 模型必须处于全局启用状态
→ 余额必须充足
→ 检查 RPM 和并发限制
→ 放行
```

### 6.3 客户端安全边界

`deviceToken` 无法在用户可控制的电脑上做到绝对不可提取。安全目标不是“永远隐藏”，而是：

- 可撤销。
- 可轮换。
- 绑定设备和 License。
- 有限权限。
- 有限速率和并发。
- 服务端审计。
- 泄露后不能访问上游 API Key。

## 7. 应保留与应删除

### 7.1 保留

- `deviceToken` 摘要验证。
- 设备、License、撤销状态。
- 服务端全局模型目录和启用状态。
- 请求限速和并发限制。
- 上游地址允许名单和 SSRF 防护。
- 上游响应大小、格式和超时限制。
- 脱敏审计。
- 商业模型全部经过 OpenClaw。
- BYOK 本地安全凭据存储。

### 7.2 删除或替换

- 前端 `gpt-5.6-sol` 硬过滤。
- 激活商业凭据中的单个 `model`。
- 商业模型普通聊天的 `modelSourceRouter` 直连路径。
- 商业模型与 BYOK 共用的执行路由。
- 为每个新增兼容模型修改客户端代码。
- 商业上游 Key 写入 OpenClaw 客户端配置。
- 同一模型目录在共享代码、客户端配置和前端各维护一份。

### 7.3 已确认删除

商业上已确认共用自建 New API 基础地址和固定 API Key，因此删除：

- 每设备 `api_key_envelope`。
- 每设备 `api_key_version`。
- 每设备独立上游 `base_url`。
- 每设备 New API 用户名与余额配置状态。
- 激活库存与上游 API Key 的一对一绑定。

客户余额、用量、撤销和限速在 U-Claw 服务端按 License/设备身份记录，不依赖每客户 New API 子账号或独立上游 Key。

## 8. 模型适配边界

以下模型只需增加服务器数据，不应增加客户端代码：

- 使用现有 OpenAI-compatible `/models`。
- 使用现有 `/chat/completions`。
- 流式 SSE 与现有协议兼容。
- Tool Calling 字段与现有协议兼容。

以下情况允许新增 Adapter：

- 非 OpenAI-compatible 协议。
- 特殊签名或自定义鉴权流程。
- 新能力类型：视频、语音、Embedding 等。
- Tool Calling、图片输入或流式协议不兼容。

Adapter 应位于服务器或 OpenClaw Provider 层，不能放在 U-Claw React 聊天组件中。

## 9. 迁移顺序建议

迁移必须保持旧版本可用，不能先删直连再补 Provider。

### 阶段 1：确认业务前提

- 已确认共用自建 New API 基础地址和固定服务器 API Key。
- 已确认所有全局启用模型向全部有效付费客户开放。
- 已确认按余额消费，不设置模型套餐或设备模型分级。
- 已确认保留 BYOK，且 BYOK 聊天仍经过 OpenClaw。

### 阶段 2：建立动态模型目录

- 服务端维护模型元数据。
- `/models` 对有效商业客户返回全局启用模型。
- 真机验证 DeepSeek、千问、豆包等至少三个模型。

### 阶段 3：接入 OpenClaw Provider

- OpenClaw 使用商业 endpoint 和 `deviceToken`。
- `models.list` 能返回所有授权模型。
- `sessions.patch` 能按会话选择模型。
- 真流式、上下文、Tool Calling 通过。

### 阶段 4：切换前端

- 删除产品模型硬过滤。
- 前端直接展示 OpenClaw `models.list`。
- 能力、分组和排序来自模型元数据，不由模型 ID 白名单决定。

### 阶段 5：删除旧链路

- 删除商业普通聊天直连。
- 删除激活凭据中的单模型约束。
- 删除不再需要的每设备上游 Key 映射。
- 保留 BYOK 独立链路和数据。

### 阶段 6：收紧门禁

- CI 禁止生产 Renderer/Electron 直接调用模型推理端点。
- 集成测试证明商业聊天一定经过 OpenClaw 和中转站。
- 日志扫描禁止 API Key、deviceToken 和 Authorization 泄露。

## 10. 验收标准

### 10.1 模型扩展

- 服务器增加一个 OpenAI-compatible 模型后，无需修改客户端代码。
- 无需重新打包，客户端可通过 `models.list` 看到新模型。
- 服务端禁用模型后，客户端刷新即消失。
- 所有有效商业客户返回同一全局启用模型集合。
- 余额不足时模型请求被明确拒绝，但模型目录不因余额变化形成另一套模型白名单。

### 10.2 凭据安全

- 客户端文件、安装包和日志中不存在上游 API Key。
- Renderer 无法读取 `deviceToken` 明文。
- 服务端日志不记录完整 Authorization Header。
- 上游 Key 只在服务器请求期间短暂进入内存。
- deviceToken 撤销后，模型请求立即失败。

### 10.3 OpenClaw 唯一聊天链

- 所有商业文本对话经过 OpenClaw `chat.send`。
- 模型切换使用 OpenClaw session 能力。
- 流式、上下文、工具、历史和图片消息不因模型不同而更换执行链。
- 客户端不存在商业模型 `/chat/completions` 直连。

### 10.4 兼容性

- DeepSeek、通义千问、豆包至少各完成一次真实流式对话。
- 至少一个模型完成 Tool Calling。
- 上游 `401`、`429`、`5xx` 和超时均能正确分类并脱敏。
- BYOK 与商业模型互不覆盖配置和凭据。

## 11. 明确不做

- 不在前端维护完整模型价格表作为授权依据。
- 不让客户端直接持有商业上游 API Key。
- 不为每个 OpenAI-compatible 模型建立专用聊天执行器。
- 不在本次重构中重新实现 OpenClaw 会话、上下文或工具协议。
- 不把 deviceToken 伪装成不可提取的硬件秘密。
- 不因旧表和旧服务已经存在，就默认“一盘一个上游 API Key”是产品硬需求。

## 12. 已确认产品决策

```text
自建 New API
+ 当前基础地址 https://api.gmnlee.com
+ 一套服务器固定 API Key
+ 域名和服务器可通过服务端配置替换
+ 所有全局启用模型向全部有效付费客户开放
+ 客户充值多少、使用多少
+ 设备和 License 只负责身份、余额、撤销、限流和审计
+ BYOK 正式保留
+ 商业模型和 BYOK 聊天全部经过 OpenClaw
```

本节产品问题已冻结。后续实现不得恢复模型套餐分级、每设备模型白名单或每设备上游 API Key。
