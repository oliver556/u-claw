# U-Claw 技术方案

> 文档状态：目标架构初稿  
> 记录日期：2026-08-07  
> 注意：本文档描述待落地方案，不代表当前仓库已实现。

## 1. 方案概要

采用“U 盘轻量启动器 + U 盘隐藏运行包 + 本机版本缓存 + U 盘持久数据”架构。

```text
U 盘
├── U-Claw.exe
└── .uclaw/
    ├── runtime.pkg
    ├── version.json
    ├── data/
    └── license/

Windows 本机
└── %LOCALAPPDATA%/U-Claw/runtime/<runtime-id>/
    ├── Electron
    ├── Node.js
    ├── OpenClaw
    └── node_modules
```

核心边界：

- 本机只放可重建 runtime。
- U 盘保存所有用户数据。
- `U-Claw.exe` 负责校验、解压、启动、监控和退出。
- Electron 负责桌面窗口与状态界面。
- Node.js/OpenClaw 负责 AI 网关和业务能力。

## 2. U 盘发行结构

### 2.1 `U-Claw.exe`

小型 Windows x64 启动器，不内嵌完整 900 MB 左右 runtime，避免每次启动都进行 NSIS 自解压。

职责：

1. 确定当前 EXE 所在 U 盘路径。
2. 读取 `.uclaw/version.json`。
3. 校验 `runtime.pkg` 存在性、版本和哈希。
4. 检查本机是否存在匹配 runtime 缓存。
5. 在后台准备 runtime，并显示前台进度。
6. 以 U 盘数据路径启动 Electron/OpenClaw。
7. 监控 U 盘连接、子进程和退出流程。

### 2.2 `.uclaw/runtime.pkg`

包含：

- Electron Windows x64 runtime。
- Node.js `v24.15.0` Windows x64 runtime。
- 锁定版本的 OpenClaw。
- 生产环境 `node_modules`。
- Windows x64 原生 `.node` 模块和 DLL。
- U-Claw 桌面壳、配置界面和必要资源。

不应包含：

- macOS/Linux 运行时。
- 测试、缓存、不必要源码、`.map` 和 `.d.ts`。
- 用户配置、API Key、聊天和记忆。

包格式需支持：

- 流式解压。
- 完整性校验。
- 解压到临时目录后原子切换。
- 解压中断后可重试，不将半成品识别为可用缓存。

### 2.3 `.uclaw/version.json`

建议字段：

```json
{
  "productVersion": "2.x.x",
  "runtimeVersion": "<runtime-version>",
  "runtimeSha256": "<sha256>",
  "runtimeSize": 0,
  "platform": "win32",
  "arch": "x64",
  "nodeVersion": "24.15.0",
  "openclawVersion": "<locked-version>"
}
```

`runtimeVersion + runtimeSha256` 共同生成本机 `runtime-id`，避免只依赖人工版本号造成缓存冲突。

### 2.4 `.uclaw/data/`

建议结构：

```text
.uclaw/data/
├── .openclaw/
├── memory/
├── conversations/
├── workspace/
├── skills/
├── backups/
└── logs/
```

实际目录名最终以 OpenClaw 真实路径契约为准。启动时必须通过环境变量、命令参数或明确配置将所有持久路径指向 U 盘。

### 2.5 `.uclaw/license/`

为后续离线许可证预留，但启动架构第一阶段不依赖该目录完成。

## 3. 启动流程

### 3.1 首次在某台电脑启动

```text
用户双击 U-Claw.exe
  -> 创建单实例锁
  -> 验证 U 盘结构与可写性
  -> 立即显示启动窗口
  -> 验证 version.json 与 runtime.pkg
  -> 解压至本机临时缓存
  -> 校验已解压 runtime
  -> 原子重命名为正式 runtime-id 目录
  -> 启动 Electron 客户端
  -> 启动 OpenClaw gateway
  -> 健康检查通过
  -> 进入主界面
```

启动界面不得等待 gateway 完全就绪才显示。

### 3.2 同一电脑二次启动

```text
用户双击 U-Claw.exe
  -> 创建单实例锁
  -> 验证 U 盘结构
  -> 检查本机 runtime-id 缓存
  -> 快速完整性检查
  -> 直接启动 Electron/OpenClaw
  -> 进入主界面
```

不再解压 `runtime.pkg`，不再遍历 U 盘中两万多个运行文件。

## 4. 进程模型

```text
U-Claw.exe（启动器/监督进程）
└── Electron 主进程
    ├── Electron 渲染进程
    └── Node.js + OpenClaw gateway
```

要求：

- 只允许一个 U-Claw 实例写入同一个 U 盘数据目录。
- 子进程必须受父进程管理。
- 正常退出、崩溃或 U 盘丢失时，必须尽可能停止 gateway。
- 端口需要动态选择或严格抢占，不得将“端口已占用”误报为初始化失败。
- 健康检查必须确认 gateway 真正可用，不只检查子进程存在。

## 5. 本机缓存策略

建议路径：

```text
%LOCALAPPDATA%\U-Claw\runtime\<runtime-id>\
```

建议状态：

- `<runtime-id>.partial`：正在解压，不可启动。
- `<runtime-id>`：校验完成，可启动。
- `manifest.json`：记录版本、哈希、时间和完整性标记。

策略：

- 当前 runtime 缓存缺失或损坏时，从 U 盘自动重建。
- 不在启动关键路径上自动删除其他版本，避免额外阻塞。
- 缓存清理策略与上限等待真实版本体积数据后确定。
- 任何缓存文件不得成为用户数据唯一副本。

## 6. 数据路径约束

启动器需生成一组明确路径，传递给 Electron 和 OpenClaw：

```text
UCLAW_USB_ROOT=<U 盘根目录>
UCLAW_DATA_DIR=<U 盘>\.uclaw\data
UCLAW_RUNTIME_DIR=%LOCALAPPDATA%\U-Claw\runtime\<runtime-id>
```

变量名只是方案示例，落地前应根据现有代码契约确定。验收重点是最终路径行为，不是变量命名。

必须审计 OpenClaw 可能写入的所有路径，包括配置、session、memory、skills、workspace、日志、缓存和临时文件。不能只修改 Electron `userData` 路径就认定“数据全部在 U 盘”。

## 7. 启动状态机

建议状态：

```text
STARTING
-> VALIDATING_USB
-> CHECKING_RUNTIME
-> EXTRACTING_RUNTIME（首次才有）
-> STARTING_GATEWAY
-> WAITING_FOR_GATEWAY
-> READY
```

失败状态：

- `USB_NOT_FOUND`
- `USB_NOT_WRITABLE`
- `RUNTIME_PACKAGE_MISSING`
- `RUNTIME_PACKAGE_CORRUPT`
- `RUNTIME_EXTRACTION_FAILED`
- `GATEWAY_START_FAILED`
- `GATEWAY_TIMEOUT`
- `USB_DISCONNECTED`

每个失败状态需提供：

- 用户可理解的中文提示。
- 重试、打开日志或安全退出操作。
- 不含敏感数据的诊断代码。

## 8. 完整性与安全

- `runtime.pkg` 必须进行 SHA-256 校验。
- `version.json` 最终应纳入数字签名，防止只替换哈希文件。
- 解压时要防止路径穿越和绝对路径写入。
- 启动子进程时使用参数数组，避免未过滤字符串经 shell 执行。
- 日志需对 API Key、token、请求头和对话正文脱敏。
- 授权验证使用公钥验签，签名私钥不得进入 U 盘或客户端代码。

## 9. 授权扩展点

后续 B 方案：

```text
启动器
  -> 读取 U 盘稳定硬件标识
  -> 读取 .uclaw/license/license.json
  -> 使用内置公钥验证签名
  -> 比对授权中的 U 盘标识和产品版本
  -> 通过后启动
```

该方案不依赖隐藏属性。需单独验证不同 U 盘品牌、USB-SATA 桥接和 Windows 权限下硬件标识的稳定性。

## 10. 构建与发行

发行流水线应：

1. 锁定 Node.js、OpenClaw、Electron 及原生依赖版本。
2. 在 Windows x64 目标环境安装生产依赖。
3. 验证所有 `.node` 和 DLL 属于 Windows x64，不混入 macOS 产物。
4. 构建 Electron 壳和运行环境目录。
5. 裁剪不必要文件，但不删除未验证的运行依赖。
6. 生成 `runtime.pkg`、SHA-256 和 `version.json`。
7. 构建轻量 `U-Claw.exe`。
8. 运行清洁 Windows 10/11 虚拟机端到端测试。
9. 生成用于复制到 NTFS U 盘的发行目录。

## 11. 测试策略

### 11.1 单元测试

- `version.json` 解析与校验。
- runtime-id 计算。
- 缓存完整性判断。
- 数据路径生成，包括带空格、中文和盘符变化。
- 状态机转换。
- 日志脱敏。

### 11.2 集成测试

- 首次解压成功。
- 解压中断后恢复。
- 缓存损坏后重建。
- 二次启动不再解压。
- 端口占用时的处理。
- 同一 U 盘重复双击时的单实例保护。
- U 盘断开时的停止与提示。

### 11.3 端到端测试

- Windows 10 x64 普通用户。
- Windows 11 x64 普通用户。
- Windows Defender 开启。
- 不同盘符和多个可移动磁盘。
- 路径包含中文和空格。
- 无本机 Node.js、无管理员权限。
- 新电脑首启、同机二启、换机首启。
- 退出后进程、端口和数据落盘检查。

## 12. 当前仓库与目标架构差距

2026-08-07 检查当前工作区，确认：

- README 主路线仍是将 `portable/` 完整拷贝到 U 盘，通过 `.bat`/`.command` 启动。
- `u-claw-app/` 在 README 中被标记为已停止发布。
- `u-claw-app/package.json` 当前使用 `"asar": false`。
- `u-claw-app/package.json` 当前依赖 `"openclaw": "latest"`，而 lockfile 中的 OpenClaw 产物是 `2026.3.8`，存在可重现构建风险。
- 当前 Electron 数据路径逻辑不等于本文档要求的 Windows U 盘数据契约。
- 当前仓库尚无 `runtime.pkg + 本机版本缓存` 启动链路。

因此，本方案需作为新的实现基线，不能将当前单文件 portable EXE 或散文件目录版直接视为完成品。
