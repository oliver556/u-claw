# Bavi-box 第一版启动、激活与授权总方案

> 文档状态：第一版权威实施基准  
> 决策日期：2026-08-13  
> 适用范围：首发 Windows 10/11 x64 U 盘产品  
> 实施状态：待按本文完成代码改造、真实服务部署和真机验收  

## 1. 文档地位

本文统一定义 Bavi-box 第一版的启动、首次激活、U 盘绑定、许可证签发、许可证校验、授权服务器、AI 网关短期凭据、人工余额运营、售后换盘和验收规则。

第一版后续需求、设计、开发、联调和验收以本文为准。旧方案保留为历史技术底座和已完成代码证据；与本文冲突时，以本文为准。

旧方案入口：

- [P3-T03 启动授权与本地验签设计](./superpowers/specs/2026-08-10-P3-T03-license-startup-design.md)：USB 指纹、Ed25519 本地验签和启动前 gate。
- [P3-T04 许可证生命周期设计](./superpowers/specs/2026-08-10-P3-T04-license-lifecycle-design.md)：在线状态、撤销、重制和离线容错。
- [P3-T05 制盘身份与 New API 自动开户设计](./superpowers/specs/2026-08-10-P3-T05-provisioning-identity-design.md)：制盘 saga、设备映射、New API 用户和 Token 自动开户。
- [第三阶段需求](./第三阶段需求.md)：原始商业授权需求。

本文保留旧方案中成熟且仍适用的安全能力，但把第一版产品流程从“制盘时完成授权和开户”改为“用户首次在线输入用户名和激活码，绑定当前 U 盘后签发许可证”。

## 2. 第一版目标

第一版必须做到：

1. 每套产品交付一个预分配用户名和一个高熵激活码。
2. 激活码只能首次绑定一个 U 盘身份。
3. 同一 U 盘换电脑、换 USB 接口、换盘符后仍可使用。
4. 同一激活码在其他 U 盘上激活必须被服务器拒绝。
5. 未激活时只允许同一个 Electron 客户端进入受限启动/激活模式，不能进入正常工作台或启动 OpenClaw。
6. 激活成功后，服务器签发与当前 U 盘绑定的 Ed25519 许可证。
7. 后续启动先完成本地验签和必要的在线状态校验，再启动主程序。
8. 已激活用户在授权服务器短时不可用时，可在受控离线宽限内继续使用。
9. 启动许可证、激活码、AI 网关短期 Token 和企业上游 Key 相互独立。
10. 内嵌 API 站点余额第一版由运营人员人工设置，不建设自动充值、支付或计费系统。

安全目标仍为“防君子”，不宣称硬件级 DRM。第一版阻止普通文件复制、激活码重复使用和低成本换盘复制；不承诺抵抗完整磁盘镜像、客户端逆向、内存提取、USB 固件仿真或专业硬件克隆。

## 3. 第一版明确不做

- 不建设完整消费者账号系统。
- 不要求用户设置密码、手机号或邮箱。
- 不做找回密码、社交登录、用户中心和多设备自助管理。
- 不做在线支付、自动充值、套餐购买和余额退款系统。
- 不在激活服务器内实现模型转发；模型请求仍由 New API 数据面处理。
- 不允许普通用户自行解绑或换绑 U 盘。
- 不保证格式化、U 盘损坏或完整重装后无需售后即可恢复。

第一版的“用户名”是销售和售后标识，不是登录账号。用户名与激活码配对使用；没有密码登录态。

## 4. 凭据与身份边界

系统存在五类不同数据：

| 数据 | 用途 | 保存位置 | 能否复用 |
| --- | --- | --- | --- |
| 用户名 | 销售、激活和售后识别 | 用户交付卡、授权服务器、U 盘脱敏状态 | 不是秘密 |
| 激活码 | 首次绑定授权 | 用户交付卡；服务端只存哈希 | 仅首次绑定；同盘恢复例外 |
| 启动许可证 | 允许指定 U 盘启动 | U 盘 `license.json` | 只适用于签名绑定的 U 盘 |
| startup secret | 证明本地授权材料完整、派生离线缓存密钥 | U 盘隐藏凭据；服务端存盐化 proof/哈希 | 不与任何 Token 复用 |
| AI 网关短期 Token | 调用内嵌模型服务 | U 盘受控短期缓存；激活后台签发 | 不作为启动授权；不得长期有效 |

企业上游 Provider Key 只能保存在 AI 网关服务端，不进入激活服务器响应、EXE、U 盘、客户端、日志或诊断导出。激活后台只验证许可证和设备状态并签发短期、受限客户端 Token；不得把 Provider API Key 返回客户端。

## 5. 用户交付物

每套产品至少交付：

```text
用户名：UCLAW-XXXXXXXX
激活码：XXXXX-XXXXX-XXXXX-XXXXX-XXXXXX
```

约束：

- 用户名由系统或运营后台生成，大小写归一化后全局唯一。
- 激活码使用 26 位 Crockford Base32 密码学安全随机数，熵约 130 bit，不计分隔符。
- 激活码不可由用户名、订单号、手机号、日期或连续序号推导。
- 服务端只保存激活码的带域哈希，不保存可直接使用的明文。
- 实体交付时激活码应使用刮层、密封卡或其他防提前查看方式。
- 日志、客服工单和截图不得记录完整激活码。

## 6. 总体架构

```text
Bavi-box.exe / Go Launcher
  ├─ USB 指纹采集
  ├─ 未激活检测
  ├─ 本地许可证验签
  ├─ 在线状态查询与离线容错
  ├─ 未激活时启动同一 Electron 客户端的受限模式
  └─ 授权通过后启动 OpenClaw 和正常工作台

同一 Electron 客户端的受限启动模式
  ├─ 输入用户名
  ├─ 输入激活码
  ├─ 显示 USB 身份可用性
  ├─ 调用激活服务器
  └─ 禁止加载正常工作台、用户数据和普通 IPC

独立部署的 Go 激活授权服务器（Linux x64）
  ├─ 激活码库存与首次绑定
  ├─ 用户名、USB、许可证映射
  ├─ Ed25519 许可证签发
  ├─ 状态查询、撤销和换盘重制
  ├─ 审计、限流和管理员操作
  └─ New API 设备账户映射

Bavi-box AI 网关 / New API 数据面
  ├─ 持有企业上游 Provider Key
  ├─ 接受激活后台签发的短期设备 Token
  ├─ 模型权限、限速和禁用
  ├─ 用量统计
  └─ 第一版由运营人员人工设置余额
```

客户端只打包一套 Electron runtime 和一套客户端代码。激活页是原客户端在授权 gate 前的受限路由，不存在第二个 Electron 激活客户端，也不使用 WebView2。激活页面和业务代码只增加少量静态资源，不重复携带 Chromium/Electron runtime。

激活服务器使用 Go 实现，作为独立项目、独立进程和独立部署单元运行；首发只构建 `linux/amd64`。生产使用 PostgreSQL。第一版采用模块化单体，不要求微服务，但授权管理接口和公开激活接口必须逻辑隔离、权限隔离。详细设计见[《Go 激活授权服务器详细设计》](./superpowers/specs/2026-08-13-Go激活授权服务器设计.md)。

真实模型对话的 UI、开发联调和 OpenClaw 接线见[《真实模型对话与消息布局设计》](./superpowers/specs/2026-08-13-真实模型对话与消息布局设计.md)。根目录 `.env` 只用于开发联调，不进入正式发行包；正式客户端只使用激活后台签发的短期 Token。

## 7. U 盘身份

沿用旧 `P3-T03` 方案：Windows Launcher 直接使用 `DeviceIoControl`，不依赖 PowerShell。

采集顺序：

1. 确认启动程序所在存储总线为 USB。
2. 首选 `StorageDeviceUniqueIdProperty`。
3. 不可用时，使用规范化的 `vendor/product/revision/serial/capacity` fallback。
4. 两类身份均不可用时，返回 `USB_ID_UNAVAILABLE`，不得生成随机身份冒充硬件身份。

服务器接收并存储版本化指纹摘要：

```text
fingerprint_version = "uclaw-usb-v1"
fingerprint_sha256 = SHA-256(canonical USB identity)
```

服务器不需要保存完整原始 descriptor。客户端和日志不得展示完整指纹，只显示末尾短摘要用于售后核对。

首发前必须在真实 Win10/11 普通用户环境验证同一 U 盘：换电脑、换接口、换盘符、重启后指纹稳定。

## 8. 启动状态机

```text
START
  -> 解析 U 盘受控路径
  -> 执行本地 preflight 与授权材料分类
     ├─ 两份授权材料都不存在
     │    -> ACTIVATION_REQUIRED
     │    -> 验证发行 manifest，准备受信 Electron 客户端 runtime
     │    -> 启动同一客户端的 activation-only 模式
     │    -> 激活成功后退出客户端
     │    -> Launcher 从 START 重新执行完整 gate
     └─ 授权材料完整
          -> VALIDATING_LOCAL_LICENSE
          -> VALIDATING_LICENSE_STATUS
          -> ACQUIRE_INSTANCE_LOCK
          -> PREPARE_RUNTIME
          -> START_APPLICATION
```

关键规则：

- 未激活不是普通授权错误，必须进入同一 Electron 客户端的受限激活模式。
- 只有 `.startup-credential.json` 与 `license.json` 都不存在时才是首次未激活。只缺一份、格式损坏、签名错误或 USB 不匹配都属于授权故障。
- 受限模式允许 Launcher 为显示界面而验证、解压和启动受信 Electron 客户端 runtime；不得启动 OpenClaw、加载用户工作区、读取业务数据或开放普通 Electron IPC。
- 受限与正常模式必须在 Electron main process 和 IPC capability 层隔离，不能只靠前端路由隐藏正常页面。
- 本地授权失败、USB 不匹配、许可证撤销等状态不得退回激活窗口覆盖旧绑定。
- 只有 `ACTIVATION_REQUIRED` 可以进行首次激活。
- 激活成功后必须关闭受限窗口，重新从 Launcher 完整执行授权 gate；激活响应不能直接绕过 gate 启动主程序。

## 9. 首次激活流程

```text
用户启动 Bavi-box.exe
-> Launcher 发现无许可证
-> 读取当前 USB 指纹
-> 验证并准备原有 Electron 客户端 runtime
-> 用 activation-only 参数打开同一个 Electron 客户端
-> 用户输入用户名和激活码
-> 客户端规范化用户名并校验输入格式
-> POST /v1/activations
-> 服务器校验激活码、用户名和库存状态
-> 数据库事务内首次绑定 USB 指纹
-> 生成 device_id、license_id、startup secret
-> 签发 Ed25519 license.json
-> 关联已准备的 New API 设备账户和策略
-> 返回授权材料和短期 AI 网关 Token
-> 客户端原子写入 U 盘隐藏目录
-> 客户端读回并完成本地验签
-> 回报激活提交结果
-> Electron 客户端退出
-> Launcher 重新执行完整启动 gate
```

同一激活码的并发首次请求只能有一个获胜。数据库必须使用事务、行锁或唯一约束保证，不得仅依赖进程内锁。

## 10. 重复激活与换盘规则

### 10.1 同一 U 盘重复请求

当用户名、激活码和 USB 指纹全部与已绑定记录一致：

- 允许幂等返回当前有效许可证，或签发同绑定的新 revision。
- 可用于激活响应丢失、授权文件写盘失败和同盘恢复。
- 不新增许可证额度，不创建第二个 New API 用户，不增加余额。

### 10.2 不同 U 盘使用同一激活码

服务器返回 `ACTIVATION_CODE_ALREADY_BOUND`。响应不得泄露原 U 盘完整指纹、激活时间、用户名之外的客户数据或许可证细节。

### 10.3 同一用户名输入错误激活码

统一返回固定认证失败。为降低枚举风险，公开响应不区分“用户名不存在”和“激活码错误”。

### 10.4 U 盘损坏或售后换盘

普通用户不能自行换绑。运营人员验证订单和旧绑定后执行 `reissue`：

1. 将旧许可证置为 `reissued` 或 `revoked`。
2. 撤销旧设备的 AI 网关短期 Token 签发资格。
3. 绑定新 USB 指纹。
4. 签发新许可证；新盘通过激活后台获取短期 AI 网关 Token。
5. 旧 U 盘永久不能恢复为 active。

## 11. 本地授权文件

沿用固定目录：

```text
.uclaw/license/.startup-credential.json
.uclaw/license/license.json
.uclaw/builtin-model-credential.v1.json
.uclaw/license/.lifecycle-cache.json
```

`.startup-credential.json` 至少包含：

```json
{
  "schemaVersion": 1,
  "deviceId": "dev_...",
  "licenseId": "lic_...",
  "startupSecret": "<random-secret>"
}
```

`license.json` 的 Ed25519 签名载荷至少绑定：

```text
schemaVersion
keyId
usernameId
deviceId
licenseId
usbFingerprintVersion
usbFingerprintSha256
startupSecretSalt
startupSecretHash
notBefore
expiresAt
revision
```

用户名明文不需要进入签名文件；可使用服务端内部 `usernameId`。普通 UI 只显示脱敏用户名和许可证状态。

文件写入必须：受控根目录、拒绝 symlink/hardlink、大小有界、strict JSON、同目录临时文件、flush/fsync、原子 rename、写后读回验证。Windows 正式实现需验证 DACL 和 pinned-handle 路径安全。

## 12. 后续启动与离线规则

本地 gate 沿用现有能力：

1. strict 读取启动凭据和许可证。
2. 验证 Ed25519 签名和 trust root。
3. 验证 startup secret proof。
4. 验证 `deviceId/licenseId` 一致。
5. 重新读取并比对当前 USB 指纹。
6. 验证 `notBefore/expiresAt`。
7. 查询服务器许可证状态。

只有在线 `active` 或满足离线规则时允许启动。

第一版离线规则沿用旧 `P3-T04`：

- 首次激活必须联网。
- 从未成功在线确认 `active` 的设备不能离线启动。
- 只有网络不可用或超时可以评估离线缓存；明确的 `revoked/disabled/reissued/expired` 不得回退离线。
- 最大离线宽限为 `min(服务器 graceUntil, 最近确认时间 + 24h, license.expiresAt)`。
- 缓存篡改、revision 回退、状态回放、anchor 不一致和明显时钟回拨均 fail-closed。

## 13. 许可证状态

```text
prepared -> active -> revoked
                  -> disabled
                  -> expired
                  -> reissued
```

| 状态 | 启动 | 说明 |
| --- | --- | --- |
| `prepared` | 否 | 库存已准备，尚未首次绑定 |
| `active` | 是 | 正常许可证 |
| `revoked` | 否 | 退款、风控或人工撤销 |
| `disabled` | 否 | 临时运营禁用，可由管理员恢复 |
| `expired` | 否 | 达到许可证有效期 |
| `reissued` | 否 | 已换盘，旧许可证永久失效 |

状态每次变更递增 `revision`。终态不得被低 revision 的旧状态恢复为 active。

## 14. 激活授权服务器功能

### 14.1 公开客户端能力

- 首次激活。
- 同盘幂等恢复授权材料。
- 查询许可证状态。
- 上报激活材料写盘成功或失败。
- 服务健康检查仅返回服务是否可用，不返回库存和客户数据。

### 14.2 管理员能力

- 生成或批量导入用户名和激活码。
- 查询用户名、激活码状态、设备、许可证和 New API 映射。
- 禁用、恢复、撤销许可证。
- 售后换盘和重新签发。
- 记录 New API 用户、短期 Token 签发策略和余额配置状态。
- 查看脱敏审计事件。
- 导出不含秘密的运营清单。

第一版管理员能力可以是受保护的 CLI 或内部 API，不要求建设完整 Web 后台。但所有状态变更必须经过认证、授权和审计，不能直接手改生产数据库作为常规操作。

### 14.3 服务端代码模块

Go 服务端保持模块化单体：

```text
product/activation-server/
  api/openapi.yaml
  cmd/server/
  cmd/admin/
  internal/activation/
  internal/license/
  internal/inventory/
  internal/device/
  internal/newapi/
  internal/token/
  internal/admin/
  internal/audit/
  internal/persistence/
  internal/security/
  migrations/
```

`api/openapi.yaml` 是客户端与服务端 HTTP 契约的唯一来源；生成 TypeScript 客户端类型和 Go server types，禁止手工维护两份漂移契约。生产 DB 固定为 PostgreSQL。私钥、管理凭据和短期 Token 签名密钥通过 KMS 或受控 secret mount 注入，不写入源码、镜像层、仓库或普通环境导出。

## 15. 数据模型

### 15.1 `activation_inventory`

```text
id
username_normalized UNIQUE
username_display
activation_code_hash UNIQUE
status: prepared | binding | active | revoked
order_reference nullable
created_at
activated_at nullable
```

`binding` 是服务端生成签名和加密授权材料期间的短暂持久化状态。相同请求可恢复该状态；其他 U 盘不得趁机占用库存。只有授权材料已加密持久化后才能改为 `active`。

### 15.2 `devices`

```text
device_id UNIQUE
inventory_id UNIQUE
fingerprint_version
fingerprint_sha256 UNIQUE
status
created_at
updated_at
```

是否允许同一物理 U 盘绑定多套授权：第一版不允许。`fingerprint_version + fingerprint_sha256` 必须唯一。

### 15.3 `licenses`

```text
license_id UNIQUE
device_id
status
revision
key_id
startup_secret_salt
startup_secret_hash
not_before
expires_at
replacement_license_id nullable
created_at
updated_at
```

### 15.4 `new_api_bindings`

```text
device_id UNIQUE
new_api_user_id UNIQUE
new_api_username UNIQUE
balance_setup_status: pending | configured | suspended
status
created_at
updated_at
```

激活服务器不保存或下发 Provider API Key。短期 AI 网关 Token 按请求签发，只保存 `jti`、设备、许可证、策略摘要、签发时间、到期时间和撤销状态；不得长期保存可直接使用的明文 Token。

### 15.5 `audit_events`

```text
event_id
actor_type: client | operator | system
actor_id nullable
action
outcome
inventory_id nullable
device_id nullable
license_id nullable
request_id
created_at
```

审计不得记录完整激活码、startup secret、Token secret、Authorization、原始 USB descriptor、签名私钥或完整远端响应。

## 16. HTTP API

生产只允许 HTTPS。公开接口使用严格、有界 JSON，禁用重定向，设置连接和总超时。

### 16.1 首次激活

```http
POST /v1/activations
Content-Type: application/json

{
  "username": "UCLAW-XXXXXXXX",
  "activationCode": "XXXXX-XXXXX-XXXXX-XXXXX-XXXXXX",
  "usbFingerprint": {
    "version": "uclaw-usb-v1",
    "sha256": "..."
  },
  "clientVersion": "1.0.0",
  "idempotencyKey": "..."
}
```

成功响应：

```json
{
  "activationId": "act_...",
  "deviceId": "dev_...",
  "licenseId": "lic_...",
  "license": {},
  "startupCredential": {},
  "builtinCredential": {},
  "status": "active"
}
```

`builtinCredential` 是设备模型凭据，不得包含 New API 管理凭据或企业上游 Key。

### 16.2 状态查询

```http
GET /v1/licenses/{licenseId}/status
Authorization: Bearer <startup-secret-derived-proof-or-frozen-contract>
```

返回脱敏状态摘要和签名回执。继续复用旧 `P3-T04` 的 opaque receipt、revision 和离线缓存契约。

### 16.3 激活提交结果

```http
POST /v1/activations/{activationId}/commit
```

客户端只在三份关键授权材料原子写入并读回验证后提交。未收到 commit 不得自动解绑；服务器保持同盘幂等恢复能力，避免响应丢失造成死锁。

### 16.4 管理接口

```text
POST /internal/v1/inventory
POST /internal/v1/inventory/import
POST /internal/v1/licenses/{id}/disable
POST /internal/v1/licenses/{id}/enable
POST /internal/v1/licenses/{id}/revoke
POST /internal/v1/licenses/{id}/reissue
PATCH /internal/v1/new-api-bindings/{deviceId}/balance-status
GET  /internal/v1/audit
```

管理接口不得与公开激活接口共用客户端凭据。建议使用独立监听入口或网关策略、管理员身份认证、最小角色权限和来源限制。

## 17. New API 与人工余额流程

第一版接受人工设置内嵌 API 余额，但设备账户和短期访问权限必须独立。

推荐销售准备流程：

```text
生成用户名和激活码库存
-> 为该库存创建独立 New API 用户和设备策略
-> 保存公开 ID、额度状态和允许模型
-> 运营人员在 New API 后台人工设置余额、模型权限和限速
-> 将 balance_setup_status 标为 configured
-> 产品可交付
```

只有 `balance_setup_status=configured` 的库存才能首次激活。这样避免用户激活成功但内嵌模型立即因零余额不可用。

若赶工期间采用“先激活、后人工充值”，客户端必须明确显示“内嵌模型服务准备中”，不能把余额未配置误报成网络或授权失败。该模式只能由管理员显式开启，并产生审计记录。

余额、额度、模型权限和禁用由运营人员在 New API 管理面操作；激活服务器只记录同步状态和映射。第一版不自动充值，不存储支付信息。

禁止所有产品共用长期 New API Token。每套产品对应独立用户和设备策略；客户端只取得短期、可撤销 AI 网关 Token，保证用量追踪、单独禁用和泄露隔离。

## 18. 公开错误与用户提示

| 服务端/客户端码 | 用户提示 | 是否可重试 |
| --- | --- | --- |
| `ACTIVATION_REQUIRED` | 此 U 盘尚未激活 | 是 |
| `ACTIVATION_INVALID` | 用户名或激活码不正确 | 可重新输入 |
| `ACTIVATION_CODE_ALREADY_BOUND` | 此激活码已绑定其他 U 盘，请联系售后 | 否 |
| `USB_ID_UNAVAILABLE` | 无法读取此 U 盘的设备身份 | 换接口后可重试 |
| `LICENSE_LOCAL_INVALID` | 本地授权文件无效 | 否 |
| `LICENSE_USB_MISMATCH` | 授权与当前 U 盘不匹配 | 否 |
| `LICENSE_REVOKED` | 授权已被撤销 | 否 |
| `LICENSE_DISABLED` | 授权已暂停，请联系售后 | 否 |
| `LICENSE_REISSUED` | 授权已迁移到其他 U 盘 | 否 |
| `LICENSE_EXPIRED` | 授权已到期 | 否 |
| `ACTIVATION_SERVICE_UNAVAILABLE` | 激活服务暂时不可用 | 是 |
| `OFFLINE_GRACE_EXPIRED` | 需要联网验证授权 | 联网后重试 |
| `BUILTIN_BALANCE_PENDING` | 内嵌模型服务准备中 | 联系客服 |

公开错误不得包含数据库错误、路径、完整 ID、指纹、激活码、Token、签名、Authorization 或远端 raw body。

## 19. 安全要求

- 激活码比较和秘密比较使用抗时序泄露方式。
- 激活接口按 IP 摘要、用户名摘要和设备摘要限流；失败次数有界。
- 不在客户端内置授权私钥、管理员凭据或 New API 管理 Key。
- Ed25519 私钥支持 `keyId` 轮换；客户端可内置多个有效公钥。
- 生产缺少 trust root、授权 endpoint 或 receipt 公钥时 fail-closed。
- DB 备份、审计导出和错误追踪系统必须执行秘密扫描和脱敏。
- 管理员 `reissue/revoke/enable` 必须记录操作者、对象、结果和时间。
- 公开激活接口不允许指定 `deviceId/licenseId/status/revision`，这些字段由服务器生成。
- 激活响应只发给本次通过认证且绑定成功的请求，并禁止缓存中间代理保存。
- 激活码一旦绑定，不能通过重复调用变更 USB 指纹。

## 20. 运营与售后

### 20.1 发货前

1. 生成用户名和激活码。
2. 创建 New API 独立设备账户和模型策略。
3. 人工设置余额、模型权限和限速。
4. 标记库存 `configured`。
5. 打印密封交付卡。
6. 不预先绑定客户 U 盘指纹。

### 20.2 用户首次使用

用户只需要联网、输入用户名和激活码。无需注册、设置密码或登录网页。

### 20.3 U 盘损坏

客服验证订单、用户名和必要购买证明。管理员执行 reissue，新盘重新激活；旧授权和旧设备的短期 Token 签发资格失效。

### 20.4 退款或风控

撤销许可证，并禁用对应 New API 用户及短期 Token 签发资格。两项操作都要执行，不能只清余额或只撤销启动授权。

### 20.5 授权服务器故障

- 未激活用户无法首次激活。
- 已激活用户按 24 小时离线宽限运行。
- 服务恢复后客户端重新在线确认。
- 监控必须覆盖激活成功率、状态查询可用率、签名错误、DB 事务失败和 New API 映射异常。

## 21. 代码改造范围

后续实现至少包含：

### Launcher

- 新增 `ACTIVATION_REQUIRED` 分支。
- 保留 USB 指纹、本地验签、在线状态和离线 gate。
- 未激活时只启动同一 Electron 客户端的 `activation-only` 模式。
- 激活成功后重新执行完整 gate。

### 同一 Electron 客户端的受限激活模式

- 用户名和激活码输入。
- USB 身份检查。
- 激活中、成功、失败、服务不可用状态。
- 不提供注册、密码和普通主应用能力。
- 与正常工作台共用 Electron runtime 和应用包，不增加第二个客户端。
- Electron main process 根据 Launcher 传入的受控启动模式只注册激活所需 IPC。

### Shared contract

- 激活输入、成功响应、安全错误、commit 和管理操作 schema。
- 延续现有 license lifecycle contract；按需要增加 `prepared` 与激活来源字段。

### Desktop/写盘

- 原子落盘三类凭据。
- 激活响应写后读回。
- 失败恢复和同盘幂等重试。
- renderer 只接收脱敏状态。

### 授权服务器

- 新增独立 Go module `product/activation-server`，首发构建目标为 `linux/amd64`。
- 库存、激活、设备、许可证、New API 映射、管理和审计模块。
- 生产数据库 migration、事务和唯一约束。
- 正式 Ed25519/KMS 密钥装配。
- HTTPS、认证、限流、备份和监控。

### 运营工具

- 批量生成/导入库存。
- 标记 New API 余额配置状态。
- 查询、撤销、禁用、恢复和换盘重制。
- 脱敏审计查询。

## 22. 验收矩阵

### 22.1 激活

- 正确用户名和激活码首次绑定成功。
- 错误用户名、错误激活码、超限输入和暴力尝试被拒绝。
- 同一激活码并发绑定两个 USB，只允许一个成功。
- 同盘响应丢失、写盘失败、重试可恢复。
- 不同盘重复使用返回已绑定，不泄露旧盘信息。

### 22.2 启动

- 未激活只进入受限激活窗口。
- 缺文件、篡改、错误签名、错误 secret、错误 USB、过期和终态均拒绝主程序。
- 授权失败前允许准备并启动受信 Electron 客户端的受限模式；不得启动 OpenClaw、加载用户工作区或开放正常工作台能力。
- 同盘换电脑、换接口和换盘符仍通过。

### 22.3 生命周期

- active、disabled、revoked、expired、reissued 行为正确。
- 首次离线拒绝；在线成功后允许有界离线。
- 24 小时边界、时钟回拨、revision 回退、cache/anchor 篡改均验证。

### 22.4 AI 网关与 New API

- 每套产品使用独立设备策略和短期 AI 网关 Token。
- 人工余额配置完成后可真实调用内嵌模型。
- 零余额、禁用、模型无权限和限流分类正确。
- 启用外部 Provider 后不消耗内嵌服务额度。
- Provider API Key 只存在于 AI 网关服务端。
- 撤销或换盘后旧 Token 不可使用，也不可继续刷新。

### 22.5 正式环境

- 真实 HTTPS、正式公钥、生产 DB、备份恢复和管理员权限通过。
- Win10/11 x64 普通用户、Defender 开启、无本机 Node.js。
- 多品牌物理 U 盘指纹兼容率达到发布标准。
- U 盘拔插、断网、服务恢复、写盘失败和并发故障完成验证。
- 客户端、U 盘、宿主机、日志、诊断、DB 和备份联合秘密扫描通过。

## 23. 第一版完成标准

以下全部满足，才能宣布第一版授权上线：

1. 用户名 + 激活码首次在线绑定流程完成。
2. 同码换 U 盘拒绝、同盘幂等恢复完成。
3. 单一 Electron 客户端的未激活受限模式和 Launcher gate 完成。
4. 正式授权服务器、数据库、HTTPS 和 Ed25519 私钥装配完成。
5. 管理员撤销、禁用、恢复和 reissue 可用且有审计。
6. 每套产品独立 New API 用户和设备策略；短期 AI 网关 Token 与人工余额运营流程可执行。
7. Win10/11 和物理 U 盘真实验收通过。
8. 旧 localhost fixture 只作为自动化证据，不作为生产服务通过证据。

在上述门禁通过前，状态统一为 `not-release-ready`。
