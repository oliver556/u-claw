# 激活服务故障处理

## 范围与安全边界

- 当前 VPS 的生产主路径是宿主 `caddy.service` 直接转发到 `uclaw-activation@18081.service` 和 `uclaw-activation@18082.service`，两实例只监听 `127.0.0.1`。故障处理默认使用 systemd 命令，详见 [激活与模型代理部署](./激活与模型代理部署.md)。
- 公网只进入 TLS Caddy `:443`，只允许 `/v1/*`、`/model-api/*`、`/health/ready`；`/internal/*`、`/metrics`、管理 API 和其他路径必须返回 404。旧客户端 IP endpoint 自域名切换起至少保留一个发行周期。
- `product/activation-server/deploy/compose.production.example.yaml` 是新环境的参考拓扑：Caddy 经 `edge_private` mTLS 到 `public-gateway:8443`，OpenResty 再到两个 activation 容器。只有事故目标明确是已审批 compose 环境时，才使用本文的 compose 专用步骤；不得在当前 VPS 混用容器命令。
- 管理 API 不得经 Caddy 公开。compose 参考拓扑的 management gateway 只绑定宿主 `127.0.0.1:8444`、使用独立 mTLS，并应再置于 VPN 或堡垒机后；不得映射 `0.0.0.0`。
- 至少运行两个无状态 activation 实例。状态、幂等、binding lease 全部以同一 PostgreSQL 为权威。
- model proxy handler 60s，OpenResty `proxy_read_timeout` 70s，Go server `WriteTimeout` 75s，按顺序为代理处理和收尾保留余量。activation 普通请求仍受较短的 read、connect 和各 handler 限制；不得把 model proxy 的长响应上限套用为全部请求的统一 timeout。
- 限流按 IP、规范化 username、device ID 分别计算 HMAC 摘要。原值不得写日志、指标或限流 key；不信任客户端提供的摘要头。
- 所有命令先选定环境和时间窗。管理操作须记录工单、操作者、请求 ID。禁止在故障处理中输出 activation code、startup secret、私钥、KEK、token 或完整设备标识。

## 指标与告警

`internal/observability.Metrics` 提供 Prometheus text handler。管理网关分别暴露稳定 target `/metrics/activation-1` 和 `/metrics/activation-2`，Prometheus 必须同时抓取，禁止经负载均衡 target 抓取导致 counter 回退。公网网关始终拒绝 `/metrics`。稳定 label 有界，内部错误统一为 `INTERNAL_ERROR`。

核心查询：

```promql
# 5 分钟激活成功率
sum(rate(uclaw_activation_requests_total{outcome="success"}[5m]))
/
clamp_min(sum(rate(uclaw_activation_requests_total[5m])), 0.001)

# P95 / P99
histogram_quantile(0.95, sum by (le) (rate(uclaw_activation_duration_seconds_bucket[5m])))
histogram_quantile(0.99, sum by (le) (rate(uclaw_activation_duration_seconds_bucket[5m])))

# 稳定错误码、DB operation failure、过期 lease、签名/KMS、stale commit
sum by (code) (rate(uclaw_activation_requests_total{outcome="error"}[5m]))
sum by (operation) (rate(uclaw_db_operation_failures_total[5m]))
rate(uclaw_binding_lease_stale_total[5m])
sum by (dependency) (rate(uclaw_signing_failures_total[5m]))
rate(uclaw_commit_stale_total[5m])

# reissue / revoke
sum by (action,outcome) (rate(uclaw_lifecycle_operations_total[15m]))
```

建议告警：

| 告警 | 条件 | 持续 | 等级 |
| --- | --- | --- | --- |
| `ActivationSuccessRateLow` | 5 分钟请求数 >= 20，成功率 < 99% | 10m | P1 |
| `ActivationP95High` | P95 > 1s | 10m | P2 |
| `ActivationP99High` | P99 > 2.5s | 10m | P1 |
| `ActivationInternalErrors` | `INTERNAL_ERROR` > 0.1/s | 5m | P1 |
| `ActivationDBFailures` | DB operation failure > 0.2/s | 10m | P2；伴随成功率下降时 P1 |
| `ActivationLeaseStale` | stale lease > 0.05/s | 10m | P2；持续上升时 P1 |
| `ActivationSigningFailure` | 任一签名/KMS失败 > 0 | 1m | P1 |
| `ActivationCommitStale` | stale commit > 0.05/s | 10m | P2 |
| `ActivationLifecycleFailure` | reissue/revoke error > 0 | 5m | P1 |

发布前以真实基线校准阈值。低流量成功率必须加最小请求数门槛，避免单个请求触发 P1。

## 首轮处置

1. 冻结发布、密钥轮换和 schema 变更。记录告警起止、版本 digest、两个实例健康、DB/KMS 状态和 request ID 样本。服务当前不自动重试 DB 写入，因此指标记录 operation failure，不能解释为 retry 次数。
2. 从管理网络检查 `/health/live`、`/health/ready`。liveness 失败只替换该实例；readiness 失败先查 DB、KMS、两把签名 key，不要反复重启全部实例。
3. 对比两个实例错误率和延迟。仅单实例异常时摘流、保留日志后替换；双实例同时异常时优先查共享 DB、KMS、gateway 和证书。
4. 按稳定错误码分流。客户端输入错误不应触发服务端重试；`INTERNAL_ERROR`、DB retry、KMS/签名错误按依赖故障处理。
5. 恢复后持续观察至少 30 分钟：成功率、P99、DB retry、stale lease/commit、reissue/revoke 全部回到基线，再解除发布冻结。

公网故障按层定位，不跳层绕过安全边界：

1. Caddy：检查 `:443` 监听、`caddy validate`、域名 ACME 状态、域名证书，以及 IP compatibility certificate 的有效期和匹配。
2. activation：分别检查 `http://127.0.0.1:18081/health/ready`、`http://127.0.0.1:18082/health/ready`、DB、KMS 和签名 key readiness。单实例失败时先 stop 它，确认另一实例继续服务，再修复并 start。
3. 仅 compose 环境：再检查 edge mTLS、OpenResty 限流、`public-gateway` healthcheck 和 Docker DNS upstream。不得使用 insecure skip verify，不得为排障公开 OpenResty 端口。

## 常见故障

### DB retry 或不可用

- 检查连接数、锁等待、主从切换、磁盘和事务延迟。不要临时放大连接池压垮 DB。
- 只重试明确的瞬时事务错误；保持原 idempotency key。未知提交结果先按权威状态查询，不生成新激活码。
- DB 未恢复时保留至少一个实例接收健康检查；不要让 gateway 将写请求转发到不同数据库。

### binding lease stale

- stale 少量出现且成功率稳定：确认被杀实例、超时和 GC/CPU 抖动，等待 lease 到期后的同 idempotency key 接管。
- stale 持续增长：查 DB 时钟、实例时钟、长事务和 KMS 延迟。不得手工改 `binding_lease_token` 或缩短 TTL。
- 恢复判据：旧 holder 无法提交；新 holder 只产生一个 device/license/binding；审计记录完整；客户端得到同一权威结果。

### 签名或 KMS 失败

- 立即 P1。停止新激活与 reissue，保留 status/revoke 可用性评估；不得降级为未加密材料或临时本地 key。
- 检查 secret 挂载权限、key version、KMS readiness 和最近轮换。只回滚到仍获批准且可审计的 key version。
- 恢复后用非生产测试库存完成 encrypt/decrypt/sign/verify；确认日志和指标无 key material。

### commit stale

- 检查客户端重试是否保持相同 activation ID、idempotency key、artifact generation。
- 幂等冲突返回固定错误，不覆盖已提交 generation。`server_bound` 长时间未 commit 时查客户端落盘和网络；不得后台假定成功。

### reissue / revoke 失败

- 先查 license 当前 revision/status 和审计事件，再重放相同 idempotency key。
- reissue 必须保证旧 license 永久 `reissued`、新 license 唯一 active；revoke 必须保持终态。禁止人工把旧 license 改回 active。
- 任一未知提交结果按权威查询收敛；不得新建第二次操作规避冲突。

### device token 疑似泄漏

本节的 `bash` 块必须整块由 root 的 Bash 执行，不得用 `sh` 或逐行复制，以保留 `set -Eeuo pipefail` 和 ERR trap。

1. 按 P1 冻结相关发布。只用 license ID、request ID 和审计事件确认影响范围，不在日志、工单或终端输出原 token。
2. 二选一：不再信任设备时执行 `revoke`，设备仍可信且需继续服务时直接执行 `reissue`。`reissue` 在同一事务中 revoke 旧 active token 并创建新 active token；不得先 `revoke` 再 `reissue`，因为 reissue 要求当前仍有 active token。
3. `--confirm-target` 的真实算法是小写十六进制 `SHA-256("license:" + licenseID)`。不使用 token 本身计算，不打印 token。

执行前定义 `$LICENSE_ID`、`$CHANGE_REASON`、`$UCLAW_OPERATOR_ID`、`$UCLAW_REQUEST_ID` 和全新 `$UCLAW_IDEMPOTENCY_KEY`。以下命令是只 revoke 的完整路径：

```bash
set -Eeuo pipefail
set +x
trap 'exit_code=$?; printf "device token revoke failed at line %s with status %s\\n" "$LINENO" "$exit_code" >&2; exit "$exit_code"' ERR
for required_name in LICENSE_ID CHANGE_REASON UCLAW_OPERATOR_ID UCLAW_REQUEST_ID UCLAW_IDEMPOTENCY_KEY; do
  test -n "${!required_name:-}"
done
export UCLAW_OPERATOR_ID UCLAW_REQUEST_ID UCLAW_IDEMPOTENCY_KEY
export UCLAW_OPERATOR_CREDENTIAL_FILE=/run/secrets/uclaw-activation/operator-credential
test "$(stat -c '%u:%a' "$UCLAW_OPERATOR_CREDENTIAL_FILE")" = '0:600'
LICENSE_CONFIRMATION_DIGEST="$(printf 'license:%s' "$LICENSE_ID" | sha256sum | awk '{print $1}')"
set -a
. /etc/uclaw-activation.env
set +a
/usr/local/sbin/uclaw-activation-admin device-token revoke \
  --license-id "$LICENSE_ID" \
  --confirm-target "$LICENSE_CONFIRMATION_DIGEST" \
  --reason "$CHANGE_REASON"
```

若选择 reissue，使用不同的全新 request/idempotency ID，并事先定义 `$DEVICE_TOKEN_OUTPUT_FILE`。其父目录必须 root 所有、mode `0700`，output 文件必须事先不存在：

```bash
set -Eeuo pipefail
set +x
trap 'exit_code=$?; printf "device token reissue stopped at line %s with status %s\\n" "$LINENO" "$exit_code" >&2; exit "$exit_code"' ERR
for required_name in LICENSE_ID DEVICE_TOKEN_OUTPUT_FILE CHANGE_REASON UCLAW_OPERATOR_ID UCLAW_REQUEST_ID UCLAW_IDEMPOTENCY_KEY; do
  test -n "${!required_name:-}"
done
test ! -e "$DEVICE_TOKEN_OUTPUT_FILE"
test "$(stat -c '%u:%a' "$(dirname "$DEVICE_TOKEN_OUTPUT_FILE")")" = '0:700'
export UCLAW_OPERATOR_ID UCLAW_REQUEST_ID UCLAW_IDEMPOTENCY_KEY
export UCLAW_OPERATOR_CREDENTIAL_FILE=/run/secrets/uclaw-activation/operator-credential
test "$(stat -c '%u:%a' "$UCLAW_OPERATOR_CREDENTIAL_FILE")" = '0:600'
LICENSE_CONFIRMATION_DIGEST="$(printf 'license:%s' "$LICENSE_ID" | sha256sum | awk '{print $1}')"
set -a
. /etc/uclaw-activation.env
set +a
/usr/local/sbin/uclaw-activation-admin device-token reissue \
  --license-id "$LICENSE_ID" \
  --confirm-target "$LICENSE_CONFIRMATION_DIGEST" \
  --reason "$CHANGE_REASON" \
  --output-file "$DEVICE_TOKEN_OUTPUT_FILE"
test "$(stat -c '%u:%a' "$DEVICE_TOKEN_OUTPUT_FILE")" = '0:600'
```

命令 stdout/stderr 只允许脱敏 result，不得 `cat`、`jq` 或输出 `$DEVICE_TOKEN_OUTPUT_FILE`。未知 commit 结果时 CLI 会保留该 `0600` 文件以供相同 idempotency key 恢复，因此不得盲目删除。成功交付新 token 后，验证只有一个 active token，旧 token 为 revoked，然后安全清理 output 文件和会话变量。

### 代理 401、429 或 5xx

- 全程只用 response/request ID 关联 Caddy、两个实例、PostgreSQL 审计和 New API 日志。禁止打印 Authorization、device token、New API Key 或完整 prompt。
- 401：检查 token digest 是否命中、token/inventory/device/license/binding 状态、license 时间窗和 setup/balance status。无 bearer、随机 bearer 和 revoked bearer 对外正文必须一致。
- 429：检查该 mapping 的 requests-per-minute 和 concurrent-requests，以及 PostgreSQL `model_proxy_admissions`。不要手工删 active lease 规避限流。
- 5xx：先区分本地 DB/KMS/decrypt 错误和上游 connect/timeout/status。对外只保留脱敏 502/503 和 request ID；检查 New API 安全组仅允许 `121.41.89.103`、mTLS 链、`NEW_API_ALLOWED_HOSTS` 和上游证书，不跟随 redirect。

### model proxy admission stale lease

- 正常终止请求会写 `completed_at`。进程被杀或超时留下的 lease 在 `lease_expires_at` 后失效；下一次同 token admission 会在 PostgreSQL transaction/advisory lock 内自动清理，每次最多 1000 条，并清理十分钟以前的记录。
- stale 持续增长时查进程被杀、`MODEL_PROXY_TIMEOUT`/`MODEL_PROXY_ADMISSION_LEASE` 顺序、DB 时钟和长事务。不手工改 `lease_expires_at`，不禁用 admission。

### 限流激增

- 按 `dimension` 判断来源，不查询或导出原始 identity。联合 WAF、网关聚合日志和 request ID 判断攻击或客户端循环。
- 攻击时优先在边缘收紧 IP；username/device 阈值调整需评估共享出口和合法重试。禁止关闭全部限流。

### activation 容器地址变化

- 本节只适用已审批 compose 环境，不适用当前 VPS systemd 主路径。
- OpenResty 在启动时通过 Docker DNS 解析 `activation-1`、`activation-2`。当前固定镜像不使用 Nginx 商业版或新版本专属的 upstream `resolve` 参数。
- 重建、替换或网络重连 activation 容器后，执行 `docker compose -f deploy/compose.production.example.yaml restart public-gateway`，刷新 upstream 地址。随后确认 `public-gateway` healthcheck 为 healthy，再确认 Caddy 对 `/health/ready` 返回 200。
- 不得临时开放 OpenResty 端口或跳过 Caddy-to-OpenResty mTLS。若 gateway 重启后仍失败，检查 Docker DNS、两个 activation healthcheck、独立 edge mTLS 证书 SAN 与有效期。

## 双实例与 lease-holder 故障注入

当前 VPS systemd 主路径先执行双实例 kill-one 验证：保持连续的公网 health 和代理鉴权请求，依次 stop 18081、验证 18082 接管、start 18081；再 stop 18082、验证 18081 接管、start 18082。每次操作前确认另一实例 ready，不得同时 stop 两个实例。

以下步骤只适用 compose 参考拓扑的专项 lease-holder 故障注入。

只有真实 Docker daemon、真实 PostgreSQL、真实 migration、真实 secret 和可审计测试库存齐全时，以下结果才能记为 `PASS`。`docker compose config`、mock、单元测试不能替代。

1. 用不可变 image digest 启动示例拓扑，确认两个实例连接同一 DB，公网不能访问 `/internal/*`，管理端口不监听非 loopback 地址。
2. 通过 TLS gateway 发起持续并发激活。确认请求实际分布到两个实例；记录吞吐、成功率、P95/P99、稳定错误码和 DB retry。
3. 选一条停在 `binding` 的测试请求，通过 request ID、审计和 DB lease token 确认真实 holder。不得根据猜测选择容器。
4. 将已确认 holder 容器 ID 赋给 `$CONFIRMED_HOLDER_CONTAINER`，执行 `docker kill "$CONFIRMED_HOLDER_CONTAINER"`。等待 lease 到期，以相同 idempotency key 重试。
5. 验证另一实例接管；只创建一个 device/license/binding；旧 holder 重启后不能 stale commit；无 secret 泄漏；审计链连续。
6. 逐一验证 reissue/revoke 在两个实例间立即读取相同权威终态。恢复被杀实例，再持续压测 15 分钟。

任一前提缺失，记录 `BLOCKED/SKIP`、时间、精确命令和原始错误。不得写“推测通过”。当前工作站示例证据（2026-08-13）：`docker version` 返回 `Cannot connect to the Docker daemon at unix:///Users/jamison/.docker/run/docker.sock. Is the docker daemon running?`，所以双实例压测与 kill lease holder 均为 `BLOCKED/SKIP`。

## 回滚与关闭

- 应用回滚只使用上一已验证 image digest；保持 DB schema 向后兼容。schema 不兼容时停止，按数据库变更计划处理。
- gateway 回滚后重新验证 Caddy TLS、edge mTLS、1 MiB body limit、60s/70s/75s timeout 链、三个摘要限流维度、公网管理路由拒绝和 loopback 管理监听。禁止通过公开 OpenResty 端口或跳过 Caddy/mTLS 完成回滚。
- 关闭事件前附：告警图、稳定错误码、request ID、部署 digest、依赖事件、处置时间线、真实验收结果和遗留风险。所有证据脱敏。
