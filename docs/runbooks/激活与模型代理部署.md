# 激活与模型代理部署

## 目标与生产基线

本手册覆盖 `121.41.89.103` 上激活服务、长期设备令牌和模型代理的部署、域名切换、New API 接入、验收和回滚。本手册不记录真实 activation code、device token、New API Key、签名私钥、KEK、数据库密码或 operator credential。

2026-08-14 只读盘点确认当前生产主路径为：

```text
public HTTPS :443
  -> caddy.service
  -> 127.0.0.1:18081 / 127.0.0.1:18082
  -> uclaw-activation@18081.service / uclaw-activation@18082.service
  -> postgresql.service
```

两个 Go 实例只监听 loopback，Caddy 监听 `80/443`，四个 systemd 服务均为 active。当前 VPS 使用宿主机 systemd + Caddy + PostgreSQL，这是本手册唯一主部署路径。`product/activation-server/deploy/compose.production.example.yaml` 是新环境的容器化参考拓扑；它增加 OpenResty、edge mTLS 和 loopback management gateway，不得在当前 VPS 发布中混用 `docker compose` 命令、容器服务名或容器端口。若未来经审批整体迁移到 compose，必须另写迁移和回退计划。

## 发布前门禁

以下标记为 `bash` 的关键块必须作为完整块由 root 的 Bash 执行，不得逐行复制，不得使用 `sh`。执行前以 `test -n "$BASH_VERSION"` 确认解释器；`set -Eeuo pipefail`、ERR trap 和 EXIT secret cleanup trap 必须在同一进程内生效。

在 VPS 上定义本次发布变量，变量值必须来自已审批的制品和 UTC 时间：

```sh
export RELEASE_GIT_SHA
export BACKUP_UTC
export RELEASE_DIR="/opt/uclaw-activation/releases/$RELEASE_GIT_SHA"
export BACKUP_DIR="/opt/uclaw-activation/backups/$BACKUP_UTC"
test -n "$RELEASE_GIT_SHA"
test -n "$BACKUP_UTC"
```

必须先满足以下条件：

1. 本地 Task 10 质量门禁通过；Linux amd64 server/admin、migration 1-4 和 SHA-256 manifest 来自同一 `RELEASE_GIT_SHA`。
2. `systemctl is-active postgresql caddy uclaw-activation@18081 uclaw-activation@18082` 全部返回 `active`；`ss -lntp` 确认 `18081/18082` 仅绑定 `127.0.0.1`。
3. `/opt`、`/var/lib/postgresql` 空间可同时容纳 custom-format dump、两版 binary、配置备份和发布制品。
4. 发布人、回滚人、观察时间窗、上一版 SHA/checksum 已记录。没有可回滚备份时停止。
5. 禁止 shell tracing：会话中先执行 `set +x`；禁止将 secret 放在 CLI 参数、命令历史、stdout、工单或验收记录。

## 可恢复备份

任一步失败必须停止发布：

```bash
set -Eeuo pipefail
on_backup_error() {
  local exit_code=$?
  printf 'backup failed at line %s with status %s\n' "$LINENO" "$exit_code" >&2
  exit "$exit_code"
}
cleanup_backup_environment() {
  unset PGSERVICEFILE PGPASSFILE
}
trap on_backup_error ERR
trap cleanup_backup_environment EXIT

: "${BACKUP_DIR:?BACKUP_DIR is required}"
export PGSERVICEFILE=/run/secrets/uclaw-activation/pg_service.conf
export PGPASSFILE=/run/secrets/uclaw-activation/pgpass
for secret_file in "$PGSERVICEFILE" "$PGPASSFILE"; do
  test -f "$secret_file"
  test ! -L "$secret_file"
  test "$(stat -c '%u:%a' "$secret_file")" = '0:600'
done

install -d -m 0700 "$BACKUP_DIR"
install -m 0600 /etc/uclaw-activation.env "$BACKUP_DIR/uclaw-activation.env"
install -m 0600 /etc/caddy/Caddyfile "$BACKUP_DIR/Caddyfile"
install -m 0600 /etc/systemd/system/uclaw-activation@.service "$BACKUP_DIR/uclaw-activation@.service"
install -m 0600 /usr/local/bin/uclaw-activation-server "$BACKUP_DIR/uclaw-activation-server"
install -m 0600 /usr/local/sbin/uclaw-activation-admin "$BACKUP_DIR/uclaw-activation-admin"
test ! -e /opt/uclaw-activation/compose.yml || install -m 0600 /opt/uclaw-activation/compose.yml "$BACKUP_DIR/compose.yml.reference-only"
pg_dump --dbname='service=uclaw_migration' -Fc --no-owner --no-acl --file "$BACKUP_DIR/activation.dump"
pg_restore --list "$BACKUP_DIR/activation.dump" > "$BACKUP_DIR/activation.dump.list"
systemctl cat caddy.service > "$BACKUP_DIR/caddy.service"
psql --dbname='service=uclaw_migration' -X -Atc \
  "SELECT version || ':' || encode(checksum,'hex') FROM schema_migrations ORDER BY version" \
  > "$BACKUP_DIR/schema-migrations.txt"
(
  cd "$BACKUP_DIR"
  find . -maxdepth 1 -type f ! -name SHA256SUMS -print0 | sort -z | xargs -0 sha256sum > SHA256SUMS
  sha256sum -c SHA256SUMS
)
```

`pg_service.conf` 的 `[uclaw_migration]` 只写 host、port、dbname、user 和 TLS 参数；密码只写入 `pgpass`。两文件均必须 root 所有且 mode `0600`。`pg_dump`/`psql` argv 只出现无密码的 service name。如生产使用 peer auth，可以等价的专用 OS/migration role 命令取代。备份中的 env、dump 和 binary 均按 secret 保管。

## migration 4

migration 只能向前。使用独立 migration role，不得使用 application role 执行 DDL。从 root-only 文件读取凭据，命令不包含密码字面量：

```bash
set -Eeuo pipefail
set +x
on_migration_error() {
  local exit_code=$?
  printf 'migration failed at line %s with status %s\n' "$LINENO" "$exit_code" >&2
  exit "$exit_code"
}
cleanup_migration_environment() {
  unset ACTIVATION_DATABASE_URL ACTIVATION_MIGRATION_ROLE ACTIVATION_MIGRATION_PASSWORD
  unset ACTIVATION_APP_ROLE ACTIVATION_APP_PASSWORD PGSERVICEFILE PGPASSFILE PGOPTIONS
}
trap on_migration_error ERR
trap cleanup_migration_environment EXIT

export PGSERVICEFILE=/run/secrets/uclaw-activation/pg_service.conf
export PGPASSFILE=/run/secrets/uclaw-activation/pgpass
MIGRATION_ROLE_FILE=/run/secrets/uclaw-activation/migration-role
MIGRATION_PASSWORD_FILE=/run/secrets/uclaw-activation/migration-password
APP_ROLE_FILE=/run/secrets/uclaw-activation/app-role
APP_PASSWORD_FILE=/run/secrets/uclaw-activation/app-password
for secret_file in "$PGSERVICEFILE" "$PGPASSFILE" "$MIGRATION_ROLE_FILE" "$MIGRATION_PASSWORD_FILE" "$APP_ROLE_FILE" "$APP_PASSWORD_FILE"; do
  test -f "$secret_file"
  test ! -L "$secret_file"
  test "$(stat -c '%u:%a' "$secret_file")" = '0:600'
done

export ACTIVATION_DATABASE_URL='service=uclaw_migration'
export PGOPTIONS='-c log_statement=none -c log_min_error_statement=panic -c log_parameter_max_length=0'
export ACTIVATION_MIGRATION_ROLE="$(<"$MIGRATION_ROLE_FILE")"
export ACTIVATION_MIGRATION_PASSWORD="$(<"$MIGRATION_PASSWORD_FILE")"
export ACTIVATION_APP_ROLE="$(<"$APP_ROLE_FILE")"
export ACTIVATION_APP_PASSWORD="$(<"$APP_PASSWORD_FILE")"
"$RELEASE_DIR/deploy/migrate.sh"
```

`PGOPTIONS` 在该 migration session 关闭 statement/parameter 日志，避免脚本中 role password DDL 进入 PostgreSQL 标准日志。部署前必须在隔离环境确认托管平台或 `pgaudit` 不会另行记录密码 DDL；无法保证时停止，不得以“先迁移后删日志”代替预防。

验证 ledger、relation 和权限：

```sql
SELECT version, encode(checksum, 'hex') FROM schema_migrations ORDER BY version;
SELECT to_regclass('public.device_access_tokens');
SELECT to_regclass('public.model_proxy_admissions');
```

预期 ledger 为 1-4，两个 relation 存在。再用 application role 读 ledger，并确认它无法更改 ledger 或创建 table/schema。migration 4 只增加 table、column、constraint 和 index，不破坏旧 binary；回滚 binary 时保留 schema 和新数据。不得删除 migration 4 对象，不得从 ledger 删除 version 4，不得运行旧 binary 携带的旧 migrator。旧 binary 回滚只复用当前新 migrator 做读取验证，或显式跳过 migration。

## 配置与域名端点

先在 root-only staging 副本中准备新代理配置。域名 DNS/证书门禁未通过时，live `/etc/uclaw-activation.env` 必须继续使用 `PUBLIC_MODEL_ENDPOINT=https://121.41.89.103/model-api/`，不得提前签发无法访问的域名 endpoint。证书门禁通过后，再将以下值安装到 live env，并保持 root-only mode：

```text
PUBLIC_MODEL_ENDPOINT=https://license.yiyong.me/model-api/
MODEL_PROXY_REQUEST_BODY_BYTES=1048576
MODEL_PROXY_RESPONSE_BODY_BYTES=4194304
MODEL_PROXY_TIMEOUT=60s
MODEL_PROXY_ADMISSION_LEASE=65s
```

`PUBLIC_MODEL_ENDPOINT` 必须以 `/model-api/` 结尾。域名切换后，新激活响应中的 `builtinCredential.endpoint` 也必须精确为 `https://license.yiyong.me/model-api/`，不得是 New API 真实地址。

### DNS 和 registry 门禁

必须先由 registry/RDAP 确认域状态中不再有 `clientHold`，再验证权威 DNS。运行：

```sh
curl -fsSL https://rdap.org/domain/yiyong.me | jq -r '.status[]'
dig +short license.yiyong.me A
dig +short license.yiyong.me AAAA
```

预期：RDAP 输出不包含 `client hold`、`clientHold` 或等价 hold 状态；A 记录只包含 `121.41.89.103`；AAAA 为空，除非 VPS 已审批并验证 IPv6 入口。当前 2026-08-14 盘点的 A/AAAA 均为空，因此域名切换仍是未满足门禁。

### Caddy 路由与自动证书

先备份 Caddyfile。新配置必须将公网路由做 allowlist：只有 `/v1/*`、`/model-api/*`、`/health/ready` 反向代理到 `127.0.0.1:18081` 和 `127.0.0.1:18082`；`/internal/*`、`/metrics`、管理 API 和所有其他路径返回 404。不得对公网监听管理端口。

`license.yiyong.me` 站点不写 `tls` 证书文件，由 Caddy ACME 自动签发和续期。`https://121.41.89.103` 站点保留现有已验证的 IP TLS 配置，不得用域名证书代替 IP compatibility certificate。当前 systemd 拓扑使用以下 allowlist 结构：

```caddyfile
{
	default_sni 121.41.89.103
}

(public_routes) {
	@public path /v1/* /model-api/* /health/ready
	handle @public {
		reverse_proxy 127.0.0.1:18081 127.0.0.1:18082 {
			lb_policy least_conn
			fail_duration 10s
			max_fails 3
			lb_retries 1
			lb_try_duration 2s
			lb_try_interval 100ms
			health_uri /health/ready
			health_interval 1s
			health_timeout 2s
		}
	}
	handle {
		respond 404
	}
}

license.yiyong.me {
	import public_routes
}

https://121.41.89.103 {
	tls {
		issuer acme {
			profile shortlived
		}
	}
	import public_routes
}
```

若当时 IP HTTPS 使用显式 compatibility certificate，保留已验证的 `tls` 证书/私钥路径，不改成上述 ACME 段。域名站点始终使用 Caddy 自动 HTTPS。验证并 reload：

```bash
set -Eeuo pipefail
trap 'exit_code=$?; printf "Caddy validation/reload failed at line %s with status %s\\n" "$LINENO" "$exit_code" >&2; exit "$exit_code"' ERR

caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy
journalctl -u caddy --since "10 minutes ago" --no-pager
curl --fail --silent --show-error https://license.yiyong.me/health/ready
printf '' | openssl s_client -connect license.yiyong.me:443 -servername license.yiyong.me 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

该块依赖 `set -Eeuo pipefail` 和 ERR trap 严格串行：`caddy validate` 成功后才执行 reload，reload 成功后才读取 journal、请求域名 health 和检查证书。任一步失败都会停止，禁止用旧站点仍返回健康响应掩盖 validate/reload 错误。只有域名 health 为 200、SAN 包含 `DNS:license.yiyong.me`、issuer 和有效期正常、Caddy journal 无 ACME 错误时，才允许把发行配置的 activation endpoint 和服务端 `PUBLIC_MODEL_ENDPOINT` 切到域名。Caddy 的 `/data` 或宿主证书存储必须持久化且可写，监控 renew 失败和证书到期时间。

域名切换还必须更新 GitHub Actions repository/environment variable：`vars.UCLAW_ACTIVATION_ENDPOINT=https://license.yiyong.me/`。`.github/workflows/portable-launcher.yml` 把该值编译进 Launcher，所以修改 variable 不会更新已发行 binary。具有已审批 GitHub 权限的发布人执行：

```bash

trap 'exit_code=$?; printf "launcher rebuild failed at line %s with status %s\\n" "$LINENO" "$exit_code" >&2; exit "$exit_code"' ERR

test "$(gh api "repos/$GITHUB_REPOSITORY/commits/$RELEASE_GIT_REF" --jq .sha)" = "$RELEASE_GIT_SHA"
gh variable set UCLAW_ACTIVATION_ENDPOINT --repo "$GITHUB_REPOSITORY" --body 'https://license.yiyong.me/'

```

`RELEASE_GIT_REF` 必须是 GitHub 上已存在的 branch/tag name；首个 `test` 保证它在触发前解析到已审批 `$RELEASE_GIT_SHA`。等待 `Portable launcher` workflow 完成，再核对该次 run 的 `headSha` 精确等于 `$RELEASE_GIT_SHA`；两次校验任一失败都停止。之后才将同一 SHA 的制品交给正式签名/公证/发布流水线。该 GitHub workflow 是构建和测试门禁，不得把其 artifact 误当为已签名正式发行物。必须重做签名、SHA-256、Win10/11 普通用户、Defender、物理 U 盘、正常激活和首次模型请求验收后，才能推送新发行。域名失败时停止新发行，将 GitHub variable 恢复为 `https://121.41.89.103/`，重新运行构建/签名门禁，并回退到上一已签名、已验收的 IP endpoint 发行物；禁止就地修改已签名 binary。

旧 IP HTTPS endpoint 自域名切换日起至少保留一个完整发行周期。移除前必须证明受支持客户端全部已迁移，且回滚不再依赖 IP。

## New API 安全接入

1. New API 侧安全组/防火墙只允许源 IP `121.41.89.103` 访问代理所需 HTTPS 端口，拒绝其他公网源。VPS 不向 New API 开放入站端口。
2. 优先在 VPS 与 New API 间使用 mTLS；client cert/key 只在 root-only secret store，New API 校验独立 client CA。若暂无 mTLS，必须记录风险、保留 IP allowlist，不得降级为 HTTP 或关闭证书校验。
3. `NEW_API_ALLOWED_HOSTS` 只包含已审批 New API hostname。`base-url` 使用 HTTPS 和该 hostname，禁止 IP 漂移、redirect 或用户信息。

New API Key 只通过 root-only mode `0600` 临时文件录入。不将 key 放在 shell 变量、CLI 参数或 stdin pipeline。先定义不含 secret 的 `$INVENTORY_ID`、`$NEW_API_USER_ID`、`$NEW_API_USERNAME`、`$NEW_API_BASE_URL`、`$DEFAULT_MODEL`、`$ALLOWED_MODELS`、`$REQUESTS_PER_MINUTE`、`$CONCURRENT_REQUESTS`、`$CHANGE_REASON`、`$UCLAW_OPERATOR_ID`、`$UCLAW_REQUEST_ID` 和 `$UCLAW_IDEMPOTENCY_KEY`，再在同一 bash 进程完成录入、扫描和清理：

```bash
set -Eeuo pipefail
set +x
test -n "${BASH_VERSION:-}"
[[ -o history ]]
: "${HISTFILE:=/root/.bash_history}"
test "$HISTFILE" = '/root/.bash_history'
test ! -L "$HISTFILE"
umask 077
touch "$HISTFILE"
test -f "$HISTFILE"
test -w "$HISTFILE"
test "$(stat -c '%u:%a' "$HISTFILE")" = '0:600'
NEW_API_KEY_FILE=/run/secrets/uclaw-activation/new-api-key.import
JOURNAL_SCAN_FILE=/run/secrets/uclaw-activation/new-api-key.journal-scan
cleanup_mapping_secrets() {
  local cleanup_status=0
  if ! history -c; then
    cleanup_status=1
    printf 'in-memory Bash history cleanup failed\n' >&2
  fi
  for sensitive_file in "$NEW_API_KEY_FILE" "$JOURNAL_SCAN_FILE"; do
    if test -e "$sensitive_file"; then
      if ! shred -u "$sensitive_file" 2>/dev/null; then
        cleanup_status=1
        printf 'secure temporary file deletion failed; attempting fallback removal\n' >&2
        if ! rm -f "$sensitive_file"; then
          cleanup_status=1
          printf 'fallback temporary file removal failed\n' >&2
        fi
      fi
    fi
  done
  unset UCLAW_OPERATOR_CREDENTIAL_FILE UCLAW_OPERATOR_ID UCLAW_REQUEST_ID UCLAW_IDEMPOTENCY_KEY
  unset DATABASE_URL ACTIVATION_PEPPER LICENSE_SIGNING_KEY STATUS_SIGNING_KEY KMS_KEK ADMIN_SECRET_FINGERPRINT_KEY
  return "$cleanup_status"
}
on_mapping_error() {
  local exit_code=$?
  printf 'mapping update failed at line %s with status %s\n' "$LINENO" "$exit_code" >&2
  exit "$exit_code"
}
on_mapping_exit() {
  local exit_code=$?
  local cleanup_status=0
  trap - EXIT
  cleanup_mapping_secrets || cleanup_status=$?
  if (( exit_code != 0 )); then
    exit "$exit_code"
  fi
  exit "$cleanup_status"
}
scan_without_echoing_secret() {
  local scan_status=0
  rg -l -F -f "$NEW_API_KEY_FILE" "$@" || scan_status=$?
  case "$scan_status" in
    0) printf 'secret match found; inspect named file without copying content\n' >&2; return 20 ;;
    1) return 0 ;;
    *) printf 'secret scan failed with status %s\n' "$scan_status" >&2; return "$scan_status" ;;
  esac
}
trap on_mapping_error ERR
trap on_mapping_exit EXIT

for required_name in INVENTORY_ID NEW_API_USER_ID NEW_API_USERNAME NEW_API_BASE_URL DEFAULT_MODEL ALLOWED_MODELS REQUESTS_PER_MINUTE CONCURRENT_REQUESTS CHANGE_REASON UCLAW_OPERATOR_ID UCLAW_REQUEST_ID UCLAW_IDEMPOTENCY_KEY; do
  test -n "${!required_name:-}"
done
export UCLAW_OPERATOR_ID UCLAW_REQUEST_ID UCLAW_IDEMPOTENCY_KEY
export UCLAW_OPERATOR_CREDENTIAL_FILE=/run/secrets/uclaw-activation/operator-credential
for secret_file in /etc/uclaw-activation.env "$UCLAW_OPERATOR_CREDENTIAL_FILE"; do
  test -f "$secret_file"
  test ! -L "$secret_file"
  test "$(stat -c '%u:%a' "$secret_file")" = '0:600'
done

umask 077
install -m 0600 /dev/null "$NEW_API_KEY_FILE"
install -m 0600 /dev/null "$JOURNAL_SCAN_FILE"
${EDITOR:-vi} "$NEW_API_KEY_FILE"
test -s "$NEW_API_KEY_FILE"
test "$(stat -c '%u:%a' "$NEW_API_KEY_FILE")" = '0:600'

set -a
. /etc/uclaw-activation.env
set +a
/usr/local/sbin/uclaw-activation-admin mapping set \
  --inventory-id "$INVENTORY_ID" \
  --new-api-user-id "$NEW_API_USER_ID" \
  --new-api-username "$NEW_API_USERNAME" \
  --base-url "$NEW_API_BASE_URL" \
  --default-model "$DEFAULT_MODEL" \
  --allowed-models "$ALLOWED_MODELS" \
  --requests-per-minute "$REQUESTS_PER_MINUTE" \
  --concurrent-requests "$CONCURRENT_REQUESTS" \
  --key-file "$NEW_API_KEY_FILE" \
  --reason "$CHANGE_REASON"
/usr/local/sbin/uclaw-activation-admin mapping show --inventory-id "$INVENTORY_ID"

journalctl -u uclaw-activation@18081 -u uclaw-activation@18082 --since '30 minutes ago' --no-pager > "$JOURNAL_SCAN_FILE"
history -a "$HISTFILE"
scan_without_echoing_secret "$HISTFILE"
scan_without_echoing_secret /root /var/log
scan_without_echoing_secret "$JOURNAL_SCAN_FILE"
cleanup_mapping_secrets
trap - EXIT
```

`mapping show` 真实输出包含 inventory/user 标识、base URL host、model/policy、KMS key version、status 和 updated time；它不输出 New API Key fingerprint，也没有 list 能力。不得把 `mapping show` 记为 key fingerprint 或“无旧 envelope 引用”的证据。该块只允许在 history 已启用的 root Bash 执行；`HISTFILE` 为空时设为唯一允许的 `/root/.bash_history`，其他路径、symlink、非 root `0600` 或不可写文件均 fail closed。`history -a` 失败会在扫描前停止；history file、`/root`、`/var/log` 和 journal 的扫描只输出命中文件名或固定错误，不输出匹配行/secret。`rg` 的 `0/1/其他` 分别代表命中/无命中/扫描失败，不会把读取错误当成无命中。`journalctl` 先完整写入 root-only 临时文件，读取失败同样停止。EXIT trap 和成功路径都清理 key/journal 文件并以 `history -c` 清空当前 Bash 内存 history；清理失败不得记为通过。

## 验收矩阵

所有证据只记录时间、git SHA、binary checksum、request/support ID、HTTP status 和脱敏摘要。

1. 公网路由：`/v1/*`、`/model-api/*`、`/health/ready` 按契约响应；`/internal/*`、`/metrics`、管理 API 和未知路径必须为 404。用 `ss -lntp` 确认无公网 admin/management 端口。
2. 代理负向：无 bearer、随机 bearer、revoked bearer 均为一致的 401；不允许模型为 403；超限为 429；上游不可用为脱敏 502/503。response 不得包含 New API hostname 之外的内部地址、key、token 或完整 prompt。
3. 激活：错误激活码为 `ACTIVATION_INVALID`；正确测试库存绑定后无 username/expiry；二次同幂等恢复返回同一 device/license/token。客户端 `builtin-model-credential.v1.json` mode 为 `0600`，endpoint 为预期公共代理地址。
4. revoke/reissue：测试 device token revoke 后立即 401；reissue 只产生一个 active token，旧 token 永久失效，新 token 只写 root-only output 文件。细节见 [激活服务故障处理](./激活服务故障处理.md)。
5. admission：两实例共用 PostgreSQL lease。一个请求逾期后，下次同 token admission 自动清理 expired lease，无需人工 SQL；十分钟以前的记录也由请求路径限量清理。
6. kill-one：先保持持续 health 和代理鉴权流量，再依次 `systemctl stop uclaw-activation@18081`、验证 18082 接管、恢复 18081；然后对 18082 重复。禁止同时 stop 两个实例。
7. New API Key rotation canary：先 set 新 envelope，通过单个专用测试库存/设备做 models 和最小 chat canary，再扩大。只有 canary 和观察通过后才可在 New API 撤销旧 key。见 [激活服务密钥轮换](./激活服务密钥轮换.md)。

## binary/config 回滚

回滚触发条件：激活回归、敏感信息泄漏、migration ledger/checksum 不一致、双实例无法 ready、公网私有路由可访问或域名证书故障无法在观察窗内恢复。

1. 停止新发布和管理写操作，保留 request ID 和脱敏日志。
2. 将 `/etc/uclaw-activation.env`、Caddyfile 和 systemd unit 恢复为 `$BACKUP_DIR` 中已验证版本，重新 `caddy validate`。
3. 将 `/opt/uclaw-activation/current` 原子指回上一 release，确认 `/usr/local` 两个 symlink 指向它。
4. 仍按 18081、18082 滚动重启和验证。不得同时重启。
5. 保留 migration 4 schema 和所有新数据。不运行旧 migrator，不执行 down migration，不删 ledger 或新 table/column。
6. 重做 public allowlist、负向代理、health、kill-one 和 secret scan。

旧 binary 只在 migration 4 保持 additive、它不强制 ledger 精确等于 3、且不会尝试降级 schema 时才能回滚。不满足任一条件时，停止自动回滚并执行隔离恢复，见 [激活数据库恢复](./激活数据库恢复.md)。

## 域名、证书和 DNS 回滚

- 证书签发失败：保持 IP HTTPS 服务和旧发行配置，不切 `PUBLIC_MODEL_ENDPOINT`；恢复 A/AAAA、80/443 入站、Caddy 存储权限、ACME 限额或系统时钟后重试。不关闭 TLS 校验。
- DNS 错指或不稳定：将 A 恢复为上一已验证值，删除未验证 AAAA，保持 Caddy 两个站点。使用权威和多个公共 resolver 监测 TTL 收敛。
- 域名已切但必须恢复 IP endpoint：将 GitHub Actions `vars.UCLAW_ACTIVATION_ENDPOINT` 改回 `https://121.41.89.103/`，回退上一已签名、已验收的 IP endpoint 发行物；将 `/etc/uclaw-activation.env` 的 `PUBLIC_MODEL_ENDPOINT` 改回 `https://121.41.89.103/model-api/`，滚动重启后用全新测试库存确认新 `builtinCredential.endpoint` 为 IP 值。不就地修改已签名 binary。

已签发的 builtin credential 内含当时 endpoint，修改服务 env 不会追溯改写客户端文件。因此域名 DNS 回滚后仍要尽量保持域名站点可用；无法保持时，必须通过已审批的客户端凭据恢复/重发流程更新 endpoint，不得只轮换 device token 并假定 endpoint 已改变。

## 发布关闭
