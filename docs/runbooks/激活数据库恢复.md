# 激活数据库备份与恢复

## 目标与边界

- RPO：生产 PostgreSQL 启用连续 WAL 归档，PITR 目标不超过 15 分钟数据损失。
- RTO：从确认恢复时间点起，60 分钟内完成新实例恢复、校验和受控切流。
- 恢复只写入新数据库或隔离实例。禁止覆盖仍在服务的生产库。
- 备份包含激活状态、许可 revision、长期设备 token digest、New API Key 加密 envelope、model proxy admission 与审计事件；不得包含明文激活码、startup secret、device token 或 New API Key。
- 部署前的 DB/env/Caddyfile/systemd/compose reference/binary 一致备份和 checksum 步骤见 [激活与模型代理部署](./激活与模型代理部署.md)。本文的数据库恢复不代替发布前完整备份。

## 备份与 PITR 前提

1. PostgreSQL 基础备份与 WAL 归档由基础设施层管理；归档存储启用版本化、加密和独立保留策略。
2. 每日逻辑备份用于可移植恢复演练：

```sh
umask 077
pg_dump --format=custom --no-owner --no-acl \
  --file activation-"$(date -u +%Y%m%dT%H%M%SZ)".dump \
  "$ACTIVATION_DATABASE_URL"
```

3. 记录 dump 的 SHA-256、PostgreSQL 主版本、开始/结束时间、源实例和 WAL 归档健康状态。备份文件与校验值不得写入仓库。

## 恢复命令

逻辑恢复必须使用新库：

```sh
createdb --maintenance-db="$ACTIVATION_ADMIN_DATABASE_URL" \
  "$ACTIVATION_RESTORE_DATABASE"
pg_restore --exit-on-error --no-owner --no-acl \
  --dbname "$ACTIVATION_RESTORE_DATABASE_URL" \
  activation-YYYYmmddTHHMMSSZ.dump

# Re-establish migration ownership, application DML grants, default privileges,
# and verify the application role still has no DDL privilege.
ACTIVATION_DATABASE_URL="$ACTIVATION_RESTORE_DATABASE_URL" \
  product/activation-server/deploy/migrate.sh
```

只允许使用当前 release 的 `deploy/migrate.sh` 和 migration 1-4。恢复旧 binary 时不运行旧 migrator；旧 binary 可以在保留 additive migration 4 schema 的前提下运行。migration 4 不做 down migration，不删除新 table/column/index/constraint，不删 `schema_migrations` version 4，不删除恢复库中的新数据。

PITR 使用最新完整基础备份创建新实例，并将目标时间设为事故前已确认 UTC 时间：

```conf
restore_command = 'restore-wal %f %p'
recovery_target_time = '2026-08-13 02:14:00+00'
recovery_target_action = 'promote'
```

`restore-wal` 由生产基础设施提供，必须从不可变 WAL 归档按文件名取回并校验。禁止在原实例上直接执行 PITR。恢复达到目标时间并暂停/提升后，先封锁应用流量，再执行验证。

## 恢复验证与切流

部署顺序固定为：使用独立 migration 管理连接运行 `deploy/migrate.sh`；成功后，application role 启动 server/admin。server/admin 只读校验 `schema_migrations` version/checksum，不执行 DDL。示例 compose 的 `migrate` one-shot job 承担该步骤，两个 activation 实例等待其成功退出。

1. 对比 `schema_migrations` 版本与 checksum；任何不一致立即停止。
2. 验证 ledger 为 1-4，`device_access_tokens` 和 `model_proxy_admissions` relation 存在，migration 4 checksum 与当前 release 一致。
3. 对比源备份清单中的表行数，重点检查 `activation_inventory`、`licenses`、`activation_attempts`、`device_access_tokens`、`new_api_bindings`、`model_proxy_admissions`、`audit_events`。不导出 `token_digest` 或 `api_key_envelope` 原值作为证据。
4. 抽查 `prepared`、`binding`、`active`、`reissued`；核对 `entitlement_revision`、license `revision`、replacement 关系、device token 状态与每设备唯一 active 约束、New API envelope/key version 成对性、admission lease/completion 时间和审计顺序。
5. 对 username、activation code digest、USB fingerprint、license `(device_id, revision)`、device token digest、每设备 active token 和 activation idempotency key 执行唯一约束负向验证；均预期 SQLSTATE `23505`。不得删除或放宽约束完成恢复。
6. 对解包后的逻辑 SQL 或受控查询输出扫描已知演练 secret marker；命中数必须为 `0`。扫描证据不得包含真实 secret 值。再扫描日志，确认无 activation code、device token、New API Key 或完整 prompt。
7. 使用应用角色连接，确认可读 `schema_migrations`且业务 DML 可用，同时 ledger 写入、`CREATE TABLE` 与 `CREATE SCHEMA` 均被拒绝。
8. 在恢复库的隔离应用实例上验证一个逾期 model proxy admission lease 会被下一次同 token admission 自动清理，不使用手工 SQL 修改 lease。
9. 记录验证人、时间、目标点、checksum、查询结果摘要和回滚点。双人批准后切换连接串；旧实例保持只读，直至观察期结束。

## 季度演练证据

每季度至少执行一次隔离恢复与 PITR 演练。证据路径：

```text
evidence/activation-db-recovery/YYYY-QN/
  manifest.md
  backup.sha256
  restore.log
  verification.log
  plaintext-secret-scan.txt
  approvals.md
```

`manifest.md` 必须记录 RPO/RTO 实测值、目标 UTC 时间、PostgreSQL 版本、备份/WAL 对象 ID、临时恢复实例 ID、异常与处置。日志先脱敏再归档；证据按安全审计保留策略保存，不提交到源码仓库。
