# 激活服务密钥轮换

## 适用范围

本手册覆盖生产激活服务的三类 managed KMS key，以及与 KMS envelope 分开管理的 New API Key。部署路径和回滚边界见 [激活与模型代理部署](./激活与模型代理部署.md)。三类 KMS key 必须使用不同 key resource、IAM 身份和审计策略，不得互用：

| 用途 | 允许操作 | 禁止操作 |
| --- | --- | --- |
| license signing key | 签发离线 license | token 加解密、release 签名 |
| token encryption key | token 加密、解密 | license/release 签名 |
| release signing key | release manifest 签名 | license 签名、token 加解密 |

生产配置只能保存 key resource 与固定 key version。私钥必须不可导出并留在 KMS；禁止在 env、配置文件、镜像、CI 变量或日志中放入 PEM、seed、base64 私钥。验证端只分发公钥。

## 轮换前检查

1. 建立变更单，记录操作者、三类 key 当前 resource/version、目标 version、开始时间和回滚负责人。
2. 检查近 24 小时 KMS timeout、permission denied 和审计缺口；存在未解释异常时停止轮换。
3. 确认每次 KMS 调用日志都记录 purpose、key version、KMS audit ID，不记录明文、密文、签名输入或私钥。
4. 备份当前配置版本、公钥 bundle 和部署制品摘要。验证旧版本仍为 enabled，且未安排销毁。
5. license、token、release 分三个变更窗口轮换。一次只切一个 purpose，禁止同时切换。

## 创建新 key version

1. 在对应 purpose 的现有 managed key resource 下创建新 version。需要算法变更时创建新 resource，并经过独立兼容性评审。
2. 保持私钥不可导出。授予运行时身份最小权限：license/release 仅 sign；token 仅 encrypt/decrypt。管理员身份不得由运行时使用。
3. 对新 version 执行非生产 canary：签名后用导出的公钥验证，或执行带 AAD 的加解密 round trip。
4. 保存 canary 的 key version、KMS audit ID 和验证结果。任何结果缺少 audit ID 都视为失败。

## 双公钥过渡

此步骤适用于 license signing key 和 release signing key；token encryption key 没有公钥 bundle，解密端应按密文记录的 key version 选择旧或新 version。

1. 从 KMS 导出新 version 的公钥，核对 fingerprint 与变更单。
2. 在验证端公钥 bundle 中加入新公钥，保留旧公钥。key ID/version 必须唯一，不能覆盖旧条目。
3. 先发布验证端。确认所有受支持客户端、离线验证器和 release 验证节点同时接受旧、新两把公钥。
4. 观察至少一个完整发布周期。验证失败率、未知 key version 和审计告警必须为零，才能切换签名端。

## 切换与观察

1. 将对应 `*_KMS_KEY_VERSION` 改为新固定 version；禁止使用 `latest`、`primary` 等可漂移 alias。
2. 灰度发布单个实例。执行 sign 或 encrypt/decrypt canary，核对响应 key version 等于目标 version，audit ID 非空。
3. 扩大发布。监控 KMS latency、timeout、permission denied、验证失败、解密失败和未知 version。
4. 保留旧 version 为 enabled：license 至少覆盖最长 license 有效期与撤销传播期；token 至少覆盖最长 token 有效期；release 至少覆盖所有仍受支持制品生命周期。
5. 分别完成 license、token、release 变更单。不得用某一 purpose 的成功替代另一 purpose 的验证。

## 回滚

1. 新 version 出现 timeout、permission denied、验证/解密失败、错误 key version 或审计 ID 缺失时，立即停止扩大发布。
2. 将对应 `*_KMS_KEY_VERSION` 恢复为旧固定 version 并重新部署；不得修改另外两类 purpose。
3. 签名 key 回滚时继续保留双公钥 bundle。token key 回滚时继续允许按 version 解密新旧密文，避免灰度期间产生的数据不可读。
4. 用旧 version 执行 canary，确认 key version 与 audit ID；恢复指标后记录事故时间线和所有相关 audit ID。
5. 不要在故障处置中销毁、禁用或删除新旧 version。

## 吊销与退役

1. 若私钥疑似泄露或被越权使用，先冻结签发/加密入口，撤销运行时 IAM 权限，并按 audit ID 确定影响范围。
2. 紧急切换到已预置的新 version。将受影响 license、token 或 release 加入各自撤销机制；不得跨 purpose 批量吊销。
3. 仅在旧 version 的全部制品、license 或 token 超过支持期，且审计确认无调用后，先 disable。观察期内保留可恢复能力。
4. disable 后仍无回退需求，按组织保留策略安排 destroy。启用延迟销毁和双人审批，记录销毁计划与最终审计 ID。
5. 签名 key 的旧公钥应保留到所有合法旧签名对象退役；公钥移除与私钥 version 销毁是两个独立审批动作。

## 验收记录

每次轮换至少保存：变更单号、purpose、resource、旧/新 version、公钥 fingerprint、部署摘要、canary 时间、KMS audit ID、指标截图、回滚验证、disable/destroy 审批。任何字段缺失，轮换不得关闭。

## New API Key 轮换

New API Key 是上游访问 secret，不是签名 key，也不是 `NEW_API_KMS_KEY_VERSION`。数据库只保存按 purpose/subject 绑定的加密 envelope。轮换不得解密、导出或打印旧 key。
本节的 `bash` 块必须整块由 root 的 Bash 执行，不得使用 `sh` 或逐行复制。每次录入新 key 都必须调用部署手册的完整 `mapping set` 块，不得摘录成省略 history 检查的短命令。该块中的 history 门禁必须原样保留：

```bash
test -n "${BASH_VERSION:-}"
[[ -o history ]]
: "${HISTFILE:=/root/.bash_history}"
test "$HISTFILE" = '/root/.bash_history'
test ! -L "$HISTFILE"
test -f "$HISTFILE"
test -w "$HISTFILE"
test "$(stat -c '%u:%a' "$HISTFILE")" = '0:600'
history -a "$HISTFILE"
scan_without_echoing_secret "$HISTFILE"
```

`history -a` 失败必须停止；扫描函数必须使用 `rg -l` 或 `rg -q`，不得输出匹配行，并分别将退出码 `0` 视为 secret 泄漏、`1` 视为 clean、`>1` 视为扫描失败。空/禁用 history、非允许路径、symlink、非 root `0600` 或不可写 history file 均 fail closed。成功和失败路径都由同一块的 cleanup 执行 `history -c`，清空当前 Bash 内存 history，并清理 New API Key 临时文件。

### 轮换前

1. 在 New API 创建新 key，保留旧 key 为 active。确认 New API 安全组仅允许 `121.41.89.103`，优先使用 mTLS；不关闭 TLS 校验或临时放开公网源。
2. 优先从 New API 官方离线 identity 工具取得可由输入 key 重算的 upstream key ID。没有经过审批的可靠 key-ID 解析能力时，使用独立 root `0600` HMAC key 计算 `hmac-sha256-v1` identity；禁止用随机 envelope digest、KMS version、portal 手抄标签或 `mapping show` 代替上游 key identity。
3. 安全管理员在操作前批准 root `0600` identity manifest。每个目标 inventory 必须有唯一 `rotationId/inventoryId/identityScheme/expectedIdentity/operationId/apiKeyVersion`，并覆盖 `new_api_bindings` 中全部 envelope/version 非空 inventory，不按 active/configured 状态过滤。expected identity 在安全工作站从同一新 key 预计算，不包含 key 明文。
4. 预创建外部 root `0600`、filesystem append-only `new-api-rotation-ledger.jsonl`。记录当前 `mapping show` 和审计摘要，确认旧 key 可在 New API 侧重新启用，但不从激活数据库取回旧 key 明文。无法建立可重算 identity、manifest 不完整或 ledger 不可追加时，本轮不得开始。

### 安全录入与 canary

1. 使用 [部署手册的完整 `mapping set` 块](./激活与模型代理部署.md#new-api-安全接入) 的 TTY writer；禁止任意 editor、swap/backup 文件、CLI key 参数或 shell key 变量。每次 mapping 前必须从实际输入 key 重算 identity，并与该 inventory/operation 的批准 manifest 精确匹配。
2. 先对 canary inventory 写入新 envelope。以 `mapping show --inventory-id "$INVENTORY_ID"` 确认 host、model/policy、批准 `apiKeyVersion`、status 和 updated time；完整块完成 history/journal/log/runtime-dir scan、key 文件与受控目录 cleanup 后，再确认 append-only ledger 已产生该 inventory 的唯一 `state="committed"` closure。stdout 和 audit 不得包含 key、HMAC key 或 envelope。
3. 用 canary device token 调用 `/model-api/v1/models` 和一条最小非流式 `/model-api/v1/chat/completions`。只记录 request ID、HTTP status、model 和用量摘要；同时检查两个实例、Caddy 和 New API 日志无 bearer、key 或完整 prompt。
4. canary 失败时立即停止扩大，保留旧 key active，用已审批的上一 key 安全源重新 `mapping set`。不在故障处理中记录任何 key 明文。

### 扩大与撤销旧 key

1. canary 通过后，按 manifest 中的 inventory 分批执行完整 `mapping set` 块；每批重新计算 input key identity、精确匹配批准 entry，并检查 401、429、5xx、latency 和 New API 用量。未更新 inventory 仍使用旧 key，因此旧 key 必须保持 active。
2. 全部 mapping 更新后，冻结 `mapping set`、binding status 和 New API 配置管理写，直到闭合验证与撤旧完成；无法冻结时不得撤旧。随后从 DB 读取全量 envelope/version 非空 mapping 集合，与批准 identity manifest、append-only closure ledger 做全量闭合，并验证每个 operation 的成功审计。定义 `$ROTATION_ID` 和 `$ROTATION_STARTED_AT`：

```bash
set -Eeuo pipefail
trap 'exit_code=$?; printf "key identity closure verification failed at line %s with status %s\\n" "$LINENO" "$exit_code" >&2; exit "$exit_code"' ERR
: "${ROTATION_ID:?ROTATION_ID is required}"
: "${ROTATION_STARTED_AT:?ROTATION_STARTED_AT is required}"
export PGSERVICEFILE=/run/secrets/uclaw-activation/pg_service.conf
export PGPASSFILE=/run/secrets/uclaw-activation/pgpass
KEY_IDENTITY_MANIFEST=/etc/uclaw-activation/new-api-key-identities.json
ROTATION_LEDGER=/var/lib/uclaw-activation/new-api-rotation-ledger.jsonl
CLOSURE_VERIFY_DIR="$(mktemp -d /run/secrets/uclaw-activation/rotation-closure.XXXXXX)"
DB_ACTIVE_INVENTORIES_FILE="$CLOSURE_VERIFY_DIR/db-active-inventories"
MANIFEST_INVENTORIES_FILE="$CLOSURE_VERIFY_DIR/manifest-inventories"
cleanup_closure_verify() {
  local exit_code=$?
  trap - EXIT
  rm -rf -- "$CLOSURE_VERIFY_DIR" || exit_code=1
  unset PGSERVICEFILE PGPASSFILE
  exit "$exit_code"
}
trap cleanup_closure_verify EXIT
for secret_file in "$PGSERVICEFILE" "$PGPASSFILE" "$KEY_IDENTITY_MANIFEST" "$ROTATION_LEDGER"; do
  test -f "$secret_file"
  test ! -L "$secret_file"
  test "$(stat -c '%u:%a' "$secret_file")" = '0:600'
done
lsattr -d "$ROTATION_LEDGER" | awk '{print $1}' | rg -q 'a'
[[ "$ROTATION_ID" =~ ^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$ ]]

psql --dbname='service=uclaw_migration' -X -At --command "
  SELECT inventory_id::text
  FROM new_api_bindings
  WHERE api_key_envelope IS NOT NULL
    AND api_key_version IS NOT NULL
  ORDER BY inventory_id
" | LC_ALL=C sort > "$DB_ACTIVE_INVENTORIES_FILE"
jq -r --arg rotation "$ROTATION_ID" \
  '.entries[] | select(.rotationId == $rotation) | .inventoryId' \
  "$KEY_IDENTITY_MANIFEST" | LC_ALL=C sort > "$MANIFEST_INVENTORIES_FILE"
DB_ACTIVE_COUNT="$(wc -l < "$DB_ACTIVE_INVENTORIES_FILE")"
MANIFEST_COUNT="$(wc -l < "$MANIFEST_INVENTORIES_FILE")"
test "$DB_ACTIVE_COUNT" -gt 0
test "$DB_ACTIVE_COUNT" = "$MANIFEST_COUNT"
test "$(LC_ALL=C uniq -d "$DB_ACTIVE_INVENTORIES_FILE" | wc -l)" = '0'
test "$(LC_ALL=C uniq -d "$MANIFEST_INVENTORIES_FILE" | wc -l)" = '0'
cmp --silent "$DB_ACTIVE_INVENTORIES_FILE" "$MANIFEST_INVENTORIES_FILE"

jq -e --slurpfile closed "$ROTATION_LEDGER" --arg rotation "$ROTATION_ID" '
  [.entries[] | select(.rotationId == $rotation)] as $expected
  | ([$closed[] | select(.rotationId == $rotation and .state == "committed")]) as $actual
  | ($expected | length) > 0
    and ($actual | length) == ($expected | length)
    and all($expected[] as $entry;
      ([$actual[] | select(
        .inventoryId == $entry.inventoryId
        and .keyIdentity == $entry.expectedIdentity
        and .operationId == $entry.operationId
        and .apiKeyVersion == $entry.apiKeyVersion
      )] | length) == 1
    )
' "$KEY_IDENTITY_MANIFEST" >/dev/null

mapfile -t expected_inventory_ids < "$MANIFEST_INVENTORIES_FILE"
for inventory_id in "${expected_inventory_ids[@]}"; do
  [[ "$inventory_id" =~ ^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$ ]]
  audit_found="$(psql --dbname='service=uclaw_migration' -X -At \
    --set=inventory_id="$inventory_id" --set=rotation_started_at="$ROTATION_STARTED_AT" \
    --command "SELECT EXISTS(SELECT 1 FROM audit_events WHERE inventory_id=:'inventory_id'::uuid AND action='new-api.mapping.set' AND outcome='succeeded' AND created_at>=:'rotation_started_at'::timestamptz)")"
  test "$audit_found" = 't'
done
```

`new_api_bindings` 的真实 schema 没有 `deleted_at`；`status='disabled'/'revoked'` 只是软删除/停用状态，不能证明旧 upstream key 已不可恢复或不再依赖。因此撤旧 source of truth 是 DB 中全部 `api_key_envelope IS NOT NULL AND api_key_version IS NOT NULL` mapping，不作 status/balance 过滤。DB 集合与 manifest 必须分别排序、非空、无重复、数量相同且逐字节相等。任一 DB mapping 未获批准、manifest 多列/漏列、批准 inventory 缺 committed closure、出现重复/额外 committed closure、identity/operation/api key version 不等或缺成功审计时，停止撤销旧 key。provisional/无 state closure 不计入最终闭合。envelope digest 只证明随机密文变化，不能证明写入了哪把上游 key。验证后再观察至少 30 分钟。
3. 只有 DB envelope/version 非空 mapping 全量集合、identity manifest 与 committed closure 三方完全闭合，全部 canary/批次验证通过且回滚负责人批准后，才在 New API 撤销旧 key。无法建立 identity 或闭合时必须保留旧 key active，不得宣称轮换完成。撤销后再做一次 models/chat canary，确认旧 key 不再有调用。
4. 每批 key 临时目录必须保留到完整块完成 `history -a`、history/journal/log/runtime-dir 扫描和 `history -c`，再由 cleanup 删除。任何 history 禁用/不可写、扫描未执行、`rg` 返回 `>1`、无权读取日志、目录残留或 cleanup 失败时，轮换不得完成。

New API Key 轮换记录包含变更单、rotation ID、canary inventory ID、每个 inventory 的 expected identity/operation ID/api key version 闭合结论、mapping 批次、request ID、观察结果、New API 旧 key 撤销审计 ID 和 secret scan 结果。keyed-HMAC identity 是非秘密比对值，但 HMAC key 与 New API Key 都不得进入记录、argv 或日志。
