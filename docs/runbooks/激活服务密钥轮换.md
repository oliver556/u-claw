# 激活服务密钥轮换

## 适用范围

本手册覆盖生产激活服务的三类 managed KMS key，以及与 KMS envelope 分开管理的 New API Key。部署路径和回滚边界见 [激活与模型代理部署](./激活与模型代理部署.md)。三类 KMS key 必须使用不同 key resource、IAM 身份和审计策略，不得互用：

| 用途 | 允许操作 | 禁止操作 |
| --- | --- | --- |
| license signing key | 签发离线 license | token 加解密、release 签名 |
| token encryption key | token 加密、解密 | license/release 签名 |
| release signing key | release manifest 签名 | license 签名、token 加解密 |

生产配置只能保存 key resource 与固定 key version。私钥必须不可导出并留在 KMS；禁止在 env、配置文件、镜像、CI 变量或日志中放入 PEM、seed、base64 私钥。验证端只分发公钥。

## 轮换前检查

1. 建立变更单，记录操作者、三类 key 当前 resource/version、目标 version、开始时间和回滚负责人。
2. 检查近 24 小时 KMS timeout、permission denied 和审计缺口；存在未解释异常时停止轮换。
3. 确认每次 KMS 调用日志都记录 purpose、key version、KMS audit ID，不记录明文、密文、签名输入或私钥。
4. 备份当前配置版本、公钥 bundle 和部署制品摘要。验证旧版本仍为 enabled，且未安排销毁。
5. license、token、release 分三个变更窗口轮换。一次只切一个 purpose，禁止同时切换。

## 创建新 key version

1. 在对应 purpose 的现有 managed key resource 下创建新 version。需要算法变更时创建新 resource，并经过独立兼容性评审。
2. 保持私钥不可导出。授予运行时身份最小权限：license/release 仅 sign；token 仅 encrypt/decrypt。管理员身份不得由运行时使用。
3. 对新 version 执行非生产 canary：签名后用导出的公钥验证，或执行带 AAD 的加解密 round trip。
4. 保存 canary 的 key version、KMS audit ID 和验证结果。任何结果缺少 audit ID 都视为失败。

## 双公钥过渡

此步骤适用于 license signing key 和 release signing key；token encryption key 没有公钥 bundle，解密端应按密文记录的 key version 选择旧或新 version。

1. 从 KMS 导出新 version 的公钥，核对 fingerprint 与变更单。
2. 在验证端公钥 bundle 中加入新公钥，保留旧公钥。key ID/version 必须唯一，不能覆盖旧条目。
3. 先发布验证端。确认所有受支持客户端、离线验证器和 release 验证节点同时接受旧、新两把公钥。
4. 观察至少一个完整发布周期。验证失败率、未知 key version 和审计告警必须为零，才能切换签名端。

## 切换与观察

1. 将对应 `*_KMS_KEY_VERSION` 改为新固定 version；禁止使用 `latest`、`primary` 等可漂移 alias。
2. 灰度发布单个实例。执行 sign 或 encrypt/decrypt canary，核对响应 key version 等于目标 version，audit ID 非空。
3. 扩大发布。监控 KMS latency、timeout、permission denied、验证失败、解密失败和未知 version。
4. 保留旧 version 为 enabled：license 至少覆盖最长 license 有效期与撤销传播期；token 至少覆盖最长 token 有效期；release 至少覆盖所有仍受支持制品生命周期。
5. 分别完成 license、token、release 变更单。不得用某一 purpose 的成功替代另一 purpose 的验证。

## 回滚

1. 新 version 出现 timeout、permission denied、验证/解密失败、错误 key version 或审计 ID 缺失时，立即停止扩大发布。
2. 将对应 `*_KMS_KEY_VERSION` 恢复为旧固定 version 并重新部署；不得修改另外两类 purpose。
3. 签名 key 回滚时继续保留双公钥 bundle。token key 回滚时继续允许按 version 解密新旧密文，避免灰度期间产生的数据不可读。
4. 用旧 version 执行 canary，确认 key version 与 audit ID；恢复指标后记录事故时间线和所有相关 audit ID。
5. 不要在故障处置中销毁、禁用或删除新旧 version。

## 吊销与退役

1. 若私钥疑似泄露或被越权使用，先冻结签发/加密入口，撤销运行时 IAM 权限，并按 audit ID 确定影响范围。
2. 紧急切换到已预置的新 version。将受影响 license、token 或 release 加入各自撤销机制；不得跨 purpose 批量吊销。
3. 仅在旧 version 的全部制品、license 或 token 超过支持期，且审计确认无调用后，先 disable。观察期内保留可恢复能力。
4. disable 后仍无回退需求，按组织保留策略安排 destroy。启用延迟销毁和双人审批，记录销毁计划与最终审计 ID。
5. 签名 key 的旧公钥应保留到所有合法旧签名对象退役；公钥移除与私钥 version 销毁是两个独立审批动作。

## 验收记录

每次轮换至少保存：变更单号、purpose、resource、旧/新 version、公钥 fingerprint、部署摘要、canary 时间、KMS audit ID、指标截图、回滚验证、disable/destroy 审批。任何字段缺失，轮换不得关闭。

## New API Key 轮换

New API Key 是上游访问 secret，不是签名 key，也不是 `NEW_API_KMS_KEY_VERSION`。数据库只保存按 purpose/subject 绑定的加密 envelope。轮换不得解密、导出或打印旧 key。

### 轮换前

1. 在 New API 创建新 key，保留旧 key 为 active。确认 New API 安全组仅允许 `121.41.89.103`，优先使用 mTLS；不关闭 TLS 校验或临时放开公网源。
2. 选择专用低额度 canary 库存/设备，记录 inventory ID、允许模型、变更 request ID 和预期指纹；不记录 key、device token 或 prompt。
3. 备份当前脱敏 mapping status 和审计记录。确认旧 key 可在 New API 侧重新启用，但不从激活数据库尝试取回其明文。

### 安全录入与 canary

1. 在 `/run/secrets/uclaw-activation` 创建 mode `0600` 临时文件。用交互编辑器写入新 key；禁止放在 CLI 参数、shell 变量、clipboard 历史或 pipeline。
2. 先对 canary inventory 执行 `uclaw-activation-admin mapping set --key-file "$NEW_API_KEY_FILE"` 写入新 envelope。以 `mapping show` 确认新 fingerprint/status；stdout 和 audit 不得包含 key 或 envelope。
3. 用 canary device token 调用 `/model-api/v1/models` 和一条最小非流式 `/model-api/v1/chat/completions`。只记录 request ID、HTTP status、model 和用量摘要；同时检查两个实例、Caddy 和 New API 日志无 bearer、key 或完整 prompt。
4. canary 失败时立即停止扩大，保留旧 key active，用已审批的上一 key 安全源重新 `mapping set`。不在故障处理中记录任何 key 明文。

### 扩大与撤销旧 key

1. canary 通过后，按 inventory 分批 `mapping set` 新 envelope；每批检查 401、429、5xx、latency 和 New API 用量。未更新 inventory 仍使用旧 key，因此旧 key 必须保持 active。
2. 全部 mapping 更新后，通过脱敏 fingerprint 盘点确认无旧 envelope 引用，再观察至少 30 分钟。
3. 只有全部 canary/批次验证通过、无旧引用且回滚负责人批准后，才在 New API 撤销旧 key。撤销后再做一次 models/chat canary，确认旧 key 不再有调用。
4. 立即安全删除临时文件，执行 shell history、systemd journal 和应用日志泄漏扫描。任何扫描未执行或无权读取日志时，轮换不得记为完成。

New API Key 轮换记录包含变更单、canary inventory ID、旧/新脱敏 fingerprint、mapping 批次、request ID、观察结果、New API 旧 key 撤销审计 ID 和 secret scan 结果。不保存 key 明文。
