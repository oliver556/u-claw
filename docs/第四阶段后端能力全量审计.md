# U-Claw 第四阶段后端能力全量审计

> 审计日期：2026-08-11
> 原项目基线：`portable/`、归档 `u-claw-app/`、锁定 `openclaw@2026.7.1-2`
> 新客户端基线：`codex/integration-p2-t10-local@9bcd854`
> 审计方式：静态入口、HTTP API、Gateway RPC、CLI、React、preload、IPC、Adapter 和生产装配对照；本次不修改业务代码，不使用真实外部凭据。

## 1. 审计边界

本文中“全量”指：

1. 当前仓库 `portable/` 对用户暴露的脚本、菜单、Config Server 和归档 Electron 能力。
2. 锁定 OpenClaw `2026.7.1-2` 核心 Gateway 公开方法域和 Dashboard 已使用的用户能力。
3. 新客户端当前 React UI 与生产调用链。

不包括未安装的未来第三方插件动态 RPC。运行时仍须以 `hello-ok.features.methods/events` 做二次能力发现。

## 2. 总结论

### 2.1 生产运行态

当前新客户端不存在仓内正式 `createDesktopMainOptions()` 实现。`product/desktop/src/entry.ts` 要求 `UCLAW_DESKTOP_WIRING_MODULE`，但生产代码没有提供该模块。

因此：

- 当前可见浏览器版使用 `MockUClawClient`。
- 所有依赖 Electron/OpenClaw 的页面在当前可运行形态中都不能计为“真实接通”。
- 这是一个横向生产装配缺口，不等于每个页面都需要重写。

### 2.2 OpenClaw 核心能力域

锁定版本核心 RPC 按 31 个能力域统计：

| 代码级状态 | 数量 | 说明 |
| --- | ---: | --- |
| 基础调用链已写 | 3 | Chat、单次 Exec 审批、单次 Plugin 审批 |
| 部分实现 | 13 | 有 UI/契约/局部服务，但未覆盖该域真实全能力 |
| 用户能力无新 UI | 11 | Agent、Cron、Usage、Node、Talk/TTS 等 |
| 内部能力/不应直接迁移 | 4 | attach 内部控制、secret helper、Dashboard 内部预览、crestodian 内部域 |
| 总计 | 31 | 不含动态第三方插件 RPC |

从真实生产运行态看，上述 27 个用户相关域当前都被正式 wiring 缺口阻断；“基础调用链已写”只是代码级结论。

## 5. 必须先补入第四阶段的缺口

### 5.1 无需产品决策，直接接线

1. 正式 Electron/OpenClaw wiring：Gateway WebSocket、`OpenClawClient`、附件、健康探测、生产 executor、领域服务。
2. 基本会话、消息、工具和审批真实链路。
3. 文件、记忆、备份、恢复、空间、日志、诊断和更新的生产服务注入。
4. Provider Store 与 OpenClaw 配置/实际模型请求统一。
5. Skill 内置目录、OpenClaw 可用状态和 SkillHub 安装读回统一。
6. Telegram、MCP 和 Plugin 已有代码链的真实 runtime 收口。
7. QQ、飞书、企微、个人微信的 OpenClaw/CLI/旧可用后端适配。
8. 活动中心改用真实 `tasks.*`/事件，成果改用 `artifacts.*`。

### 5.2 需要产品决策的原 OpenClaw 用户能力

以下能力原 Dashboard/Gateway 存在，但当前三阶段需求和新 UI 没有完整入口：

- Agent 列表、身份、创建/编辑/删除、Agent 文件。
- 会话 reset、compact、branch、restore、steer。
- 定时任务 Cron 和历史运行。
- 真实后台 Task 取消与详情。
- 工具/命令目录、有效工具投影和审批策略。
- OpenClaw 用量、成本和时序。
- 设备配对、Node 管理与 token 轮换/撤销。
- Environment/worktree 管理。
- 原生 Terminal。
- Talk/TTS、Voice Wake、Push。
- Discord 渠道。
- Skill curator/proposals 和 Plugin UI descriptors/session actions。

若产品目标是“原项目所有用户可用后端能力全部进入新 UI”，上述条目不能继续只留在高级控制台；必须追加 UI、shared 契约、IPC 和 Adapter Task，或逐项获得明确的“不迁移”批准。

## 6. 对第四阶段设计的修正结论

现有第四阶段设计需要增加 `P4-T00`：

```text
P4-T00 原后端能力冻结与迁移决策
-> 本审计 31 个 OpenClaw 域 + portable 能力表
-> 每项标记：接入新 UI / 内部使用 / 明确不迁移
-> 用户可用能力不允许默认遗漏
```

未完成 `P4-T00` 的迁移决策前，不应宣称第四阶段矩阵已覆盖原项目全部用户能力。

## 7. 主要代码证据

- `portable/config-server/server.js`：Config、Update、Local Model、个人微信 HTTP API。
- `portable/Windows-Menu.bat` / `portable/Mac-Menu.command`：15 类原菜单能力。
- `docs/OpenClaw协议审计.md`：锁定版本核心 RPC 域与 Dashboard 使用面。
- `product/desktop/src/entry.ts`：强制要求仓内尚缺的生产 wiring module。
- `product/frontend/src/app/App.tsx`：无 preload bridge 时使用 `MockUClawClient`。
- `product/adapter/src/openclaw-client.ts`：Chat/Session/Model/Telegram/MCP 映射及 Skill、File、日志等 `Unsupported` 边界。
- `product/desktop/src/main.ts`：各领域服务组装槽位已有，但依赖外部正式 options/executors/runtime。
- `product/frontend/src/features/data/DataManager.tsx`：无 Electron bridge 时固定只读和空列表。
- `product/adapter/fixtures/openclaw-2026.7.1-2/channels.json`：当前锁定 fixture 只证明 Telegram，明确将 QQ/飞书/企微标为 unavailable。
