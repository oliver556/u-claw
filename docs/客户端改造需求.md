## 1. 改造背景

当前仓库包含两条历史路线：

- `portable/`：当前持续维护的 U 盘便携版，负责 Node.js/OpenClaw runtime、U 盘数据路径、配置中心、启动脚本和运行辅助能力。
- `u-claw-app/`：2026-06-20 归档的 Electron 桌面版，能启动 OpenClaw gateway 并用 Electron 窗口加载 Dashboard，但已停止发布和功能同步。

当前客户体验仍有三个核心问题：

1. 旧 Electron 客户端与当前 `portable/` 的功能、配置和 OpenClaw 版本已脱节。
2. 原客户端只是将 OpenClaw Dashboard 放入 Electron 窗口，视觉和交互仍是网页控制台。
3. 大型 portable EXE 每次自解压、或从 U 盘直接运行大量散文件，都无法提供合格启动速度。

## 2. 现状证据

2026-08-07 对当前仓库的 Git 历史和源码核对结果：

- `u-claw-app/src/main.js` 最后实质更新时间为 2026-06-20，即 Electron 桌面版归档时。
- 归档后 `portable/` 继续接收了 12 次相关更新。
- 归档后新增或改进的能力包括：本地模型、微信登录、内网模型和代理绕行、OpenClaw Doctor、更新检查、端口处理和启动首屏。
- 当前 `portable/config-server/public/index.html` 相比归档 app 中的 `resources/Config.html` 有大量新功能差异。
- `u-claw-app/package.json` 当前声明 `"openclaw": "latest"`，但 lockfile 中安装产物仍是 OpenClaw `2026.3.8`，存在版本不可重现问题。
- 当前 `portable/` 已跟随更新的 OpenClaw 发行版，不能用归档 app 的依赖状态代替。

因此，客户端改造不能在“旧 app”和“新网页”之间二选一，必须按职责重组。

## 3. 已确认技术决策

### 3.1 代码基线

- 使用当前 `portable/` 和锁定版本 OpenClaw 作为后端能力来源。
- `u-claw-app/` 只作为 Electron 进程启动、端口管理、gateway 健康检查、preload/IPC 和窗口生命周期的参考。
- 不在归档 `u-claw-app/` 上直接继续堆叠正式产品功能。
- 不将 OpenClaw Dashboard 原样套入 Electron 后视为客户端改造完成。

### 3.2 桌面容器

- 第一版使用 Electron。
- Electron runtime 从本机 SSD 版本缓存运行，不从 U 盘直接启动。
- 不使用 electron-builder `portable` 大型单 EXE 每次自解压模式。
- Tauri 不作为第一版技术基线；待 Electron 完成后，只在实测常驻内存或启动性能不达标时重新评估。

### 3.3 前端技术

- 新建 React + Vite 前端。
- 自建 U-Claw 客户端信息架构、样式和交互。
- NextChat 只作为会话导航、主对话区、输入框、Markdown 和附件交互的产品参考，不直接 fork 为 U-Claw 的业务基础。
- 前端不直接依赖 OpenClaw Dashboard DOM、CSS 类名和内部页面结构。

### 3.4 OpenClaw 适配层

- 在自建前端和 OpenClaw gateway 之间增加 U-Claw Adapter。
- Adapter 负责吸收 OpenClaw API、WebSocket 消息、字段和版本差异。
- React 前端只调用 U-Claw 定义的稳定契约。
- OpenClaw Dashboard 保留为“高级控制台”，为新前端尚未覆盖的功能提供兜底。

## 4. 目标架构

```text
U 盘 U-Claw.exe
  -> 验证 U 盘、版本和 runtime.pkg
  -> 准备/复用本机 SSD runtime 缓存
  -> 启动 Electron
       -> 加载 React + Vite 前端
       -> 启动 U-Claw Adapter
       -> 启动 Node.js + OpenClaw gateway
            -> 读写 U 盘 .uclaw/data
```

职责边界：

| 组件 | 职责 | 禁止事项 |
| --- | --- | --- |
| Launcher | U 盘校验、runtime 缓存、启动和监督 | 不承载完整 Electron/OpenClaw 散文件 |
| Electron | 窗口、托盘、preload/IPC、子进程生命周期 | 不将 Node API 直接暴露给渲染进程 |
| React | 产品 UI 和用户交互 | 不直接操作 OpenClaw Dashboard DOM |
| Adapter | 统一 OpenClaw 协议、版本兼容和错误模型 | 不承载视觉组件 |
| OpenClaw | Agent、session、模型、技能、工具和渠道 | 不决定 U-Claw 产品 UI |
| U 盘数据层 | 配置、API Key、记忆、会话、工作数据和授权 | 不将唯一副本移入本机缓存 |

## 5. 仓库目录规划

自研产品代码统一放在仓库根目录的 `product/`，避免与上游目录混合。

```text
u-claw/
├── portable/                 上游当前便携版，尽量保持原样
├── u-claw-app/               上游归档客户端，只参考
├── install/                  上游安装工具
├── bootable/                 上游启动盘
├── product/
│   ├── launcher/             轻量 U-Claw.exe 启动器
│   ├── desktop/              Electron 主进程、preload、托盘
│   ├── frontend/             React + Vite 客户端界面
│   ├── adapter/              OpenClaw 协议适配层
│   ├── shared/               共享类型、错误码和状态
│   ├── packaging/            runtime.pkg 与发行包构建
│   └── tests/                集成与 Windows 端到端测试
├── docs/                     中文产品、技术和决策文档
└── outputs/                  本地构建产物，不提交 Git
```

目录约束：

- 新客户端 UI 不放入 `portable/`。
- 正式产品代码不继续写入 `u-claw-app/`。
- 只有当上游本身存在通用缺陷时，才直接修改 `portable/`；该改动应独立提交，便于向上游回馈或在同步时审查。
- `.superpowers/`、`outputs/`、runtime 缓存和 `node_modules/` 不进入版本库。
- `docs/` 和 `product/` 属于我们的产品代码，需正常版本管理。

## 6. 全量功能追踪矩阵

### 6.1 使用规则

本矩阵是客户端改造的唯一功能统计入口。阶段清单、开发任务和验收结果都必须引用功能编号，不能另建一份口径不同的清单。

状态定义：

| 状态 | 含义 |
| --- | --- |
| `未开始` | 尚未进入协议审计或开发 |
| `审计中` | 正在确认现有实现、OpenClaw 协议或数据路径 |
| `开发中` | 已有负责人和代码变更，尚未完成 |
| `待验收` | 开发完成，等待自动化或真实 Windows 环境验收 |
| `已完成` | 已满足该行验收标准，并留下测试或验收记录 |
| `阻塞` | 存在明确外部依赖，必须记录阻塞原因 |
| `待确认` | 是否迁移或具体产品形态尚未确认，不计为完成 |
| `不迁移` | 已明确不进入新客户端，必须在该行写明替代方案或原因 |

进度统计只看“新客户端状态”。现有脚本、配置网页或 OpenClaw Dashboard 中已经可用，不代表新客户端已经完成。

阶段定义：

- `基础`：公共契约、数据安全和构建基础，其他功能依赖它。
- `第一阶段`：形成可长期使用的桌面客户端和完整对话主链。
- `第二阶段`：将现有管理能力和 OpenClaw 能力全部原生接入新 UI。
- `第三阶段`：完成面向正式销售的设备授权、制盘开户、隐藏内置模型服务和服务端运营控制。
- `第四阶段`：将前三阶段 UI 与真实 OpenClaw 及现有后端能力全量接线。
- `第五阶段`：建设可一键添加和直接对话的助手库，封装 OpenClaw Agent 配置、记忆和 Skill 组合。
- `后续`：不阻塞第三阶段完成的其他产品形态或增强能力。

阶段明细入口：

- [第一阶段完整需求](./第一阶段需求.md)：桌面客户端、对话主链、U 盘数据边界和 Windows 便携运行。

模型源产品规则：

- `builtin` 只作为隐式默认状态存在，不在模型设置中展示服务地址、用户名、Token 或编辑入口。
- 原项目已支持的 DeepSeek、Kimi、Qwen、GLM、MiniMax、豆包等国产 Provider 配置必须保留。
- OpenAI-compatible 纯自定义配置必须保留，允许用户填写 Base URL、API Key 和模型名。
- 国产模型与纯自定义模型均已配置时，以用户最后一次明确启用的来源为准，不能按“哪个 Key 非空”推断。
- 用户启用外部来源后，模型推理请求不得经过或消耗 U-Claw 内置服务；启动授权校验仍独立执行。
- 外部服务认证失败、余额不足、限流或网络异常时，直接报告当前来源错误，不得静默回退到内置服务。
- 用户提供的外部 API Key 只保存在 U 盘本地数据中，不上传 U-Claw 自有服务器。

SkillHub 接入边界：

- 不建设 U-Claw 云端安装服务；Electron Node 本地后端直连 SkillHub.cn，renderer 不直连市场 API，也不直接写文件系统。
- 列表和搜索固定使用免费条件 `pricing_type:!paid`；安装前后端必须再次检查详情元数据，拒绝 `pricing_type:paid`，防止绕过 UI 安装。
- 免费 Skill 可以需要第三方 API Key；UI 必须单独标识，不得将“免费”表述为“无配置即用”。
- 安装目录由 desktop 根据当前 U 盘运行时状态解析，不接受 renderer 传入任意绝对路径，不写 `node_modules/openclaw/skills`。
- 安装、更新和卸载同属技能生命周期，第二阶段一并交付；更新需保留旧版回滚点，卸载需区分市场安装与用户自建目录。
- SkillHub 登录、发布、付费 Skill、专家包和 Soul 不纳入此技能子包。MCP 不属于 Skill，继续作为 `CAP-006` 独立能力实现。

| SVC-001 | New API 设备账户准备 | 自动制盘 saga 已有本地代码，第一版改用人工运营 | 发货前为每套产品准备独立 New API 用户或设备 Token；余额、模型权限和限速由运营人员人工设置 | 第三阶段 | 待生产落实 | 余额配置完成后才允许正常交付；禁止多客户共用 Token；激活、撤销和换盘保持映射一致 |
| SVC-002 | 内置服务运营控制 | localhost 控制底座已实现，真实管理面未接 | 通过 New API 管理每个设备的余额、限速、模型权限和禁用；第一版允许人工操作 | 第三阶段 | 待生产落实 | 可按设备或 New API 用户调整并读回；上游 Key 不进入 U 盘；单设备泄露只影响该设备 |

第三阶段授权与复制边界：

- New API 用户名使用随机唯一、不含客户敏感信息的标识，并永久记录 `device_id -> new_api_user_id -> username -> token_id` 映射；用户名不是密钥。
- U 盘保存本设备专属 New API Token，不保存企业商家的上游 Key。上游 Key 仅由自有 New API 服务端持有。
- 隐藏独立启动密钥不得复用为 New API Token；两者泄露、轮换和撤销范围必须隔离。
- 普通格式化会清空程序、授权和用户数据，属于客户自行承担的数据清除行为。
- 本阶段目标是防止只复制可见 `U-Claw.exe` 后直接启动，不承诺抵抗完整磁盘镜像、逆向或硬件级复制。
- 完整复制得到同一授权时，服务端仍将其视为同一设备账户，共享同一额度、限速和封禁状态，不自动创建新账户。

### 6.11 视觉要求

- 客户端应表现为长时使用的工作工具，不是官网、控制台网页或营销页。

## 7. Adapter 稳定契约

第一阶段前端不应认识 OpenClaw 内部路由或消息结构，而是调用类似以下能力：

```ts
interface UClawClient {
  getGatewayStatus(): Promise<GatewayStatus>;
  listSessions(): Promise<SessionSummary[]>;
  createSession(input: CreateSessionInput): Promise<Session>;
  renameSession(id: string, title: string): Promise<void>;
  deleteSession(id: string): Promise<void>;
  getMessages(sessionId: string): Promise<Message[]>;
  sendMessage(input: SendMessageInput): AsyncIterable<MessageEvent>;
  stopMessage(sessionId: string): Promise<void>;
  listModels(): Promise<ModelSummary[]>;
  selectModel(sessionId: string, modelId: string): Promise<void>;
  listSkills(): Promise<SkillSummary[]>;
  listTools(): Promise<ToolSummary[]>;
  openAdvancedConsole(): Promise<void>;
}
```

此接口是需求边界示例，实际签名必须在完成 OpenClaw gateway 协议审计后确定。

Adapter 必须统一处理：

- OpenClaw 连接、认证和重连。
- 流式事件到 U-Claw 消息模型的转换。
- OpenClaw 版本能力检测。
- 新旧字段兼容和默认值。
- gateway 错误到 U-Claw 用户错误的转换。
- 日志脱敏，不暴露 API Key、token 或对话正文。

## 8. Git 与上游同步方案

### 8.1 本地仓库

只保留一个本地 Git 仓库，不在当前仓库内嵌套第二个仓库，也不需要并排长期维护两份工作目录。

当前本地仓库的 `origin` 是我们的 fork：

```text
origin = git@github.com:oliver556/u-claw.git
```

需增加原作者仓库为 `upstream`：

```text
upstream = git@github.com:dongsheng123132/u-claw.git
```

### 8.2 分支规划

- `main`：尽量跟随 `upstream/main`，用于接收上游更新。
- `product`：我们的客户端产品开发分支，包含 `product/` 和正式 `docs/`。
- 上游同步时可使用临时 `upstream-sync-*` 分支完成审查，同步完成后删除。

更新方向：

```text
upstream/main
  -> origin/main
  -> product
```

### 8.3 上游同步流程

1. 拉取 `upstream/main`，检查发行日志和 `portable/` 差异。
2. 将上游更新合并到我们的 `main`。
3. 在 `main` 上验证上游 portable 基线没有被我们的产品代码破坏。
4. 将更新合并到 `product`。
5. 运行 OpenClaw 协议契约测试、Adapter 测试、Electron 集成测试和 Windows 端到端测试。
6. 通过后生成新 runtime.pkg，再发布产品版本。

## 9. OpenClaw 升级方案

- 产品构建不得使用 `openclaw: latest`。
- 每个 U-Claw 发行版必须记录精确 OpenClaw 版本和 runtime 哈希。
- OpenClaw 新版本不直接进入正式 runtime，先进入兼容性验证。
- 如果只有后端修复且协议不变，更新 OpenClaw/runtime 即可，React 前端不应修改。
- 如果 API 或 WebSocket 协议变化，优先只修改 Adapter 和契约测试。
- 如果 OpenClaw 增加新功能，新功能可先通过“高级控制台”使用，再评估是否加入 U-Claw 原生页面。

该边界保证上游更新时，不需要重新合并或重写整套 U-Claw 前端。

## 10. 构建与发行产物

仓库代码经构建后，在本地 `outputs/windows-x64/` 生成：

```text
outputs/windows-x64/
├── U-Claw.exe
└── .uclaw/
    ├── runtime.pkg
    ├── version.json
    ├── data/
    └── license/
```

发行要求：

- `U-Claw.exe` 是轻量启动器，不是每次解压完整 Electron 的大型 portable EXE。
- `runtime.pkg` 包含锁定的 Electron、Node.js、OpenClaw、Adapter 和 React 前端产物。
- 用户数据只写入 `.uclaw/data/`。
- 正式 Windows 客户盘优先使用 NTFS。
- 发行时通过“格式化 + 复制发行文件”制作 U 盘，不采用烧录模式。

## 14. 第一阶段验收条件

### 14.1 架构

- 正式产品代码集中于 `product/`。
- `portable/` 可继续接收上游更新，不需要同时合并自建 React UI。
- 新前端不依赖 OpenClaw Dashboard DOM 注入。
- OpenClaw 协议变化主要由 Adapter 吸收。

### 14.2 体验

- 双击后及时显示客户端启动状态。
- 客户端不显示终端和浏览器地址栏。
- 会话列表、主对话区和输入区交互稳定。
- 流式输出、中止生成、工具状态和错误恢复可用。
- 未被新前端覆盖的 OpenClaw 功能可从高级控制台进入。

### 14.3 更新

- 可从 `upstream/main` 获取 U-Claw 上游更新。
- 可在不替换 React 前端代码的情况下升级兼容的 OpenClaw 版本。
- 协议不兼容时，契约测试能在发布前拦截。
- 更新 runtime 不破坏 `.uclaw/data/` 中用户数据。

### 14.4 Windows 发行

- Windows 10/11 x64 普通用户权限可启动。
- 无本机 Node.js 时仍可运行。
- 首启在本机 SSD 创建版本缓存，二启不再全量解压。
- 退出后不遗留 Electron、Node.js 或 OpenClaw 孤立进程。
- 配置、API Key、session、记忆和工作数据可验证地保存在 U 盘。
