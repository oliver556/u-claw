# U-Claw 第二阶段需求

> 文档状态：38 项功能代码已本地集成，严格验收进行中  
> 记录日期：2026-08-10  
> 发行前置：基础项与第一阶段全部完成并通过 Windows 验收；独立功能包可提前开发  
> 权威来源：`docs/客户端改造需求.md` 中标记为“第二阶段”的 39 项功能
> 验收边界：[《第二阶段验收边界》](./第二阶段验收边界.md)

## 1. 阶段目标

第二阶段将原项目已有管理能力和 OpenClaw 能力完整接入 U-Claw 原生客户端。完成后，高级控制台只保留诊断用途，不再承担永久功能缺口。

本阶段不改变第一阶段形成的 Electron、React、Adapter、Launcher 和 U 盘数据架构，不重做客户端骨架。

## 2. 进入条件

以下条件是第二阶段整体完成和正式发行门槛。为缩短周期，可以在契约边界稳定后提前开发独立功能包，但未满足这些条件前不得宣称第二阶段完成或生成正式发行版：

1. 功能矩阵中的“基础”和“第一阶段”项均已验收。
2. Win10/11 x64 首启、二启、换机、拔盘和进程清理通过。
3. React 只依赖 U-Claw shared 契约，不直接依赖 OpenClaw 原始 payload。
4. Adapter 已具备版本能力检测、错误转换、重连和日志脱敏。
5. 配置、API Key、会话、记忆和工作文件的唯一持久副本位于 U 盘。

## 3. 功能包一：会话整理与成果

需求编号：`CHAT-003`、`CHAT-013`、`CHAT-014`

交付内容：

- 会话搜索、固定和分组，支持大量历史会话整理。
- U 盘交付形态按单用户自有设备设计，不区分“普通用户”和“超级管理员”；设备持有人可管理全部可见会话与自建分组。
- OpenClaw 内部主会话 `agent:main:main` 只供运行时使用，不进入用户会话列表；顶部“新建会话”必须创建并打开独立用户会话。
- 所有可见会话支持新建、重命名、删除、固定和分组；所有自建分组支持新建、重命名和删除。
- 删除分组只删除整理元数据，组内会话必须保留并回到“未分组”，已固定状态必须保留。
- 全局任务活动中心，聚合长任务、工具、渠道、更新和错误事件。
- 成果文件页签，允许从文件、代码、表格等产物回到来源会话。

会话整理数据边界：

- OpenClaw 继续作为真实会话、消息历史、标题、模型和运行状态的唯一权威来源，U-Claw 不复制聊天记录。
- 当前锁定版本未证明 `sessions.patch` 支持固定和分组；第二阶段由 Electron 主进程将这两项 U-Claw 自有元数据保存到 U 盘 `.uclaw/data/uclaw/session-organizer.json`。
- 元数据使用版本化严格 schema，只记录 `sessionId`、`pinned` 和 `groupId`；renderer 只能通过白名单 IPC 读写领域对象，不能传入任意路径。
- 文件必须同目录临时写入、刷新并原子替换；写入失败保留上一版，不得影响 OpenClaw 会话和历史。
- OpenClaw 会话被删除后，孤立整理项在受控清理时移除；元数据损坏时只降级为未固定、未分组，会话和消息不能丢失。
- 后续 OpenClaw 若提供已验证的固定、分组协议，先迁移和写后回读，再停用本地字段；迁移前禁止向 `sessions.patch` 透传未经 fixture 证明的参数。

验收重点：

- 搜索、固定、分组状态换机后保持一致。
- 删除或损坏整理元数据只影响固定和分组，不影响 OpenClaw 会话及消息历史。
- 新建、重命名、删除会话及新建、重命名、删除分组均可从新 UI 完成；删除分组后组内会话仍可见。
- 活动中心能区分运行、等待操作、成功和失败状态。
- 产物来源关系准确，不重复复制用户文件，不绕过 U 盘数据边界。

## 4. 功能包二：模型与 Provider

需求编号：`MODEL-001`–`MODEL-006`

交付内容：

- 原生管理多个 Provider，支持新增、编辑、启停、排序和逐个验证。
- 保留并验证原项目已有的虾盘云、MiniMax、Kimi、DeepSeek、GLM、Qwen、豆包、OpenAI、Claude、Groq、硅基流动等服务商。
- 通过受控 IPC/Adapter 管理 API Key，renderer 不读取已保存的完整明文。
- 保留 OpenAI-compatible 纯自定义服务，支持 Base URL、API Key 和模型名。
- 发现并选择 Ollama、LM Studio 等本地模型。
- 提供模型连通测试，区分网络、认证、模型名和响应格式错误。
- 管理代理与 `NO_PROXY`，避免内网模型错误经过系统代理。

验收重点：

- 多个 Provider 并存时互不覆盖，当前选择真实生效。
- 日志、错误、导出和 renderer 响应不泄露完整 Key。
- 自定义服务、本地模型和原有服务商均完成真实请求验证。
- 本阶段只完成用户可见 Provider 能力；隐藏内置 New API 属于第三阶段。

## 5. 功能包三：技能、插件与 MCP

需求编号：`CAP-001`–`CAP-007`

交付内容：

- 展示已安装技能、版本、来源、更新状态和 OpenClaw 可用状态。
- Electron Node 本地后端直连 SkillHub.cn，提供免费 Skill 的榜单、搜索、分类和详情。
- 支持免费 Skill 安装、更新、卸载、进度、失败清理和回滚。
- 支持技能启用、禁用、依赖和冲突提示。
- 独立实现插件的列表、安装、更新、卸载和状态管理。
- 独立实现 MCP 服务器新增、编辑、启停、删除和连接状态。
- 高风险技能、插件和 MCP 能力启用前展示权限与风险。

验收重点：

- Skill、Plugin、MCP 使用独立领域契约，不混用安装流程。
- SkillHub 列表和安装接口都拒绝付费 Skill，不能只依赖前端过滤。
- 安装目标只能是当前 U 盘允许的持久目录，renderer 不能指定任意绝对路径。
- 更新失败保留旧版，卸载不误删用户自建目录。

## 6. 功能包四：渠道与连接

需求编号：`CONN-001`–`CONN-006`

交付内容：

- 原生配置 Telegram、QQ Bot、飞书、企业微信。
- 完成个人微信扫码、刷新、超时、登录成功、失效和退出登录流程。
- 在“连接”页统一显示渠道健康、凭据状态和待处理操作。

验收重点：

- 每个渠道完成真实连接、消息收发、断开和错误场景验收。
- 缺插件、凭据错误、二维码失效和网络错误有不同提示。
- 渠道凭据遵守 U 盘持久化与日志脱敏要求。

## 7. 功能包五：文件、记忆与数据维护

需求编号：`DATA-001`、`DATA-002`、`DATA-007`、`DATA-008`

交付内容：

- 原生浏览、搜索、打开、重命名、移动和删除工作区文件。
- 原生查看、搜索、编辑和删除 AI 记忆。
- 提供备份预览、恢复确认、保留策略和失败回滚。
- 提供存储空间分类统计和受控清理。

验收重点：

- 文件操作不能越出当前 U 盘工作区。
- 记忆修改结果与 OpenClaw 实际读取结果一致。
- 恢复失败可回到原状态，清理不删除配置、会话、记忆和用户文件。

## 8. 功能包六：日志、诊断与系统维护

需求编号：`OPS-001`–`OPS-005`、`OPS-007`、`OPS-009`

交付内容：

- 原生日志查看、级别筛选、搜索、脱敏导出和保留策略。
- 原生 OpenClaw Doctor 检查和受控修复。
- 原生内网、离线、DNS、代理、端口、认证和模型诊断。
- 展示可脱敏复制的系统信息。
- 提供恢复出厂的删除范围、备份入口、二次确认和执行结果。
- 提供原始配置的只读脱敏视图与受控导出。

验收重点：

- 日志和导出不包含 Key、Token、请求头和对话正文。
- 修复与恢复操作可审计，失败保留诊断信息。
- renderer 不能借由原始配置页面绕过敏感字段脱敏。

## 9. 功能包七：更新、发行与安全

需求编号：`REL-001`、`REL-003`、`REL-006`、`REL-007`、`SEC-004`

交付内容：

- 原生更新检查，覆盖无网、无更新、有更新和检查失败。
- 下载签名 runtime 包，执行兼容性验证、原子切换和失败回滚。
- 为 runtime 包和清单验证可信发行者数字签名。
- 系统页原生诊断与高级控制台替代面向普通用户的 CLI/Doctor 快捷方式，`REL-006` 按“不迁移”验收。
- U 盘版无需卸载，提供只清除本机可重建 runtime 缓存的入口。

验收重点：

- 篡改 runtime 包、版本清单或签名后无法启动。
- 更新失败不破坏当前可用 runtime 和 `.uclaw/data/`。
- 缓存清理不删除 U 盘数据。

## 10. 功能包八：暗色主题

需求编号：`UX-008`

暗色主题在其他第二阶段功能完成后实施。所有页面、浮层、表单、图表、Markdown、代码块和状态色统一使用已冻结语义 Token，不为暗色主题重写业务组件。

验收重点：

- 启动过程无白闪。
- 所有页面无错层、低对比度和不可读内容。
- Win10/11 的 100%、125%、150% 缩放均通过验收。

## 11. 实施顺序

1. 先冻结各功能包 shared schema、Adapter fixture 和权限边界。
2. 会话、模型、能力、渠道、数据和诊断功能包可在契约稳定后并行实施。
3. 更新、签名和回滚在发行链路稳定后实施。
4. 高级控制台永久缺口清零后实施暗色主题。
5. 每个功能包独立测试、验收和更新总功能矩阵，不等待阶段末统一补状态。

## 13. 第二阶段验收条件

- 39 项第二阶段需求均为“已完成”或已有明确批准的“不迁移”结论。
- 原项目已有主要管理能力均有原生入口，不依赖隐藏网页或脚本菜单。
- 高级控制台只作诊断，不承担永久功能缺口。
- 所有写操作经过 shared schema、Adapter 或受控 Electron IPC。
- 国产模型、自定义模型、本地模型、技能、渠道、文件和诊断主流程完成真实环境验证。
- 更新失败可回滚，runtime 篡改可被拒绝，U 盘用户数据不受影响。
- 亮色、暗色及 Windows 三档缩放完成全页面验收。

## 14. 第二阶段不交付

- U 盘启动许可证和设备身份。
- 制盘时自动创建 New API 用户和 Token。
- 用户不可见的内置默认模型服务。
- 自有 New API 的额度、限速、模型权限和封禁管理。
- macOS、Linux、Windows ARM 产品包。
- 独立本机安装版。

以上商业授权与内置服务能力统一进入第三阶段。
