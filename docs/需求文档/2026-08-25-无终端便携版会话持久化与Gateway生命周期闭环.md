## 1. 结论

当前“会话丢失”不能简单归类为一个普通 bug。

它是无终端便携版在以下生命周期链路上没有闭环：

```text
Gateway 运行期
-> 会话落盘期
-> 本机 Data 工作缓存同步期
-> U 盘 data 权威主库回写期
-> 下次启动恢复期
```

无终端启动只解决“不显示外部终端窗口”的体验问题。

无终端启动本身不能保证会话不丢。

必须先补齐会话持久化和 Gateway 生命周期闭环，再把无终端便携版作为正式交付形态。

## 2. 问题

### 2.1 用户可见问题

当前可能出现：

```text
Gateway 掉了
-> 用户只能重启 Bavi-box
-> 重启后当前聊天记录不见
-> 表现为“整个会话丢了”
```

用户感知是会话丢失。

实际可能有几种不同情况：

1. 最新消息没有写入 transcript。
2. 本机 Data 工作缓存有新记录，但尚未同步回 U 盘 data。
3. 下次启动时旧 U 盘 data 覆盖了本机 Data 工作缓存。
4. Gateway 重启后 UI 打开了新的 dashboard session key，旧会话仍在 Sessions 页或文件中。
5. 退出时 Gateway 被强杀，sqlite WAL、session jsonl 或 sessions.json 仍有未收尾状态。

### 2.2 当前链路缺口

当前已确认的风险链路：

```text
Gateway 异常退出后，Electron 主进程只标记 gatewayReady=false，不自动重启 Gateway。
```

```text
App 退出时 stopGateway() 发送 SIGTERM，5 秒后仍未退出则 SIGKILL。
```

```text
便携启动脚本启动时先把 U 盘 data 镜像到本机 Data 工作缓存。
```

```text
Mac 使用 rsync --delete。
Windows 使用 robocopy /MIR。
```

```text
如果 U 盘 data 比本机 Data 工作缓存旧，下次启动可能用旧数据覆盖新会话。
```

```text
当前没有运行中 portable sync / journal / checkpoint 机制。
```

```text
当前没有退出等待界面，也没有明确的 flush / fsync / checkpoint / final sync 状态。
```

### 2.3 不能接受的交付形态

以下形态不能作为正式无终端便携版交付：

```text
只隐藏终端窗口。
只让 Electron 后台 spawn Gateway。
只在正常退出后同步 data。
启动时仍无条件 USB data -> cache --delete。
Gateway 掉线后仍要求用户重启整个 App。
重启后不能回到原 sessionKey。
Gateway stdout/stderr 不落盘。
```

## 3. 为什么这样设计

### 3.1 U 盘 data 必须是权威主库

Bavi-box 是便携产品。

用户预期是：

```text
U 盘插到哪里，数据就在哪里。
```

因此：

```text
<USB>/Bavi-box/data/
```

必须是权威便携主库。

本机 Data 工作缓存可以存在，但只能作为高速工作副本，不能成为聊天、配置、记忆、license、设备绑定材料的唯一副本。

### 3.2 本机 Data 工作缓存仍然必要

OpenClaw 运行期有大量小文件、sqlite、jsonl、缓存和浏览器相关读写。

直接让所有随机小写长期打到 U 盘，会带来：

1. 启动和运行变慢。
2. ExFAT 文件锁和权限风险增加。
3. Windows 杀毒软件干扰增加。
4. U 盘异常拔出时更容易产生半写状态。

所以设计应保留：

```text
本机 Data 工作缓存
```

但必须新增：

```text
运行中增量回写 U 盘 data
启动前冲突检测
退出前最终同步
异常恢复机制
```

### 3.3 不能只依赖退出同步

只在退出时同步有天然漏洞：

```text
Gateway 崩溃
App 卡死
用户强关
系统重启
U 盘拔出
脚本二次启动
```

任一情况都可能让本机 Data 工作缓存的新会话未回写到 U 盘。

如果下次启动又执行镜像覆盖，本机新数据可能被旧 U 盘 data 删除。

因此必须引入运行中 checkpoint / journal / sync。

### 3.4 Gateway 生命周期必须由 Electron 主进程托管

无终端版中，用户不再看到 Gateway 终端。

所以 Electron 主进程必须负责：

1. 启动 Gateway。
2. 捕获 stdout/stderr。
3. 检测 Gateway 掉线。
4. 自动重启 Gateway。
5. 恢复当前 sessionKey。
6. 退出时受控停止 Gateway。
7. 记录结构化日志。

无终端后如果没有这些能力，故障会从“用户可见终端错误”变成“App 黑盒异常”。

## 4. 怎么实现开发

### 4.1 开发目标

本需求目标：

```text
补齐无终端便携版的会话持久化与 Gateway 生命周期闭环。
```

不做：

```text
启动强制更新。
production.json / manifest.json 更新器。
签名验签。
staging/current 原子切换。
OpenClaw runtime 重写。
聊天协议重写。
```

### 4.2 推荐开发顺序

#### P0-1 启动前数据保护

修改便携启动脚本和/或 Electron Bootstrap。

启动前不能无条件执行：

```text
USB data -> 本机 Data 工作缓存 --delete
```

需要新增：

1. 本机 Data 工作缓存是否比 U 盘 data 更新的检测。
2. 本机 Data 工作缓存存在未回写 marker 时，先备份 U 盘 data。
3. 同步前生成启动前快照。
4. 冲突时保留两边数据，不直接删除。
5. 明确写入日志。

推荐 marker：

```text
<WORK_DATA>/data/.uclaw-sync/dirty.json
<WORK_DATA>/data/.uclaw-sync/last-sync.json
<USB_DATA>/.uclaw-sync/last-sync.json
```

#### P0-2 运行中增量回写

新增 portable sync 服务。

监听或定时检查关键路径：

```text
.openclaw/agents/*/sessions/sessions.json
.openclaw/agents/*/sessions/*.jsonl
.openclaw/agents/*/agent/*.sqlite
.openclaw/agents/*/agent/*.sqlite-wal
.openclaw/state/*.sqlite
.openclaw/state/*.sqlite-wal
.openclaw/openclaw.json
.openclaw/workspace/
.openclaw/memory/
.openclaw/devices/
logs/
memory/
backups/
```

实现策略：

1. debounce 合并小写。
2. 关键会话文件优先同步。
3. sqlite 同步前 checkpoint WAL 或确保同组文件一致。
4. 同步失败不杀 App，但写日志并保留 dirty marker。
5. U 盘不可写时进入 degraded 状态，提示用户。

#### P0-3 Gateway watchdog

修改 Electron 主进程。

Gateway 退出时不能只做：

```text
gatewayReady = false
```

需要：

1. 判断是否用户主动退出。
2. 非主动退出时自动重启 Gateway。
3. 使用指数退避，避免死循环。
4. 重启后加载原 Dashboard URL。
5. 恢复当前 sessionKey。
6. 记录 gateway exit reason、code、signal、restart count。

推荐状态：

```text
starting
ready
exited
restarting
failed
stopping
```

#### P0-4 当前 sessionKey 持久化

主进程或前端需要保存当前 sessionKey。

推荐位置：

```text
<WORK_DATA>/.openclaw/uclaw-ui-state.json
<USB_DATA>/.openclaw/uclaw-ui-state.json
```

内容示例：

```json
{
  "activeSessionKey": "agent:main:dashboard:...",
  "updatedAt": "2026-08-25T00:00:00.000Z"
}
```

Gateway 重启或 App 重启后：

1. 优先恢复 activeSessionKey。
2. 如果 sessionKey 不存在，打开最近非归档会话。
3. 如果没有会话，再创建新会话。

#### P0-5 退出收口

App 退出必须变成受控流程：

```text
用户退出
-> 标记 stopping
-> 停止新请求
-> flush UI state
-> flush / checkpoint 会话和 sqlite
-> final sync 本机 Data 工作缓存 -> U 盘 data
-> 停 Gateway
-> 停 video adapter
-> 停 Config Server
-> 等待子进程退出
-> 超时强杀
-> 写退出日志
-> App 退出
```

不能先杀 Gateway，再尝试保存关键状态。

#### P1-1 无终端日志落盘

Gateway stdout/stderr 必须落盘。

目标文件：

```text
<USB_DATA>/logs/main.log
<USB_DATA>/logs/gateway.log
<USB_DATA>/logs/config-server.log
<USB_DATA>/diagnostics/desktop-logs/uclaw-gateway.jsonl
```

要求：

1. 敏感信息脱敏。
2. 日志轮转。
3. 启动失败也能定位。
4. U 盘不可写时写本机 fallback log，并标记 dirty。

#### P1-2 退出等待界面

退出等待界面必须接真实状态，不做假进度。

状态：

```text
正在保存会话
正在同步 U 盘数据
正在停止本地服务
正在关闭 Gateway
正在写入日志
正在完成退出
```

若同步失败：

```text
提示用户不要拔 U 盘。
给出日志路径。
允许重试。
```

常规入口不得提供“跳过保存并退出”。

### 4.4 当前实现记录

本轮已在正式开发目录实现 P0 最小闭环：

```text
u-claw-app-dev/src/main.js
u-claw-app-dev/scripts/Mac-Start-App.command
u-claw-app-dev/scripts/Windows-Start-App.bat
```

已实现：

1. 启动脚本不再使用 `rsync --delete` / `robocopy /MIR`。
2. 启动脚本检测 `.uclaw-sync/dirty.json`，发现未同步 marker 时先备份 U 盘 data，再把本机 Data 工作缓存回写到 U 盘。
3. Electron 主进程支持 `UCLAW_USB_DATA_DIR`，运行时每 30 秒把本机 Data 工作缓存同步回 U 盘 data。
4. Electron 主进程写入 `.uclaw-sync/dirty.json` 和 `.uclaw-sync/last-sync.json`。
5. Electron 主进程在 Gateway 异常退出时自动重启，并写入 `logs/main.log`。
6. Gateway stdout/stderr 落盘到 `logs/gateway.log`。
7. 退出时按 `before-stop sync -> stop Gateway -> stop video adapter -> after-stop sync` 顺序收口。
8. UI 当前会话 key 写入 `.openclaw/uclaw-ui-state.json`。
9. 恢复会话时使用 `/chat?session=...#token=...` 入口，避免仅打开 dashboard 根路径。
10. Gateway 子进程默认剥离宿主 shell 的 `http_proxy` / `https_proxy` / `all_proxy` 等标准代理环境变量，避免用户终端坏代理污染模型请求。
11. 如确需继承宿主 shell 代理，可显式设置 `UCLAW_INHERIT_SYSTEM_PROXY=1`；OpenClaw/龙虾自己的显式代理配置仍保留。

当前仍未实现：

1. SQLite WAL 显式 checkpoint。
2. 文件级增量 watcher / debounce。
3. U 盘不可写时的前端 degraded 状态提示。
4. 退出等待界面。
5. Windows 真机异常注入验证。

## 5. 验收

### 5.1 必测场景

#### A. 正常聊天后退出

步骤：

```text
启动无终端便携版
发送一轮文本对话
等待回复完成
关闭 App
重新启动
```

预期：

```text
上次会话仍在。
最近消息仍在。
U 盘 data/.openclaw/agents/main/sessions/ 下有对应 sessions.json 和 *.jsonl。
日志记录 final sync success。
```

#### B. Gateway 进程被杀

步骤：

```text
启动 App
发送一轮对话
手动杀 Gateway node 子进程
等待 Electron 主进程 watchdog
继续发送消息
```

预期：

```text
App 不退出。
Gateway 自动重启。
UI 恢复连接。
当前 sessionKey 不变。
会话记录连续。
日志记录 gateway exit 和 restart。
```

#### C. App 被强关后重启

步骤：

```text
启动 App
发送一轮对话
回复完成后强制结束 App
重新启动
```

预期：

```text
不会用旧 U 盘 data 覆盖本机新 Data 工作缓存。
若存在未回写 dirty marker，先进入恢复/合并流程。
旧 U 盘 data 自动备份。
会话最大只允许丢最后一次未完成写入，不允许整段丢失。
```

#### D. 启动脚本二次启动

步骤：

```text
在本机 Data 工作缓存比 U 盘 data 更新时再次运行启动脚本
```

预期：

```text
脚本不得直接 rsync --delete / robocopy /MIR 覆盖新缓存。
必须检测 dirty marker 或 mtime/hash 差异。
必须保留本机新会话。
必须写入恢复日志。
```

#### E. 删除本机 Data 工作缓存

步骤：

```text
正常退出 App
删除本机 Data 工作缓存
重新从 U 盘启动
```

预期：

```text
U 盘 data 可恢复完整会话。
配置、记忆、设备绑定、日志存在。
```

#### F. U 盘异常拔出

步骤：

```text
运行中拔出 U 盘或模拟 U 盘不可写
继续观察 App 状态
```

预期：

```text
App 进入 degraded 状态。
不破坏既有 U 盘 data。
本机 Data 工作缓存保留新数据。
重新插入后可重试同步。
日志记录 sync failure。
```
