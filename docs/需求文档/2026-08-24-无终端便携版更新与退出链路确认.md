# Bavi-box 无终端便携版更新与退出链路确认

- 日期：2026-08-24
- 文档类型：决策确认与后续需求承接
- 状态：已确认方向，待补充后续更新需求
- 影响范围：无终端便携版、Electron 主进程、Gateway 生命周期、更新 Bootstrap、发布包结构、日志展示

## 1. 结论

Bavi-box 后续目标形态为：

```text
无终端便携版
= 便携数据模型
+ 桌面 App 启动模型
```

它不是普通安装版。

普通安装版的核心特征是数据默认进入宿主机用户目录。

无终端便携版的核心特征是：

- 用户不再看到外部终端窗口。
- Electron 主进程托管 OpenClaw Gateway。
- 数据、配置、日志、记忆和备份仍强制留在 U 盘数据目录。
- 更新按 Bavi-box 整包更新处理，不允许只让 OpenClaw runtime 自行更新。

## 2. 当前便携版与目标形态差异

现有脚本便携版中，外部终端承担 Gateway 宿主职责。

典型命令为：

```text
node app/core/node_modules/openclaw/openclaw.mjs gateway run --allow-unconfigured --force --port <port>
```

用户关闭该终端，Gateway 即停止。

目标无终端便携版中，该命令由 Electron 主进程通过子进程拉起。用户看到的是 Bavi-box App，不看到独立终端。

## 3. 数据目录硬规则

无终端便携版必须强制使用 U 盘数据目录。

建议外层启动器或 Bootstrap 明确设置：

```text
UCLAW_PORTABLE_DATA_DIR=<USB>/data
OPENCLAW_HOME=<USB>/data
OPENCLAW_STATE_DIR=<USB>/data/.openclaw
OPENCLAW_CONFIG_PATH=<USB>/data/.openclaw/openclaw.json
```

Electron 主进程可继续保留“检测 .app 旁边 portable 目录”的兼容逻辑，但正式便携发行不应只依赖该猜测。

禁止把正式便携版用户数据写入宿主机目录。

## 4. 更新链路确认

Bavi-box 不直接采用原版 OpenClaw 的 `openclaw update` 作为产品更新链路。

原因：

- Bavi-box 包含 Electron 壳。
- Bavi-box 内置 Node runtime。
- Bavi-box 内置并 patch OpenClaw。
- Bavi-box 有 Config Center、中文化、适配器和 SkillHub 改造。
- Bavi-box 有 Mac/Windows 便携发布结构。
- 单独更新 OpenClaw runtime 会绕过 Bavi-box 的打包、验证和兼容边界。

Bavi-box 更新链路按整包更新设计。

目标流程：

```text
启动 Bavi-box
-> Bootstrap 检查服务端版本 manifest
-> 发现本地不是 requiredReleaseSequence
-> 下载完整新包
-> 校验 sha256、manifest 和签名
-> 解压到 staging
-> 请求正式 App 进入退出/停机流程
-> 停 Gateway、Config Server、其它子进程
-> 原子切换程序目录
-> 重启 Bavi-box
-> 新版本启动失败时按服务端修复版本策略处理
```

数据目录不参与覆盖：

```text
data/
data/.openclaw/
data/logs/
data/memory/
data/backups/
```

程序目录可参与替换：

```text
app/
portable/lib/
Config.html
Welcome.html
SkillHub.html
其它随包静态资源
```

## 6. 退出链路确认

无终端便携版中，Electron 主进程是 Gateway 生命周期 owner。

退出流程必须由主进程收口：

```text
用户点击退出
-> 显示退出等待界面
-> 标记正在停止
-> 停止 Gateway
-> 停止 Config Server
-> 停止 video adapter / 其它附属子进程
-> flush 日志和关键状态
-> 等待子进程退出
-> 超时后强杀残留子进程
-> App 退出
```

当前 Bavi-box 主进程已有基础停止逻辑：

```text
gatewayProcess.kill('SIGTERM')
5 秒后仍未退出则 SIGKILL
```

后续需要补齐用户可见等待界面、结构化日志、退出原因和更完整的子进程管理。

## 7. 退出等待界面

退出等待界面是必要能力，不是装饰。

目的：

- 告知用户正在保存和停止服务。
- 避免用户误以为卡死。
- 降低用户直接拔 U 盘导致脏状态的概率。
- 给 Gateway、日志和缓存收尾时间。
- 超时强杀时给出明确结果。

建议状态：

```text
正在保存数据
正在停止本地服务
正在关闭 Gateway
正在写入日志
正在完成退出
已强制停止残留进程
```

退出等待界面不得提供跳过安全退出的常规入口。

## 8. 日志链路确认

无终端后，stdout/stderr 不能丢。

必须落盘到 U 盘数据目录，并能在 Bavi-box 设置或诊断页面查看。

建议文件：

```text
data/logs/main.log
data/logs/gateway.log
data/logs/config-server.log
data/diagnostics/desktop-logs/uclaw-gateway.jsonl
```

日志要求：

- Gateway stdout/stderr 必须捕获。
- 主进程启动、退出、更新、子进程管理事件必须记录。
- 敏感信息必须脱敏。
- 日志写入失败不得阻断启动或退出。
- 日志应有大小限制和轮转。

## 9. 原版 OpenClaw 行为边界

原版 OpenClaw 支持：

```text
openclaw gateway run
openclaw gateway install
openclaw gateway start
openclaw gateway stop
openclaw gateway restart
openclaw update
```

原版 CLI 前台模式收到 `SIGINT` / `SIGTERM` 会停止进程。

但原版 OpenClaw 不负责 Bavi-box 的桌面退出等待界面，也不负责 Bavi-box 的整包更新事务。

Bavi-box 必须自己管理：

- Electron App 退出体验。
- Gateway 子进程生命周期。
- U 盘数据目录不漂移。
- 整包更新、验签、切换和重启。

## 10. 已确认风险

### 10.1 退出不干净

通常不会导致下次完全不能用。

可能后果：

- 旧 Gateway 残留占用端口。
- 下次启动改用后续端口。
- 残留进程继续占资源。
- 配置或会话写入中断。
- 缓存、browser profile 或锁文件残留。
- 首启变慢或局部页面异常。

因此退出链路必须做等待、超时和强杀。

### 10.2 日志不可见

无终端后，如果不落盘，启动失败会变成黑盒。

因此日志展示必须保留到客户端设置或诊断页。

### 10.3 状态目录漂移

如果环境变量或便携路径推断失败，数据可能落入宿主机。

这是无终端便携版的 P0 风险，必须通过启动器、Bootstrap 和主进程三层约束。

## 11. 后续待补需求

后续更新相关需求继续补充到本链路下，重点待定：

- manifest 字段最终版。
- releaseSequence 与 contentVersion 映射。
- Mac `.app` / DMG / ZIP 便携结构。
- Windows EXE / ZIP 便携结构。
- Bootstrap 进程形态。
- 更新时是否允许 App 内展示进度，还是必须在独立 Bootstrap 窗口展示。
- 更新失败后服务端修复版本等待页。
- 更新包目录切换策略。
- 旧版本保留数量。
- 日志查看 UI 的入口和脱敏规则。
