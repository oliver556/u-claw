# U-Claw 打包策略与 Key 保留评估

- 日期：2026-08-27
- 文档类型：评估 / 规格输入
- 状态：待冻结
- 适用范围：客户便携版、主播/内部便携版、远程强制更新

## 0. 2026-08-27 冻结决策

```text
视频 provider 走公网 adapter。
当前生产先保留旧公网 adapter：https://video-adapter.gmnlee.com/xai/v1。
服务器和 yiyong.me 路由配置完成后，再切到 https://yiyong.me/uclaw/video/xai/v1。
公网 adapter 首选部署香港网络优化机。
阿里云 1C1G3M 只做 license/device/token/发布控制，不做视频主链路承载。
硬更新采用方案 C：阿里云 update check 返回 R2 下载地址，R2 承载静态更新包下载。
Phase 1 / staging 允许使用 R2 public r2.dev URL；prod 由阿里云控制是否下发。
旧主播盘 key 不做手动修复工具。
新盘 key 由激活链路写入 data。
普通打包部署和远程硬更新都不能覆盖 data。
```

## 1. 结论

当前“key 老是丢”的根因不是单个打包命令失败，而是三条规则叠加后没有写清优先级：

```text
stage 初始化 data/.openclaw/openclaw.json
旧 U 盘部署必须保留 data/
远程硬更新永远不能包含 data/
```

因此必须把 key 规则拆成两类：

```text
新盘初始化规则
旧盘保留规则
远程更新排除规则
```

硬规则：

```text
客户版 stage 可以生成空 key。
主播版 stage 在激活链路完成前，可从本机桌面配置或 UCLAW_NEW_API_KEY 继承真实 New API key，用于内部验证/母盘过渡。
主播版正式新盘 key 后续由激活链路写入 data。
部署到已有 U 盘时，永远不能覆盖目标盘 data/.openclaw/openclaw.json。
远程硬更新包永远不能包含真实 key，也不能修复旧盘 key。
旧盘 key 缺失，属于旧盘数据问题，不属于硬更新问题。
```

跨规格生命周期边界见：

```text
docs/需求文档/2026-08-27-便携版生命周期边界冻结草案.md
```

## 2. 当前事实

源码入口：

```text
u-claw-app-dev/scripts/package-portable.js
u-claw-app-dev/scripts/sync-openclaw-config.js
u-claw-app-dev/resources/default-openclaw.json
```

当前打包行为：

```text
assembleStage()
-> 生成 release/portable-<edition>/U-Claw
-> stage 内初始化 data/.openclaw/openclaw.json
-> streamer 版额外写 auth_profile_store sqlite

deploy()
-> 覆盖 app/、launcher、脚本、说明
-> 仅当目标盘没有 data/ 时 copy stage/data
-> 目标盘已有 data/ 时输出 data preserved
```

这符合“旧盘 data 永不覆盖”，但也意味着：

```text
如果目标盘已有 data/ 且 openclaw.json 缺 key，
部署 streamer 新包也不会修复该 key。
```

这是正确的数据保护结果，不应通过覆盖 data/ 修复。

## 3. Key 来源矩阵

| 场景 | 允许写入真实 New API key | 来源 | 是否覆盖已有 data |
|---|---:|---|---:|
| 客户版新 stage | 否 | 空模板 | 不适用 |
| 客户版新盘初始化 | 否 | stage/data | 仅 data 不存在时 |
| 客户版旧盘部署 | 否 | 保留旧盘 data | 否 |
| 主播版新 stage | 是 | 桌面配置或 `UCLAW_NEW_API_KEY` | 不适用 |
| 主播版新盘初始化 | 是 | stage/data | 仅 data 不存在时 |
| 主播版旧盘部署 | 不主动写 | 保留旧盘 data | 否 |
| 远程硬更新 | 否 | 不包含 data | 否 |

## 4. 必须冻结的边界

打包脚本负责：

```text
生成客户版空 key 模板。
生成主播版带 key stage。
新盘初始化 data/。
旧盘部署时保留 data/。
输出 data initialized 或 data preserved。
验证 stage 类型正确。
验证 customer 不含真实 key。
验证 streamer stage 含真实 key。
```

打包脚本不负责：

```text
覆盖旧盘 data/.openclaw/openclaw.json。
修复旧盘缺失 key。
迁移旧盘 key。
删除旧盘聊天、skills、memory、license、logs。
在远程更新包中携带真实 key。
```

硬更新负责：

```text
下载、校验、替换程序层。
保留 data/。
保留 openclaw.json hash。
更新后重启 launcher。
```

硬更新不负责：

```text
初始化 streamer key。
补写 New API key。
读取开发机桌面配置。
把 key 从远程包写入 U 盘。
```

## 5. 旧盘 key 缺失处理

旧盘部署时发现 streamer key 缺失，本轮不提供手动修复工具。

原因：

```text
旧盘正常情况下应该已有 key。
新盘 key 后续由激活链路写入。
硬更新和普通部署必须保持 data 不变。
手动修复会和激活链路、license/device 边界冲突。
```

若未来必须修复，只能另立需求，不混入本轮：

```bash
cd <repo>/u-claw-app-dev
npm run sync:config -- --streamer --usb /Volumes/<USB>
```

执行前提：

```text
用户明确要求修复该盘配置。
该盘确认为主播/内部盘。
本机桌面配置或 UCLAW_NEW_API_KEY 有真实 New API key。
脚本先备份原 openclaw.json。
脚本输出新旧 hash、key present、备份路径。
```

禁止：

```text
普通 package:portable deploy 自动调用该修复。
远程硬更新自动调用该修复。
为了让旧盘可用而覆盖 data/。
本轮开发该修复工具。
```

## 6. 当前风险

### R1：视频地址历史冲突已冻结

历史上文档写过本机 adapter：

```text
providers.xai.baseUrl = http://127.0.0.1:18808/xai/v1
```

历史上代码和默认模板写过旧公网 adapter：

```text
providers.xai.baseUrl = https://video-adapter.gmnlee.com/xai/v1
```

冻结结论：

```text
视频 provider 走公网 adapter。
当前目标地址保留 https://video-adapter.gmnlee.com/xai/v1。
yiyong.me 路由完成后，目标地址再切到 https://yiyong.me/uclaw/video/xai/v1。
代码里的本机 adapter fallback 需要在后续生命周期修复中收口或转为仅 dev/debug。
```

### R2：旧盘 data preserved 被误判为打包失败

如果目标盘 `data/.openclaw/openclaw.json` 本来缺 key，部署后仍缺 key，是 `data preserved` 的必然结果。

验收必须区分：

```text
stage streamer key present
目标旧盘 openclaw.json hash unchanged
目标旧盘 key state unchanged
```

不能用“旧盘更新后 key 仍缺失”直接判定 package streamer 失败。

### R3：R2 与阿里云职责混淆

方案 C 冻结：

```text
R2 只放 production.json / manifest.json / runtime.pkg / sha256 / sbom / public keys。
R2 不做 license/device 鉴权。
R2 不保存真实 key。
R2 Access Key / Secret Key 只存在本机 .env 或 CI secret。
阿里云 update check API 返回当前设备可用的 R2 下载 URL。
阿里云不转发 runtime.pkg 大文件，避免 1C1G3M 带宽成为瓶颈。
香港机不参与硬更新控制链路；香港机优先用于 New API / video adapter。
```

当前真实 R2：

```text
staging bucket: u-claw-updates-staging
staging public URL: https://pub-8289f643846848528b61bfd5dbf17e43.r2.dev
prod bucket: u-claw-updates-prod
prod public URL: https://pub-4f24fbbe718b4c75955440700c70bdeb.r2.dev
```

### R4：auth_profile_store 与 openclaw.json 双配置

streamer stage 目前同时写：

```text
data/.openclaw/openclaw.json
data/.openclaw/agents/main/agent/openclaw-agent.sqlite
```

旧盘部署保留 data/ 时，两者都不会被覆盖。

因此旧盘如果 sqlite 内 auth profile 缺失，也不会被普通部署修复。

## 7. 验收口径

打包验收：

```text
[ ] `npm run package:portable:customer` 退出码 0
[ ] customer stage `custom/litellm.apiKey` 为空
[ ] `npm run package:portable:streamer` 退出码 0
[ ] streamer stage `custom/litellm.apiKey` present
[ ] streamer stage auth_profile_store present
[ ] Git diff / stage notes / logs 不泄露真实 key
```

旧盘部署验收：

```text
[ ] 部署前记录目标 data/.openclaw/openclaw.json sha256
[ ] 部署后输出 data preserved
[ ] 部署后 openclaw.json sha256 不变
[ ] app/、launcher、脚本、说明已更新
[ ] archive hash 与 stage 一致
```

新盘初始化验收：

```text
[ ] 目标盘部署前无 data/
[ ] 部署后输出 data initialized
[ ] customer 新盘 key empty
[ ] streamer 新盘 key present
[ ] openclaw.json 存在
[ ] auth_profile_store 按 edition 符合预期
```

硬更新验收：

```text
[ ] update package 不含 data/
[ ] update package 不含 .openclaw/
[ ] update package 不含 openclaw.json
[ ] update 前后 openclaw.json hash 不变
[ ] update 不改变 key state
[ ] update 后 launcher/app 正常启动
```
