# Bavi-box 独立更新器方案定稿

- 日期：2026-08-31
- 文档类型：正式方案 / 发货更新路径定稿
- 状态：已实现，待 Review
- 适用范围：Bavi-box U 盘交付、Windows 更新入口、macOS 更新入口、现有启动硬更新链路复用边界

## 1. 结论

本轮发货与后续客户更新，统一改为：

```text
独立更新器
= 与 Bavi-box 主程序同级放置
+ 用户手动双击
+ 联网拉取远端更新包
+ 校验后替换当前 U 盘程序层
+ 保留 data 与配置
```

本轮不再采用：

```text
启动前强制硬更新
```

客户可见更新入口固定为两个文件：

```text
Bavi-box Win Update.exe
Bavi-box Mac Update.command
```

它们都放在 U 盘根目录、与主程序同级：

```text
<USB>/Bavi-box/
├─ Bavi-box.exe
├─ Bavi-box.app
├─ Bavi-box Win Update.exe
├─ Bavi-box Mac Update.command
├─ app/
├─ data/
└─ .openclaw/
```

用户动作固定为：

1. 把更新入口保留在 U 盘根目录。
2. Windows 用户双击 `Bavi-box Win Update.exe`。
3. macOS 用户双击 `Bavi-box Mac Update.command`。
4. 更新器联网检查新版本，下载当前平台更新包。
5. 校验通过后替换程序层。
6. 更新结束后提示启动，或直接帮助启动。

## 2. 为什么这样定

本需求真正要解决的是：

```text
客户只做一件事：
双击更新入口
-> 更新完成
```

更新本质确实只是：

```text
拉取
-> 校验
-> 解压
-> 替换
```

但用户“双击同一个物理文件，同时给 Win 与 Mac 原生执行”不成立。

原因不是更新逻辑复杂，而是操作系统入口格式不同：

- Windows 原生双击入口通常是 `.exe/.bat/.cmd/.ps1`
- macOS 原生双击入口通常是 `.app/.command`
- 同一个物理文件不能同时稳定满足两边原生双击、签名、交付与客户支持要求

因此本方案收口为：

```text
用户侧两个清晰入口
实现侧尽量一套更新核心
```

这样比“单文件跨平台幻觉方案”更稳，也比一堆脚本和临时文件更清楚。

## 3. 当前启动硬更新现状

当前仓库内，启动硬更新代码并没有彻底删除。

当前真实状态是：

```text
启动链路仍保留硬更新调用点
但默认由环境变量关闭
```

现状细节如下：

1. Windows 启动脚本仍会进入 `run_startup_hard_update`。
2. macOS 启动脚本仍会进入 `run_startup_hard_update`。
3. 两边都先判断：

```text
UCLAW_ENABLE_STARTUP_HARD_UPDATE == 1
```

4. 若不是 `1`，直接输出：

```text
[Bavi-box] Startup hard update disabled by environment.
```

5. 也就是说，当前不是“逻辑已删完”，也不是“完全注释死”，而是：

```text
代码还在
默认不跑
```

这点要写清，避免后续误判为“仓库里已经没有可复用更新实现”。

## 4. 当前链路里已经可复用的部分

现有启动硬更新实现里，真正有价值的不是“放在启动前”这件事，而是下面这些能力已经基本成型。

### 4.1 已有远端更新协议

现有 Node 客户端已经能处理：

- `production.json`
- `manifest.json`
- `runtime.pkg`
- update check API 返回的下载地址
- 平台与架构匹配
- 包大小限制
- SHA-256 校验
- 签名校验
- tree digest 校验

也就是说：

```text
更新包能不能下
下完是不是对
是不是当前平台能装
```

这些核心判断不是从零开始。

### 4.2 已有受控暂存与事务文件

现有链路已经有：

```text
app/update-transaction.json
app/.update-staging/<transaction-id>/
```

并且事务状态已经分成：

```text
checking
downloading
downloaded
verifying
extracting
staged
waiting-for-app-exit
switching
switched
cache-invalidated
restarting
complete
failed
```

这说明：

```text
更新过程有状态机
不是一把梭覆盖
```

### 4.3 已有程序层替换与保护边界

现有实现已明确拒绝覆盖：

```text
data/
.openclaw/
openclaw.json
auth_profile_store
auth-profile-store
*.env
*.key
```

并且只允许安装/替换受控根目录。

这部分非常关键，因为它正好符合 Bavi-box 当前产品边界：

```text
只换程序层
不碰客户数据层
```

### 4.4 已有 staged 后 apply 的两段式流程

当前启动硬更新已经拆成：

```text
startup-update
apply-startup-update
```

这意味着现在不是“边下载边乱改盘”，而是：

```text
先下载与验包
-> 再等主程序退出
-> 再执行替换
```

这套分段思路可以直接转成独立更新器。

### 4.5 已有应用退出请求协议

现有实现会写：

```text
app/.runtime/update-shutdown-request.json
```

这说明当前主程序与更新器之间已经有“请求退出后更新”的协议雏形。

独立更新器方案里，这部分仍然能参考。

## 5. 当前链路为什么不适合继续放在启动前

虽然当前链路“能下、能验、能 staged、能 apply”的概率不低，但它放在启动前，产品体验和稳定性都不好。

核心原因：

### 5.1 启动链路职责太重

启动链路本来应该只负责：

```text
启动
缓存解压
数据同步
打开主程序
```

如果再塞入硬更新下载与替换，就会把问题混在一起：

- 是启动慢
- 还是下载慢
- 还是验包慢
- 还是解压慢
- 还是程序锁没释放

客户和支持都很难判断。

### 5.2 更新失败会污染启动体验

只要硬更新放在启动前，就容易出现：

```text
客户想打开 Bavi-box
-> 先卡在更新
-> 更新失败
-> 看起来像“软件打不开”
```

这和客户心理预期相反。

### 5.3 启动与更新的日志、状态、异常语义混在一起

当前启动脚本要同时管：

- 本地缓存解压
- runtime data sync
- 主程序退出码
- startup-update 结果
- apply-startup-update 结果

这会让问题排查非常绕。

### 5.4 发货前已明确策略：默认关闭启动硬更新

发货策略已经偏向：

```text
启动修复优先
启动硬更新默认关闭
更新改成独立入口
```

所以现阶段继续把主要精力投入“启动前硬更新打磨”，方向不对。

## 6. 新方案：独立更新器

### 6.1 目标形态

独立更新器只解决一件事：

```text
客户主动更新当前 U 盘里的 Bavi-box 程序层
```

它不负责：

- 首次激活
- 启动门禁
- 正式业务 UI
- 自动静默更新
- 后台常驻

### 6.2 客户入口命名

本轮正式命名固定为：

```text
Bavi-box Win Update.exe
Bavi-box Mac Update.command
```

后续若 macOS 体验要升级，可在不改产品命名语义前提下改成：

```text
Bavi-box Mac Update.app
```

但本轮先不强制。

### 6.3 摆放位置

更新入口与主程序同级，不再藏在深层目录：

```text
<USB>/Bavi-box/
├─ Bavi-box.exe
├─ Bavi-box.app
├─ Bavi-box Win Update.exe
├─ Bavi-box Mac Update.command
├─ app/
├─ data/
└─ .openclaw/
```

这样客户和客服都容易沟通：

```text
“打开 U 盘根目录，双击对应更新器”
```

## 7. 独立更新器流程

### 7.1 Windows

```text
用户双击 Bavi-box Win Update.exe
-> 更新器定位当前 U 盘根目录
-> 读取本地版本
-> 请求远端 production.json 或 update-check
-> 发现有新版本
-> 下载 win32-x64/runtime.pkg
-> 验签、sha256、tree digest 校验
-> 提示关闭 Bavi-box，或主动等待主程序退出
-> 替换 app/ 与受控程序文件
-> 保留 data/ 与 .openclaw/
-> 清理 staging
-> 提示“更新完成，是否启动 Bavi-box”
```

### 7.2 macOS

```text
用户双击 Bavi-box Mac Update.command
-> 更新器定位当前 U 盘根目录
-> 读取本地版本
-> 请求远端 production.json 或 update-check
-> 发现有新版本
-> 下载 darwin-arm64/runtime.pkg 或 darwin-x64/runtime.pkg
-> 验签、sha256、tree digest 校验
-> 提示关闭 Bavi-box，或主动等待主程序退出
-> 替换 app/ 与受控程序文件
-> 保留 data/ 与 .openclaw/
-> 清理 staging
-> 提示“更新完成，是否启动 Bavi-box”
```

### 7.3 共用规则

两边都必须遵守：

1. 不覆盖 `data/`
2. 不覆盖 `.openclaw/`
3. 不覆盖真实 key、token、环境文件
4. 不接受降级包
5. 不接受签名错误包
6. 不接受 hash 错误包
7. 只替换程序层
8. 失败后保留日志

## 8. 与现有硬更新代码的关系

### 8.1 可以直接复用

建议直接复用或抽取的部分：

- `scripts/hard-update-client.js` 的远端检查逻辑
- `scripts/hard-update-client.js` 的下载逻辑
- `scripts/hard-update-client.js` 的 manifest / package 校验逻辑
- `scripts/hard-update-client.js` 的 staging / transaction 写入逻辑
- `scripts/hard-update-client.js` 的 installFromStaging 安装逻辑
- `scripts/lib/hard-update-utils.js` 的路径安全、hash、解压等工具
- `scripts/updater/main.go` 的程序层替换边界与禁止路径模型

其中真正值得优先复用的是 Node 这条主链路。

原因：

1. 当前远端更新协议已经在 `hard-update-client.js` 收口。
2. 当前下载、验签、解压、staging、安装已经跑在同一份逻辑里。
3. 当前主进程已经能识别 `update-shutdown-request.json` 并执行退出收口。
4. 现阶段重写一套 Go/其它语言“完整更新客户端”成本高、回归面大。

因此，Phase 1 的正确方向不是“重写更新内核”，而是：

```text
保留现有 Node 更新内核
把启动前调用方式抽出来
改成独立更新器调用
```

### 8.2 不能直接照搬

下面这些不能原样沿用：

1. **启动前触发方式**
   - 现在是 launcher 启动时调用
   - 新方案要改成用户主动双击独立更新器

2. **退出码语义**
   - 当前 `20` 代表“已 staged，launcher 负责 apply+relaunch”
   - 独立更新器不能再依赖启动脚本兜这个分支

3. **命名与路径仍有旧名残留**
   - 代码和文档里仍有 `U-Claw`、`uclaw`、旧 URL 路径残留
   - 新方案要统一客户可见名为 `Bavi-box`

4. **Go updater 允许根目录仍偏旧名**
   - 当前 `scripts/updater/main.go` 的允许根项里仍有 `U-Claw.exe`、`U-Claw.app`
   - 如果后续要用它作为正式替换器，需要补齐 Bavi-box 命名边界

5. **现有 apply 时机绑在 launcher**
   - 当前 `apply-startup-update` 依赖启动链路等待 pid 退出、再重新拉起
   - 独立更新器要自己承担这段控制流

6. **现有一段式路径里有 mock 逻辑**
   - `mockUpdate()` 虽然接近“一次完成下载、校验、安装”
   - 但里面包含 `writeRunStateMock()`、`writeShutdownCompleteMock()` 这类测试辅助逻辑
   - 不能直接作为正式客户更新入口

7. **独立更新器首次运行时不一定已有本机 app cache**
   - 当前启动链路通常先完成 app cache 安装，再调用盘内 Node 更新脚本
   - 独立更新器不能默认假设 `APP_CACHE_DIR` 已经存在
   - 需要单独设计 Node/runtime 定位顺序

## 9. 独立更新器实现建议

### 9.1 Phase 1

优先目标不是“最优雅”，而是：

```text
先稳定交付一个客户可用更新入口
```

建议 Phase 1 做法：

- Windows：`Bavi-box Win Update.exe`
- macOS：`Bavi-box Mac Update.command`
- 内部尽量共用现有更新核心
- 先跑通“下载 -> 校验 -> 替换 -> 启动”

Phase 1 的核心实现判断：

```text
先抽现有 Node 更新逻辑
不先重写更新算法
```

更具体地说，优先从 `scripts/hard-update-client.js` 抽出一个正式新入口，例如：

```text
independent-update
```

它的目标不是再分成：

```text
startup-update
+ apply-startup-update
```

而是独立完成整条客户更新路径：

```text
检查版本
-> 下载 runtime.pkg
-> 验签 / 校验
-> 解压到 staging
-> 请求正在运行的 Bavi-box 退出
-> 等待主程序与相关子进程退出
-> 安装 staging 到当前 U 盘
-> 失效本机 cache stamp
-> 写回新版本
-> 清理 staging
-> 启动 Bavi-box
```

### 9.2 关于 Node

现有硬更新链路已经证明：

```text
盘内 / 包内 Node 可以跑更新逻辑
```

因此 Phase 1 不需要因为“必须完美”而重写整套更新核心。

但也要承认：

```text
Node 不是这件事最轻的壳
```

所以本方案对 Node 的态度是：

- 它可以作为现阶段复用现有逻辑的实现细节
- 它不应该成为客户侧额外安装要求
- 后续若要更轻量，可再把壳迁到 Go 或别的更薄执行器

也就是说：

```text
先复用
不先重写
```

这里再补一个实现边界：

```text
客户不需要自己安装 Node
更新器只允许使用 Bavi-box 自带 Node / runtime
```

也就是：

- Node 可以作为实现依赖
- 但不能变成客户环境前置条件

### 9.3 Node 运行时定位策略

独立更新器如果继续复用 Node 内核，必须先解决：

```text
从哪里拿到可执行 Node
```

Phase 1 建议按下面顺序找：

1. 当前机器上已存在的 Bavi-box app cache 内 Node
2. 当前 U 盘程序层内已存在的 Node runtime
3. 当前 U 盘 archive 中可提取出的最小 Node/runtime

不建议依赖：

- 用户系统 PATH 里的 Node
- 用户自行安装的 Node

原因：

1. 客户环境不可控。
2. 版本不一致会放大更新问题。
3. 这会把“Bavi-box 更新器”变成“依赖宿主机开发环境”的工具，产品上不可接受。

因此 Phase 1 的推荐策略是：

```text
优先用 Bavi-box 自带 Node
找不到才报错
不碰系统 Node
```

当前实现把三个平台 runtime 压缩放在 U 盘：

```text
<USB>/Bavi-box/app/update-runtime/node-darwin-arm64.tar.gz
<USB>/Bavi-box/app/update-runtime/node-darwin-x64.tar.gz
<USB>/Bavi-box/app/update-runtime/node-win32-x64.zip
```

双击入口先解压对应 runtime 到本机临时缓存，再运行同一份
`app/scripts/hard-update-client.js`。不依赖系统 Node，也不直接执行 U 盘上的
`node`，避免更新时文件锁。

独立更新默认请求生产发布索引：

```text
https://download.yiyong.me/uclaw/releases/production.json
```

灰度或测试时，可通过 `--production-url` 或
`UCLAW_UPDATE_PRODUCTION_URL` 覆盖。

当前发布归属必须明确：

```text
正式独立更新器默认入口 = 64 前置机公开下载入口
64 前置机 = 64.90.19.251
远端发布目录 = /srv/uclaw-updates/releases
公开入口 = https://download.yiyong.me/uclaw/releases/production.json
```

R2 只能作为历史方案或临时验证记录保留，不得作为当前独立更新器默认入口。
当前独立更新器源码、测试盘入口、发布 runbook 若仍指向 `r2.dev`，都必须改回
`https://download.yiyong.me/uclaw/releases/production.json` 后再做客户测试。

### 9.3.1 2026-08-31 正式发布链路更新

当前正式发布链路已从 R2 切到 64 前置机静态目录。

正式脚本：

```text
u-claw-app-dev/scripts/hard-update-upload-front64.js
u-claw-app-dev/scripts/publish-hard-update-release.js
```

废弃脚本：

```text
u-claw-app-dev/scripts/hard-update-upload-r2.js
```

`hard-update-upload-r2.js` 只保留为失败保护入口。执行时必须直接失败，提示改用
`hard-update-upload-front64.js`，避免误传 R2。

正式一键发布命令：

```bash
cd u-claw-app-dev
npm run hard-update:publish -- \
  --stage release/portable-customer/Bavi-box \
  --version 1.0.1 \
  --channel prod \
  --confirm-prod
```

执行流程：

```text
hard-update-package create
-> hard-update-package verify
-> hard-update-upload-front64
```

`hard-update-upload-front64` 的远端流程：

```text
1. 清理同 releaseId 旧目录。
2. 创建远端 bootstrap/ 与 packages/<releaseId>/<platform>/。
3. 上传 release-public-keys.json、manifest.json、runtime.pkg、runtime.pkg.sha256、sbom.json。
4. 在 64 机子上校验 SHA-256。
5. 上传 production.json 到 .production.json.tmp。
6. 校验通过后再原子切换为 production.json。
7. 清理 AppleDouble 文件、旧 releases.tmp-*、releases-test。
8. 只保留最近 3 个 packages 版本。
```

正式保留策略：

```text
/srv/uclaw-updates/releases/packages/
  只保留最新 3 个 vX.Y.Z 目录。
```

例：

```text
已有：v1.0.1、v1.0.2、v1.0.3
发布：v1.0.4
保留：v1.0.2、v1.0.3、v1.0.4
删除：v1.0.1
```

旧版本不再转存 R2。原因：

```text
客户只需要当前生产版本。
故障回滚应发布更高版本号的新包，而不是让客户端回退到旧包。
旧包长期保留会持续占用服务器空间。
```

如需临时保留更多版本，可发布时传：

```bash
npm run hard-update:publish -- ... --keep 5
```

### 9.4 独立更新器入口壳职责

Win/Mac 两个入口壳不应该承载更新算法。

它们只做三件事：

```text
定位 U 盘根目录
定位 Bavi-box 自带 Node/runtime
调用独立更新命令
```

建议控制在“薄壳”级别。

也就是说：

- Windows 外壳负责找到 `node.exe` 并执行更新命令
- macOS 外壳负责找到 `bin/node` 并执行更新命令
- 具体下载、验签、解压、替换，不在壳里重写

### 9.5 Phase 2

若 Phase 1 落地后发现：

- Node 启动太慢
- 平台路径查找太绕
- 双击体验不够产品化

则再做：

- Windows 独立编译更新器
- macOS 独立编译更新器或 `.app`
- 但保持同一远端协议、同一 manifest、同一替换边界

## 10. 远端发布物要求

独立更新器继续使用现有发布物模型，不新开一套野路子：

```text
production.json
manifest.json
runtime.pkg
```

并继续按平台拆包：

```text
win32-x64
darwin-arm64
darwin-x64
```

不做“一个全平台大包”。

原因：

- 体积大
- 客户下载慢
- 解压慢
- 校验慢
- 两端文件内容本来也不同

## 11. 必须保留的安全边界

独立更新器必须继续遵守以下硬规则：

### 11.1 禁止覆盖

```text
data/
.openclaw/
openclaw.json
auth_profile_store/
auth-profile-store/
*.env
*.key
```

### 11.2 禁止行为

- 不做任意路径覆盖
- 不接受 path traversal
- 不接受符号链接逃逸
- 不接受非规则文件
- 不接受降级安装
- 不接受签名错误包

### 11.3 失败策略

更新失败时至少做到：

```text
写日志
保留事务状态
不破坏当前 data
不把半包当成功版本
```
